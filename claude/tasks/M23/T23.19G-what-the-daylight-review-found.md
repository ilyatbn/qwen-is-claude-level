- **F3 (medium, can go red on its own): the pickup mask is x-only, over every item on the map.**
  `bullets-visible.mjs::columnProfile` projects every `debug().itemPositions` entry to a strip column with
  `(i.x - worldView.x) * zoom - clip.x` and never reads `i.y`. `GameScene.ts` fills `itemPositions` from
  `this.mirror.items`, which is every item in the world (up to `MAX_WORLD_ITEMS`, 40), not only those in view. So a
  pickup anywhere above or below the lane, whose x falls inside the strip, removes `2·PICKUP_RADIUS·zoom + 1`
  (41 at zoom 1) columns from both the lane and the control. The masked share grows as items pile up during the
  check, and the lane's own columns can be masked, which gives a false "no bright column". **Do:** mask only items
  whose y is within the strip's y-range ± `PICKUP_RADIUS`, and log how many columns were masked. Check: plant an item
  far above the lane at the lane's x; with the fix it is not masked, and before the fix it is.

### T23.11 (`bcc5b30`)

- **F5 (medium, visible, undocumented): space maps are now F5's moonlit day all the time.** `GameScene.ts` calls
  `setDaylight(nightShare(darkness, …), …)` with `darkness = sceneDarkness(space, …)`, which returns 0 in space
  (`sky-math.ts::sceneDarkness`). So on a space map `t` is always 0, and `WorldRenderer.blendHour` hands every frame
  F5's look and `F5.palette`: terrain lighting, bloom, grade, exposure and combat palette. Before T23.11 space drew
  F1's. `gameDescription`'s own comment still says "its bloom and grade stay F1's until T23.20", which is now false.
  **Do:** decide which look space gets and state it at `gameDescription`. The minimum is to hand `t = 1` (F1, as
  before and as the comment says) when `map.space`. Check: a unit test that `gameDescription({space: true})` plus
  `setDaylight(0, u)` yields F1's `look.grade`/`bloom`, and that a ground map at t=0 yields F5's (the control).

- **F6 (medium, GPU tier, a hitch at a gameplay moment): the sky compiles new shader programs in the middle of a
  match.** `skyMaterial.ts::setColours` calls `define('NSET'|'DSET', …)`, which sets `mat.needsUpdate` whenever a
  moon set's weight crosses 0. The round starts in day (NSET 0, DSET 1). The first dusk, 60 s in, needs (1, 1) and
  full night needs (1, 0). Each is a program three compiles on first use. `WorldRenderer`'s warm-up covers
  `glowLayer`, `fxLayer` and `warmTerrain` only; no sky variant is warmed (`grep -n "warm\|compile"` over
  `worldRenderer.ts` and `skyMaterial.ts`). So the first dusk and the first night of every match each stall a frame
  while a program compiles. **Do:** compile all three variants at `setScene` (`renderer.compile` per define set, or
  draw once in each). Check: `__world.info().memory.programs` is equal before and after the clock is pushed through
  dusk and night in a live match. Planted out (no warm), the count rises at dusk.

- **F7 (low-medium): the moon arcs copy `cycle.rs`'s phase table as literals, and nothing checks them against the
  darkness curve.** `daylight.ts` hardcodes `DAY_MOON_U = 0.25`, `NIGHT_MOON_U = 0.76` and
  `MOON_REACH = [0.37·…, MOON_SAG·0.74·0.74]`. The 0.37 and 0.26 are 0.62 − 0.25 and 0.76 − 0.50, worked out by hand
  from `DUSK_START`, `NIGHT_START` and `DAWN_START`. `MOON_TRAVEL` 1600 and `MOON_SAG` 240 are numeric tunables that
  are not in `constants.rs`. If a phase boundary moves, a set can be visible (`vis > 0`) past the extent it was baked
  to (`SkyQuad.reach`), and that is a moon clipped at the bake edge with no test red.
  `daylight.test.ts::jumps back only where its end is invisible` sweeps hand-picked u-ranges (0–0.5, 0.5–1). It
  never reads `darknessAt`, so it cannot see this. **Do:** derive the anchors and the reach from the phase table
  (`sky-math.ts::darknessAt` / `cycle.rs`), or add the test that pins them. Check: a vitest that sweeps u in steps of
  0.001 and, wherever `nightShare(darknessAt(u))` gives a set `vis > 0`, asserts `|arcOffset(u, ref)| <= MOON_REACH`.
  Planting `NIGHT_MOON_U = 0.70` must turn it red.

- **F8 (low): tests pin tunables as literals** (CLAUDE.md: never hardcode a number in a test).
  `look-sky.mjs::NIGHT_MOON_T = 0.76 * 120` and `look-day-night.mjs::DAY_T = 30` ("0.25 of the 120 s cycle") both
  hardcode the cycle length and the moon anchors. `daylight.test.ts` uses `nightShare(…, 0.82)`, where it should
  use `NIGHT_DARKNESS`. **Do:** read `DAY_DURATION + NIGHT_DURATION` from `rust-constants.mjs`, as
  `look-day-night-match.mjs` already does, and import the anchors.

- **F9 (low, a test that cannot fail for a class of bug): the continuity test skips every field that snaps.**
  `daylight.test.ts::is continuous` reads each leaf as `m.has(k) ? channels(…) : null` and skips NaN pairs. A field
  that `mixValue` switches at `t = 0.5` (null against an object, arrays of unequal length, `mixString`'s "nearer end"
  for a non-colour string) exists on only one side of the switch, so it is compared nowhere. A visible pop at
  mid-dusk would pass. **Do:** collect the paths whose value changes type or presence between adjacent steps, and
  assert that list equals a named allow-list. Today that is the `FADED` keys (`sun`, `rays`, `rayColor`, `moons`) at
  the ends, plus any shape strings. Check: making F5's `fogFront` null turns it red.

- **F10 (info, a label only):** m9-checkpoint's `night < day * 0.75` and space-sky's `dm.mean - nm.mean > 15`, both
  restored and described as T23.11 putting them back, hold with the blend deleted. The night view darkens everything
  outside the sight circle, and `look-day-night-match.mjs`'s own header says so. They gate "night costs something",
  which is right, but they are not evidence for the blend. `look-day-night-match` is that evidence. Fix the two
  comments so no one later retires `look-day-night-match` as redundant.
