### Item 4 — why the owner's round replayed with the shovel alone
**The room's privacy was never recorded.** The registry tells a room it is private with `Command::SetIdentity`, a moment
after the room task has already written the replay header — and `SetIdentity` was "not recorded: registry bookkeeping".
But privacy is simulation input: `check_settings_change` refuses every lobby setting in a public room, and a private
lobby starts on consent rather than on the bot timeout. The owner's file body: `SetBots(0,false)` @231,
`SetBots(0,true)` @262, `SetStartKit(0,Basic)` @314, `SetStartKit(0,All)` @339, `Ready` @650/@701 — a private lobby.
Replayed public, both `SetStartKit`s were refused: the human held the shovel, as T23.26E saw.

Fix: `ReplayCommand::SetPrivate` (tag 26, appended, no version bump — the policy at `REPLAY_VERSION`) noted in the
`SetIdentity` arm, mapped back by `to_command`; and `replay.rs::infer_privacy` restores it for older files — sound in one
direction only (a recorded private-only setting proves the live check passed, which needs a private room).

Measured on the owner's file at its own code (255fc7d's runner + the inference as an env switch, scratch only; player 0's
resting places against the live `state.jsonl`, matched per 30 s): **without** 2/2 6/11 1/8 0/12 0/6 … (first miss
18.5 s); **with** 2/2 11/11 6/8 1/12 0/6 … (first miss 58.6 s, health 83 — a hit). The kit: 1 stack → 16. **But the
checkpoints still do not match — 0 of 27, first at tick 1200, mid-warmup, with or without** — so the world beyond the
human differs from the start (most likely the bots: `make start` is `cargo run` on the main tree's working copy; runners
at 255fc7d, ab38d33, 1753990 and 3e7765b all give 0/27, and so does `DEV_BOT_FRENZY`). **For the coordinator: a replay
file does not name the build that recorded it**, so this cannot be settled from the file; a build id in the header (with
a dirty flag) would.

Falsified (`tests/replay_run.rs::a_human_style_private_session_replays_to_the_footer_hash`, both arms green unplanted):
- the note removed from the `SetIdentity` arm → `kit in lobby false: a human's private session did not reproduce (the
  replayed human holds 15 stacks)` (the config-kit arm: privacy is all that says the lobby started on consent);
- that plus `infer_privacy` off → `kit in lobby true: … (the replayed human holds 1 stacks)` — the owner's symptom.

**Addendum — the second cause: the buried secret.** The owner's header carries `buried_secret` `0x90a249364fc7904d`
(the server ran without `FIXED_SEED`), and the replayed room ignored it: `to_config` sets `fixed_seed`, and a
`fixed_seed` room derives secret 0 — a different buried hand from the first tick. Every other replay test pins the
seed, so both sides were 0 and nothing could see it. With privacy **and** the header's secret, the 255fc7d runner
matches **4 of 27** checkpoints (1200–3000; was 0), first mismatch at tick 3600; the human's health track then
matches the live one to ~50 s, where a bot hit lands differently. Fixed in `Room::for_replay` (T23.29 item 2's
commit); test `a_room_with_an_unpinned_seed_replays_with_its_own_buried_secret` (plant → red). What diverges by
3600 is not settled from the file: the build that recorded it is not named (a build id in the header would settle
it), and runners at four nearby commits do no better. The warmup length was a third unrecorded input (v40 now
records it).
