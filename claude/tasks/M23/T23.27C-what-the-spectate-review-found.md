# T23.27C — What the spectate / daylight-fix review found

Code-only review of `2a146e0` (T23.19G), `b24636f` (T23.27 server), `674874f` (T23.27 client) and `f9b5f3c` (journal),
2026-10-01. Read as committed (`git show <sha>`, `git show <sha>:<path>`). Nothing was run: a builder held the box.
Each finding says how it was checked. Not yet started.

## Do

- **F1 (medium, spec: "its inputs and commands do nothing"): a spectator can start a lobby, a private one included.**
  `session.rs`'s `start_with_bots` handler sends `Command::StartWithBots(id)` for any seated socket ("Any player in
  the room may press it"). `room.rs::Room::apply`'s `StartWithBots` arm calls `request_start()`, and
  `Room::request_start` checks only `phase() == Lobby`. Neither reads `has_body`. So a spectator seated in a lobby of
  waiting humans starts the match on them. In a private room it also skips §E3's everyone-ready consent: `seat()`
  honours `"spectate": true` on **every** verb, `join_room` by code included. The guard is also per-arm today. `Input`
  and `VoteRestart` check `has_body`, while `UseItem`, `SelectSlot`, `MoveItem`, `DropItem`, `UseHeal`,
  `UseBatteryPack`, `QuickThrow`, `UseAt` and `Fire` reach the world (no-ops only because no body exists) **and are
  recorded** into the replay. Input, by contrast, is "neither applied nor recorded".
  **Do:** use one guard, shared: at the top of `Room::apply`, refuse every per-id command whose seat `!has_body()`.
  Leave `Ready`, `Leave` and `ResyncMap` alone, because the latch, the departure and the resync are a seat's, not a
  body's. Reply `false`/`None` where the arm has a reply. Then delete the two per-arm checks.
  *(Checked: `grep -n "Command::StartWithBots" room.rs session.rs`, `Room::request_start` body, the arms listed.)*
  **Check:** a unit test in which a lobby holds a human and a spectator, the spectator's `StartWithBots` and 300 ticks
  leave `phase() == Lobby`, and the human's `StartWithBots` (the control) starts the match. A second test asserts
  that `recorded_commands()` is unchanged across a spectator's `UseItem`/`Fire`.

- **F2 (medium, a spec claim with no test): "a recorded watched match replays identically" (`docs/78` §A1) is
  asserted by nothing.** The only spectator replay test is the tag round-trip (`replay.rs::tests`, `every_command`).
  `tests/replay_run.rs::a_recorded_round_replays_to_the_same_state_hash` has no spectator twin. There is a second gap,
  which predates this work but is now hit every round: `Room::restart` opens a **new file** (`start_recording`) and
  writes no seat roster into it. Only round one's file holds the `JoinSpectator`. From round two on, a replay has no
  reserved spectator id, so `seat_bots` allocates different ids than the live round did. A watched room never goes
  back to a lobby, so after its first round it produces nothing but files of this kind. (Human rounds two and later
  have the same hole. `tests/replay.rs` checks only round two's *header*.)
  **Do:** add a `replay_run.rs` test that records a round with one spectator seated in the lobby and one seated
  mid-round, re-simulates it, and gets the same `state_hash`. Plant `to_command` mapping `JoinSpectator` →
  `Command::Join`: the test must go red. State the round-two roster gap in `replay.rs`'s header comment. Fixing it
  (a roster preamble per file) needs a format change, so it goes to the coordinator.

- **F3 (medium): "a spectator may join at any time" is unreachable from the client and untested on the server, and
  the comment that called that path unreachable is still there.** `registry.rs::quick_match` skips
  `has_started()` rooms, and the client's `{ kind: 'spectate' }` only ever emits `join`, which is quick match. So the
  live-join path (`session.rs::seat`'s map_init and `catch_up_world` catch-up, dormant since §E4) is reachable only
  through `join_room` by code, which nothing sends, and no test reaches it. In `seat()` the new line "the catch-up
  below is live again for it" sits directly on top of the old "**Dormant since §E4, and deliberately so** … unreachable
  in production" paragraph, and the inventory/catch-up comment further down still says "Dormant with the `map_init`
  catch-up above". CLAUDE.md: a comment claiming an invariant is an intention, so check it.
  **Do:** (a) add an integration test (`tests/in_progress.rs` is the home): a socket joins a **started** room with
  `"spectate": true` and receives `map_init`, the catch-up events and snapshots; its id is absent from
  `world.players`; and the control, the same join unflagged, is refused `in_progress`. (b) Rewrite the dormant
  comments to say what is now true. (c) Ask the coordinator whether a spectator's quick match should prefer a
  **started** room. As built, `make watch` against a server with a live match makes a new room.

- **F4 (medium-low): the watched room's real start is untested.** `a_watched_room_restarts_on_its_own` calls
  `room.request_start()`, so it never runs the path `make watch` depends on: `Command::Spectate` → `arm_bot_timeout()`
  → `tick_once`'s `timed_out` → start. A `Spectate` arm that stopped arming the timeout would pass every test, and
  the room would sit in a lobby forever (the sweep's item 4, one door earlier).
  **Do:** add a test in which a spectator-only public room, with no `request_start` and ticked past
  `config.lobby_bot_timeout`, reaches `Playing` with `bot_count() > 0`. Control: the same in a **private** room stays
  `Lobby`. Plant: remove the `arm_bot_timeout()` call from the `Spectate` arm, and the test goes red.

- **F5 (low-medium): legs of `spectate.mjs` that cannot fail for the thing they name.**
  (a) The "line names B" leg passes on any line containing `SPECTATING` and not `waiting`, so a line naming A, or
  `p3`, passes. Assert that it contains B's name (`debug().scores` or the roster) and, after Shift+Tab, A's.
  (b) Nothing asserts that the HUD shows **the watched player's** numbers (task: "name, health, energy, jet and
  weapon"). Add `debug().hud.health` (or the bar's value) equal to B's snapshot health after Tab. The control is that
  A and B differ: give them different `DEV_START_HEALTH` spend, or assert it only when they differ and log otherwise.
  (c) The viewpoint leg (`dv <= VIEW_TOL`) is close to a tautology: `viewAt` and `drawnPlayers` both come from the
  same `sampled` map in one frame (`GameScene.update` → `viewer(sampled)` / `renderRemotes(sampleAt, sampled)`). The
  camera-centre leg is the real evidence, so say so in the header. (d) Leg 1 never asserts that `d0.me` is a seated id
  (≥ 0). A `-1` passes "not in its own snapshot" vacuously.

- **F6 (low): `a_spectators_commands_do_nothing`'s control is described and not written.** Its doc says "The control
  is a player's fire in the same match, which the world accepts". The code only asserts that `p` has a body and never
  fires as `p`. The `Input` half cannot fail either: `World::queue_input` returns early for an id with no
  `newest_input` slot, so removing the `has_body` early return in the `Input` arm leaves the test green.
  **Do:** fire as `p` and assert `Ok` (or a projectile/use event). For input, assert that `recorded_commands()` is
  unchanged and that the spectator seat's `last_seq` is still 0. Plant: delete the `Input` arm's guard, and the test
  goes red.

- **F7 (low): spectators are uncapped, and quick match counts them as occupants.** `Seats::alloc_spectator` has "no
  cap but the id pool's". The pool is the room's 256 `u8` ids, so enough spectating sockets make every later `Join`
  `alloc` return `None` ("full") and also stop `seat_bots`. `RoomEntry.humans` counts spectator sockets in
  `quick_match`'s `e.humans >= max_players`, so a lobby with five humans and a watcher at `max_players` 6 is skipped.
  That is a change for humans in a room with a spectator, and the task said "behave exactly as today". The comment
  calls it "the cautious side".
  **Do:** add `MAX_SPECTATORS` to `constants.rs` (with its basis) and refuse past it in `alloc_spectator`. Either count
  only players in `quick_match` (a second counter on `RoomEntry`) or get the coordinator's ruling on the current
  behaviour. Test: N+1 spectators → the last is refused, and a `Join` still seats.

- **F8 (low, rustdoc rot): `arm_bot_timeout` was inserted between `kick_newest_bot`'s doc comment and its `fn`.**
  `arm_bot_timeout`'s rustdoc now opens "Free a seat for a human by removing the newest bot…", and `kick_newest_bot`
  has no doc. `Seat.spectator`'s doc says it is read by "the world's two doors (`populate_world`, the in-match
  `Join`)", but the in-match `Join` arm never reads `has_body`. That arm is player-only by construction, since
  `Spectate` is its own command, so say that instead.

- **F9 (low, client): spectate mixes the viewer's and the watched player's state.** `meAlive` is set only from
  `s.players.find(p => p.id === this.me)` (absent for a spectator, so it stays `true`), while `irradiated`, `health`,
  `vision` and `flashlight` come from the watched row. `radiation.update(…, this.meAlive, this.irradiated &&
  this.meAlive, …)` therefore follows a watched player's radiation through their death. When `watch.watching` is
  `null` (nobody alive), the HUD keeps the last player's numbers and does not blank them.
  **Do:** in spectate, take `meAlive` from the watched row (or route both through `viewId()`), and blank the bars when
  `viewId() === -1`. Vitest or `debug()` leg: watch a player who dies, and `radiation` / alive follow them.

- **F10 (low, T23.19G): `effect-lights`' `drawnLights()` does not hide a dropped light, but the inconsistency it
  routed around is not filed.** Checked `bothWays`. The light must be once in `__world.lights()` (held) **and** once
  in `drawnLights()`, otherwise it throws "held but the terrain did not draw it". A light `pickLights` evicted is
  therefore a red check, not an invisible one, so that part is sound. What the fix does hide: `setActors([])` takes
  the actors out of both reads because "the actors are lit by the renderer's whole list, uncapped". So when the held
  list exceeds the tier's slots (12 gates + muzzle + impact against 10 on the low tier), a gate's orb glows from a
  light whose rock is unlit. That is a visible terrain/actor disagreement, recorded only as a check workaround in
  the As-built. No check now measures an effect light on actors.
  **Do:** file it for the coordinator. Either light actors from `pickedLights` (one list, shared) or state at
  `WorldRenderer` that actors take the uncapped list on purpose. `worldHandle.ts` and `effect-lights.mjs` were outside
  T23.19G's Touch only. That is justified by the coordinator's "own `effect-lights` here", but the As-built should say
  so.

### Checked and fine
- No body: `populate_world` and `human_count` filter `has_body`. `Seats::alloc` caps on bodies (no bot kicked; the
  twin test has a real control). `last_seqs`/snapshots reach the spectator, it is absent from `lobby_state` and
  `roster`, `settings_owner` and the private ready rule exclude it, and `acks_before` skips it (no
  `last_simulated_seq`). `seat_bots` caps through `alloc`, so 6 bots + a watcher = 6 bots.
- Restart: `restart_wins(humans) || (watched && window_closed)` sits inside the `!resolved && (window_closed || …)`
  gate. A human + spectator room is `watched() == false`, so a silent human still goes `ToLobby` (the unit control).
  A human leaving mid-round with a watcher left makes the room watched, the registry keeps it alive (sockets), and it
  restarts. That matches §A1.
- Client: no core body, predictor or local view in spectate. Every input handler is guarded, and the step/send block
  is inside `if (predictor)`. `viewer()` feeds the camera, `renderRemotes`' circle (`localPos = this.viewAt`), the
  minimap (`rp`), the night view (`rp`) and `ear()`. `debug().player` is `null`. `spectating` survives a server
  restart (`resetForNewRound` runs only from `create`/`SHUTDOWN`).
- T23.19G F6 `SkyQuad.warm` and the F7 derivations (`MOON_SHOWN_K` gives 0.37/0.26 from 0.50/0.62/0.90, the same as
