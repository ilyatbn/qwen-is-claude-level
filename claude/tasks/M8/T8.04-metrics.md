## Deliverable

**Metrics** — plain text at `GET /metrics` (not Prometheus format in v1):
```
uptime_s 1834
rooms 1
players 4
tick_p50_ms 1.2
tick_p99_ms 4.8
tick_overruns 3
snapshot_bytes_per_s 1940
commands_per_tick_avg 5.2
inputs_dropped 0
```

**`DEBUG_DUMP=1`** — at round start, write to `debug/<seed>/`:
- `map.png` (terrain, with spawn points and buried slots marked),
- `meta.json` (the full `MapMeta`),
- `surface.png` (surface points, with the largest traversable component highlighted).

**The log audit** — walk `docs/61-logging-debug.md` §3's table and verify each
diagnostic log line actually exists. Add any that are missing:

| Symptom | Required line |
|---|---|
| unplayable map | `game::map` generation summary: `attempts`, `traversable_fraction`, `used_safe_preset` |
| spawned inside rock | `game::player` respawn: chosen point, re-check result, fallback used |
| laggy | `game::sim` tick overruns; `game::net` snapshot cadence |
| shot through a wall | `mask_checksum` mismatch on `game::net`; carve `seq` gaps |
| item vanished | `game::items` despawn: TTL vs eviction |
| rocket did nothing | `game::weapons` fire rejection reason |
| weather never fired | `game::effects` next roll time and chosen kind |

## Notes

The audit is the substance of this task. Those seven lines exist so that a user's
vague report maps onto something concrete, which is the brief's explicit requirement
that logs be good enough for an AI agent to diagnose problems from a description.
They are each a deliberate call, not a by-product of verbosity — check every one and
say in your report which were missing.

Tick timing percentiles need a small histogram or a ring buffer of recent samples.
A 1024-entry ring is plenty and costs nothing.

`surface.png` is the direct visual answer to "why did validation reject this map?".
It is the most useful of the three dumps and the easiest to forget.

`DEBUG_DUMP` runs during `Warmup`, before the round starts, so it never costs tick
time. It is off by default because it costs disk and a few hundred ms.

Also verify the negative discipline from `docs/61-logging-debug.md` §2: **no
`info`-level line is emitted per tick or per input**, and there is no logging inside
the per-pixel loops of map generation or carving. Add the test below.

`/metrics` is unauthenticated and exposes no player data. Note that in a comment —
if authentication is ever needed, this is the file.

## Tests

`crates/game-server/tests/metrics.rs`:

- `GET /metrics` returns 200 with every documented key.
- `tick_p50_ms` and `tick_p99_ms` are plausible after 600 ticks.
- `tick_overruns` increments when a tick exceeds its budget (force one with a sleep).
- `snapshot_bytes_per_s` matches the expected rate for the connected client count.
- `inputs_dropped` increments when `MAX_INPUT_QUEUE` is exceeded.
- `GET /healthz` includes `rooms` and `players`.
- `DEBUG_DUMP=1` writes all three files and they are valid.
- `DEBUG_DUMP=0` writes nothing.
- `DEBUG_DUMP` does not increase mean tick time (measure across 600 ticks).
- **Log audit**: with a captured subscriber, each of the seven required lines is
  emitted under its condition.
- **No `info` line is emitted per tick** across a 600-tick run.
- Every room log line carries `room` and `tick`.
