## Deliverable

```rust
pub struct ReplayWriter { file: BufWriter<File>, commands: u64 }

impl ReplayWriter {
    pub fn create(dir: &Path, seed: u64, scale: MapScale, config: &Config)
        -> io::Result<Self>;
    pub fn record(&mut self, tick: u32, cmd: &Command) -> io::Result<()>;
    pub fn finish(self, world: &World, scores: &[(PlayerId, i16)]) -> io::Result<()>;
}
```

File format (`docs/61-logging-debug.md` §4):
```
header: magic, version, seed, scale, sim_hz, round_seconds, player list
body:   repeated { tick: u32, command: Command }
footer: final world state hash, final scores
```

Enabled by `RECORD_REPLAY=1`; writes to `replays/<timestamp>-<seed>.replay`.

## Notes

**This works only because the room task is single-threaded with a fixed command
order** (`docs/41-server-loop-rooms.md` §1–§2). A round is fully determined by its
seed plus the ordered command list, so recording those reproduces it exactly. If a
future change introduces any other source of nondeterminism, this file is where it
will show up — as a footer hash mismatch — which is precisely why the footer exists.

Record commands **as accepted by the room**, after sequence filtering (T6.06), not
as received off the socket. Replaying rejected inputs would apply input the live
round never saw.

Do not record snapshots or outbound events. They are derived, and including them
would multiply the file size for no diagnostic value.

Serialise with `serde` + `bincode`, or hand-roll — either is fine, but the format
must be **versioned**, and a version mismatch must be a clear error rather than a
misparse.

`finish` must run on graceful shutdown too (`docs/41-server-loop-rooms.md` §7), or
a round interrupted by `docker compose down` produces a truncated file — exactly the
round you most want to inspect.

Buffer writes; do not flush per command. Flush on `finish` and on phase transitions.

Timestamps come from the caller, not from `Date::now` inside the recorder — the
replay runner has no clock (`docs/61-logging-debug.md` §4).

A 4-minute 6-player round should be a few hundred KB. If it is megabytes, something
is being recorded that should not be.

## Tests

`crates/game-server/tests/replay.rs`:

- `create` writes a valid header with the right seed and scale.
- `record` appends commands and the file grows.
- `finish` writes the footer with the world hash and scores.
- A round with no commands produces a valid, minimal file.
- The file round-trips through the reader (T8.02 writes it; stub a minimal reader
  here).
- A version mismatch is a clear error, not a misparse.
- **A 4-minute 6-player round produces a file under 1 MB** — assert the bound, since
  a bloated replay usually means something derived is being recorded.
- Graceful shutdown mid-round still produces a readable file with a footer.
- `RECORD_REPLAY=0` writes nothing and creates no file.
- The replay directory is created if it does not exist.
- Recording adds under 0.1 ms to a tick (measure over 1000 ticks).
