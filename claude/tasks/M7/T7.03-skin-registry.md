## Deliverable

**`assets/skins.json`** — the schema from `docs/50-sprites-skins.md` §2, with **five
player skins** (the Kenney character pack's colour variants) and one weapon skin per
v1 weapon.

**`client/src/render/skins.ts`:**
```ts
export interface PlayerSkin { id: number; name: string; atlas: string;
  prefix: string; frames: Record<AnimState, string[]>;
  anchor: {x: number; y: number}; tint: number | null }

export interface WeaponSkin { id: number; weaponKey: string; atlas: string;
  frame: string; muzzle: {x: number; y: number}; pivot: {x: number; y: number} }

export class SkinRegistry {
  static async load(url: string): Promise<SkinRegistry>;
  playerSkin(id: number): PlayerSkin;        // falls back to skin 0
  weaponSkin(weaponKey: string): WeaponSkin;
  frameKey(skin: PlayerSkin, state: AnimState, index: number): string;
  validate(textures: Phaser.Textures.TextureManager): string[];  // missing keys
}
```

## Notes

Resolution is `atlas` + `prefix` + frame name. That is what makes five colour
variants of the same rig cost five registry entries and zero new art — the Kenney
pack is organised exactly this way (`character_green_*`, `character_purple_*`, …).

**The `u16 skin_id` on the wire is the only thing the server knows**
(`docs/50-sprites-skins.md` §1). It does not validate it, does not know what skins
exist, and never sends texture names. Adding a skin is a client asset change with no
server deploy — preserve that property.

Weapon skins are **not** on the wire. Everyone sees the default weapon skin on other
players; your own is personal. Do not add a weapon skin id to the protocol.

**Every lookup falls back** (`docs/50-sprites-skins.md` §8): unknown skin id → skin
0; missing frame → the magenta placeholder, logged **once per key**. This is what
kept M3–M6 runnable before any art existed, and it must survive.

`validate()` is called once after loading and logs every missing key in one batch.
One clear list at boot beats fifty scattered warnings during play.

`anchor.y` is per-skin because different art has different proportions relative to
the 16×28 hitbox. Replace `playerView.ts`'s hard-coded 0.9 with the registry value.

## Tests

`client/src/render/skins.test.ts`:

- `skins.json` parses and validates against the schema.
- Every player skin `id` is unique; every weapon `weaponKey` is unique.
- Every referenced atlas key appears in `manifest.json`.
- **Every frame key referenced by every skin exists in that atlas's JSON.** This is
  the cross-file check that catches a typo before it becomes a magenta box in game.
- `playerSkin(999)` returns skin 0 without throwing.
- `weaponSkin("nonexistent")` returns a default without throwing.
- `frameKey` composes `prefix` + frame correctly.
- A missing frame logs exactly once even when requested fifty times.
- `validate()` returns the complete list of missing keys, not just the first.
- With `assets/atlas/` emptied, the registry still loads and every fallback fires.
- Every v1 weapon (`bazooka`, `grenade`, `smg`) has a weapon skin.
- All five player skins have every `AnimState` populated.

## Done when

```sh
npm --prefix client test -- --run skins
```
Then in game, switch `skin_id` and confirm the character changes for all players.
