## Deliverable

```ts
/** Reusable scratch buffers. Allocated once, never per bake. */
export class BakeScratch {
  constructor();
  readonly stencilCanvas: HTMLCanvasElement;   // CHUNK_SIZE square
  readonly imageData: ImageData;
}

/** Write the chunk's mask slice into the scratch stencil: solid = opaque white. */
export function buildStencil(core: Core, chunkX: number, chunkY: number,
                             scratch: BakeScratch): void;

/** Bake one chunk into its CanvasTexture: tiled fill, punched to the mask shape. */
export function bakeChunk(
  texture: Phaser.Textures.CanvasTexture,
  fillImage: CanvasImageSource,
  chunkX: number, chunkY: number,
  core: Core, scratch: BakeScratch,
): void;
```

Steps, exactly as the doc's §2:
1. `buildStencil` — per-pixel loop over the chunk's mask slice into `ImageData`,
   then `putImageData` into the scratch canvas.
2. Clear the chunk canvas; `drawImage` the tiling fill texture, offset by the
   chunk's world position **modulo** the texture size, tiled to cover 256×256.
3. `globalCompositeOperation = 'destination-in'`; draw the stencil.
4. Reset the composite mode and `texture.refresh()`.

## Notes

**The modulo offset in step 2 is what makes the fill continuous across chunk
seams.** Drawing the texture from (0,0) in every chunk produces a visible grid of
repeated tiles, which is the most obvious possible rendering artefact and is easy to
avoid here and painful to retrofit.

**Allocate nothing per bake.** `BakeScratch` holds the canvas and the `ImageData`;
reuse them. Allocating a 256×256 `ImageData` per bake, at four chunks a frame, is
1 MB of garbage per frame.

`buildStencil` is the only per-pixel loop in the renderer (~65k iterations). Read
through `core.maskView()` directly — do not call `core.solidAt` per pixel across a
property accessor, and do not call into WASM per pixel. Compute the byte and bit
index inline.

Write `ImageData` through a `Uint32Array` view (one 32-bit write per pixel:
`0xFFFFFFFF` or `0x00000000`) rather than four `Uint8ClampedArray` writes. It is
several times faster and the code is shorter.

**Never call `getImageData` during a bake.** It forces a GPU readback and will
dominate the frame time. All mask data comes from WASM.

`fillImage` is supplied by the caller (the theme's `fill.png`, or the procedural
fallback from T7.05). This function does not know about themes.

## Tests

`client/src/render/chunkBake.test.ts`, with a stub canvas — test the pure parts:

- The stencil bit-index maths: for a known small mask, `buildStencil` produces
  opaque pixels exactly where the mask is solid. Extract the index computation into
  a testable helper if the canvas stands in the way.
- A fully solid chunk produces a fully opaque stencil.
- A fully empty chunk produces a fully transparent stencil.
- The tile offset for chunk (3, 2) with a 256-px texture is (0, 0); with a 100-px
  texture it is `(768 % 100, 512 % 100)` = (68, 12).
- `BakeScratch` allocates its canvas once — construct it, bake twice, and assert the
  canvas identity is unchanged.
- Chunk index → world position: chunk (3, 2) is at world (768, 512).

Visual verification happens in T3.07's sandbox. Note in your report that the pixel
output itself is not unit tested, by design (`docs/60-testing.md` §7).
