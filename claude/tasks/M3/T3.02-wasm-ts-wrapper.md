## Deliverable

```ts
export interface MapMeta { /* mirrors the Rust MapMeta, from meta_json() */ }
export const enum MapScale { Small = 0, Medium = 1, Large = 2 }

export class Core {
  static async init(): Promise<Core>;          // loads and instantiates the wasm

  generate(seed: bigint, scale: MapScale): void;
  loadMask(w: number, h: number, rle: Uint8Array): boolean;

  get width(): number;
  get height(): number;
  get meta(): MapMeta;                          // parsed once per generate/load, cached

  /** A live view over WASM memory. Re-acquired automatically after growth. */
  maskView(): Uint8Array;
  solidAt(x: number, y: number): boolean;       // reads the view directly

  carve(cx: number, cy: number, r: number): void;
  takeDirtyChunks(): Uint32Array;

  addPlayer(id: number, x: number, y: number): void;
  applyInput(id: number, seq: number, buttons: number, aim: number, dt: number): void;
  setPlayerState(id: number, s: PlayerState): void;
  playerState(id: number): PlayerState;

  maskHash(): Uint8Array;
}
```

"predev":   "wasm-pack build crates/game-wasm --target web --out-dir ../../client/src/core/pkg",
"prebuild": "wasm-pack build crates/game-wasm --target web --out-dir ../../client/src/core/pkg --release"

## Notes

**The memory-growth trap.** A `Uint8Array` view over WASM memory is detached
whenever the WASM heap grows. Reading a detached view throws, or worse, silently
returns zeros. `maskView()` must check `this.view.buffer !== memory.buffer` (or
`view.byteLength === 0`) and re-acquire if so. Do this inside the accessor so no
caller has to remember. This is the single most likely bug in this task.

`solidAt` reads the view directly rather than crossing the boundary per pixel — a
per-pixel WASM call for a 65k-pixel chunk bake would be unusably slow.

Bit order must match `Mask`'s layout exactly: `bit = y * w + x`, byte `bit >> 3`,
`(byte >> (bit & 7)) & 1`. Note this is **byte**-granular on the JS side while the
Rust side is `u64`-granular; on little-endian (every platform that runs a browser)
these agree. State that in a comment — it is the kind of assumption that is
invisible until it is wrong.

If `wasm-pack` is missing, the hook must fail with an install instruction. The
default failure is a module-not-found error from Vite much later, which is
needlessly confusing.

## Tests

`client/src/core/index.test.ts` (vitest, real WASM in node):

- `Core.init()` resolves.
- `generate` then `width`/`height` match the scale.
- `meta` parses and has non-empty `spawn_points` and `surface_points`.
- `solidAt` agrees with a known pattern: generate, carve a radius-40 hole at a known
  solid point, and assert the centre is now air and a point 50 px away is unchanged.
- `takeDirtyChunks` is non-empty after a carve and empty on the second call.
- **Memory-growth safety**: hold a `maskView()`, call `generate` again (which
  reallocates), then read through `solidAt` — it must return correct values, not
  throw and not return zeros. This is the test that pins the trap above.
- `loadMask` with bytes from a generated map produces a matching `maskHash`.
- `loadMask` with random bytes returns false.
- `playerState` round-trips through `setPlayerState`.
