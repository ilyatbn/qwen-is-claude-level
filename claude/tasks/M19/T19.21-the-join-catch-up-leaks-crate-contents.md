# T19.21 — The join catch-up tells a late joiner what every crate holds (v7)

Milestone: M19 · Depends on: nothing · Size: small, but read the question first

**Found by T19.17's review**, verified rather than reasoned.

> **PREMISE CHECKED, AND THE BOOKING STANDS — it is live. 2026-09-06.**
>
> This was briefly "corrected" to *latent, not live* on the strength of the catch-up block's
> own comment, which says that since §E4 a seating socket can only seat into a lobby, so
> `inspect` answers `None` and all three blocks are unreachable in production. **That
> correction was wrong and has been withdrawn.** The comment is an intention; the code
> samples the fact it rests on at a different time than it uses it.
>
> **The mechanism, verified at the symbols.** `session.rs::seat` reads the guard
> `if room.has_started()` and returns `join_error: in_progress`. That read is a bare
> `AtomicBool` load — `room.rs::has_started` is `self.started.load(Relaxed)` — taken **outside
> the room task**. Between it and the catch-up there are **two command round-trips**:
> `room.join(...).await` and `room.join_info().await`, each a `oneshot` through the room
> task's channel. Only then does `inspect` run.
>
> The room task is a `tokio::select!` loop whose ticker arm drains queued commands with
> `try_recv` and then ticks — **and calls `room.install_world(world)` in that same arm**
> (`room.rs`, the `generated_this_tick` path). So a world can be installed between the guard
> and the `inspect`, at any of the ticks that fall in that window. This is the loop's ordinary
> operation, not a race needing bad luck: interleaving commands with ticks is what it is for.
>
> When it happens, all three catch-up blocks take the `Some` arm and the joiner receives
> `map_init`, every `item_spawn` **with `item_id`**, and the graveyard. On a public lobby
> `LOBBY_BOT_TIMEOUT` guarantees the window is entered eventually.
>
> **`has_started()` is not "has a world".** They are separate fields, and the three writes to
> `self.world` are individually careful — `install_world` sets the bit *before* the world,
> `return_to_lobby` clears the world *before* the bit (both over-refuse, the safe direction),
> and `restart` sets world before bit but runs to completion inside the room task. The bug is
> not in any of those orderings. It is that `seat` samples the bit once, outside, and acts on
> it three round-trips later.
>
> **The structural fix, preferred over widening the guard:** re-check `has_started()` *inside*
> the same room-task access that performs the `inspect`, so the check and the read are one
> operation. Widening or moving the outer guard cannot work — any guard outside the task has
> the same window.
>
> Citations rotted too: the catch-up is at `session.rs`'s `"item_spawn"` emit, ~30 lines below
> the `:1284-1286` cited below, in a file now 1675 lines. Grep
> `grep -n '"item_spawn"' crates/game-server/src/session.rs`, not the line.
>
> The design question below is untouched by all of this and still has to be answered first.
>
> **THE WINDOW IS THE MAP GENERATOR, NOT A GAP BETWEEN TICKS.** Found on review of the
> withdrawal. The ticker arm does not go drain-then-install: between them sits
> `tokio::task::spawn_blocking(blueprint).await` — the map generation — and the room task
> yields there for the whole of it. The comment beside that call states the duration itself:
> **"the generator is 0.3–1.1 s and this loop has 16.7 ms."** So the exposure is not a
> sub-frame gap. It is *every `seat` that passes the guard while a world is being generated*,
> and generation is the slowest thing a room ever does. Expected frequency is not
> "occasionally" — it is **every lobby start with a join in flight**, and a public lobby
> reaching `LOBBY_BOT_TIMEOUT` opens the window on the tick it fires.
>
> **`Command::Join` does not re-guard, and it does more than let the catch-up through.** The
> handler allocates a seat and then `if let Some(world) = self.world.as_mut() {
> world.add_player(id, skin_id, name) }`, with its own comment saying *"A player who joins a
> running match is still added immediately, below."* So a socket that passes the outer guard
> during generation is not merely told what the crates hold — **it is seated into the running
> match**. The crate leak is the part this task books; note the larger behaviour rather than
> fixing it here, and say so if it turns out to be intended.
>
> **A SIBLING COMMENT MAKES THE SAME OVER-CLAIM AND MUST BE CORRECTED IN THIS CHANGE.**
> Directly above the `install_world` call:
>
> > *"Sets the §E2/§E4 bit itself, before the map goes out, so no socket can be seated into a
> > match that is already handing out its map."*
>
> True for a socket whose guard-read lands *after* `install_world`; false for one already past
> it. It is the identical shape as the comment that produced the withdrawn correction, one
> file over — and it is the comment a builder meets **while implementing this fix**, so it is
> the single thing most likely to convince them the remedy is unnecessary. Correct it, and say
> which sockets the ordering does and does not protect.
>
> Grep, do not trust the line numbers in this box either: `grep -n "install_world(world)"` and
> `grep -n "spawn_blocking(blueprint)"` in `crates/game-server/src/room.rs`.

## Read first
- `docs/40` §3 — the event table, specifically `:184` and `:187`
- `crates/game-server/src/session.rs:1284-1286` — the catch-up
- `crates/game-core/src/items/world.rs:759,767` — how a crate is spawned
- `crates/game-server/src/events.rs:7` — the visibility table

## What was found

`docs/40` pins **two** shapes: `item_spawn` `{tick, world_item_id, item_id, count, x, y,
source}` at `:184`, and `crate_spawn` `{tick, world_item_id, x, y}` at `:187`. A crate's
contents are withheld **structurally** — the fields are simply not in the payload.

That is a design decision rather than an omission. The spec annotates access control
explicitly where it means it (`inventory` is *"to the owner only"*, `damage` *"to the victim
and the attacker only"*), and `events.rs:7`'s own visibility table puts both `item_*` and
`crate_spawn` in the **Everyone** row — so nothing is access-controlled here and the only
thing hiding crate contents is the shape of the event.

**The catch-up ignores that.** `items/world.rs:759,767` spawns a crate as an ordinary world
item carrying its real contents (`w.spawn(MEDKIT, 1, …, SpawnSource::Crate, …)`), and
`session.rs:1284-1286` maps **every** world item to `item_spawn`, `item_id` included, with
**no source filter**. So a late joiner is told what each unopened crate holds.

**Why it is a bug:** watch a crate land and its contents are hidden from you; join after it
landed and you are told. Two players in one match, different information.

## The question to settle BEFORE fixing

**Does `SpawnSource::Crate` mean "this is an unopened crate" or "this item came out of a
crate"?** The client uses `source: 'Crate'` for **both** — the mirror sets it from
`crate_spawn`, and `worldMirror.test.ts` also feeds an `item_spawn` carrying
`source: 'Crate'`. If one value is doing both jobs that is the *"a field that means two
things"* shape, and it is plausibly the root of this confusion rather than a detail of it.
**The fix depends on the answer**, so grep it first and say which it is.

## Deliverable

- The catch-up announces an unopened crate with **`crate_spawn`**, not `item_spawn`.
- If `SpawnSource::Crate` is overloaded, split it, and say so — do not filter on a value
  that means two things.

## Tests

- A late joiner receives `crate_spawn` for an unopened crate and **no `item_id` for it**,
  with a control: an item that is genuinely on the ground still arrives as `item_spawn`
  **with** its id, so "the joiner learns nothing" cannot pass for a catch-up that stopped
  sending items.
- Two clients, one joining after a crate lands: assert both hold the **same** knowledge of
  that crate. Counting at both ends is the point.

## Note for the coordinator

**`docs/40` contains no catch-up rule at all** — grepped for catch-up, "on join", re-send,
late joiner, snapshot-of-items: **zero hits**. So this is not a contradiction in the spec;
it is **one clause and a silence**, and a builder filled the silence with the wrong event.
A sentence in `docs/40` saying a late joiner receives `crate_spawn` for unopened crates
would stop it recurring. **That amendment is the coordinator's to write, not a builder's.**
