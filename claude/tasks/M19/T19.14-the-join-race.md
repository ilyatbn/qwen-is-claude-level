## Deliverable

Two-client checks fail intermittently at **both** the pre-bullet commit and HEAD, in the
same mode, with nothing to do with any M19 change:

- **`in battle (phase warmup, 0 players)`** — the client reads the roster while it is
  still empty. A join that has not arrived is being read as a join that returned nothing.
- **`vite did not report a port within 90 s`** under sustained browser load.

Find the actual cause of the first one and fix it. It is a **race, not a slow path**, so
the repair is a wait on the condition — a roster that has the players in it — and not a
larger number. `CLAUDE.md`: a wait hardcoded against a tunable is a test that expires.

The second may be the box rather than the code. Measure it before deciding: if vite is
genuinely slower under load, the check needs to stop competing with the suite, not get a
longer deadline.

## Amended after implementation (`ca3c8de`) — what this file got wrong

Recorded rather than silently worked around, per `CLAUDE.md`: reporting a spec defect is a
valued outcome, and the next reader of this file should not repeat the reasoning.

- **"A join that has not arrived is being read as a join that returned nothing" is wrong.**
  There is no join race. `worldMirror` fills `players` from the **snapshot**, which is the
  full roster including self (`docs/40` §3) and not a delta, so an empty roster means *no
  snapshot has been applied yet*. The reported `in battle (phase warmup, 0 players)` was a
  **stale variable in the harness**: `enterBattle` never reassigned `d` after the
  simulating-wait. Measured over ten runs before any change: the stale value was 0 in eight
  of them, the fresh value was 2 in **ten of ten**, and **every run passed**.
- **"The repair is a wait on the condition — a roster that has the players in it"** is right
  in shape and dangerous as written. `enterBattle` has 24 call sites and only six are
  multi-client; implementing it as *wait for two players* hangs the other eighteen the day
  it lands. The wait defaults to `expectPlayers: 1`, which every client satisfies by its own
  presence, and the multi-client sites opt in.
- **"Whatever you key the wait to is asserted against the constant that governs it, not a
  literal" cannot be satisfied.** No constant governs a network round-trip plus a mask
  decode. Read literally this requirement fabricates a tunable nobody chose — the same trap
  T19.04 correctly refused when it keyed `standStill` to the effect instead of inventing a
  "stopped" constant. The wait is keyed to the observable effect and bounded by the caller's
  existing `timeoutMs`.
- **The Done-when cannot reproduce the second deliverable.** `for i in $(seq 1 10); do node
  scripts/e2e.mjs two-clients; done` runs one check at a time, which is the idle-box case,
  while the vite failure is specified as happening *under sustained browser load*. That half
  was not reproduced and not measured, and is booked as **T19.16** rather than left as an
  unfinished half of a ticked task.
