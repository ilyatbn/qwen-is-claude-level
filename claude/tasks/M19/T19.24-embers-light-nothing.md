# T19.24 — `Weather.lights()` has no caller, so embers light nothing (v7)

Milestone: M19 · Depends on: nothing · Size: small, but read T19.20 first

**Found during T19.20's investigation, verified independently.** The thirteenth instance of the
shape `CLAUDE.md` opens its code rules with: built, unit-tested, and wired to nothing.

## What was found

`client/src/render/weather.ts::lights()` returns
`Array<{ x, y, r, a }>` and its doc comment states the intent: *"Feed the lightmap: fire is a
light source at night (§A3)."*

**Nothing calls it.** Counted, not glanced:

```
grep -rn "weather\.lights\|\.weather\.lights" client/src scripts   →  0
```

The 22 `.lights()` call sites in the client are all `OrdnanceState` or `OrdnanceFxState`
(`GameScene.ts:1776` and `:1783`, `ordnanceFx.ts`, `ordnance.ts`, `SandboxScene.ts:1220`, and
their tests). `GameScene` reads `weather.fogAlpha`, `weather.rainDrops`, `weather.toxicIntensity`
— never `weather.lights()`.

**So ground fire and embers are dark at night**, while the same frame lights rockets and
grenades through the ordnance path.

## Why it is separate from T19.20

T19.20 is blocked on a **design ruling** — whether a permanently-on flashlight cone is wanted,
since T20.07 removed the toggle. **This one needs no ruling.** `docs/14` §A3 already says fire
is a light source at night, and nothing in `docs/70`–`75` amends it. It is wiring an agreed
behaviour to the renderer that should have been calling it.

Do not fold the two together: one is waiting on a person and the other is not.

## SCOPE SETTLED 2026-09-08 — option 2, and option 1 is unbuildable

**Option 1 was tried and refused before it was written.** There is no lava hazard on the
client to hang a light on: `HazardKind` is `'toxic' | 'smoke' | 'other'`, `hazardKind()` maps
anything unrecognised to `'other'`, and the server emits **no** lava `HazardSpawn` at all — the
only two `HazardSpawn` sites in `world/mod.rs` are burn zones and smoke, and every `lava` hit
in `game-server/src` is `WEATHER=` env parsing. So `if (h.kind === 'lava')` would have been
dead on arrival: **the third no-op remedy this task has attracted**, and refused rather than
shipped.

## The defect, stated properly

Lava reaches a networked client only as terrain carves, and — during the **burn** phase — as
smoulder flames, which are ordnance projectiles and *are* lit. But `smoulder()` deliberately
emits nothing during the **jet** window, and **the jet is the only phase that deals damage**
(`LAVA_JET_DPS`).

> **At night a networked player is damaged by a lava jet that emits no light and draws no
> vent, no mouth and no ember.** The sandbox renders all of it. Nobody plays in the sandbox.

## The missing piece, already identified

The server derives its vents from the effect seed — `LavaBurst::new(seed, &self.map, now)` —
and puts **that same seed on `effect_start`**, so it is already on the wire. The client has
the map and the wasm core and no way in: `weather_step` returns empty unless a local scheduler
exists, and `force_effect` seeds one from `map.meta.seed` rather than from a server-supplied
effect seed.

**So the deliverable is a wasm entry point taking `(kind, seed, now)`** that seeds the client's
scheduler from the server's effect seed. That the seed is already broadcast is good evidence
this was the original intent and only the client half is missing.

**Determinism is the whole game here**: the client must derive the *same* vents the server did,
from the same seed, or it will draw fire where there is none and miss fire that is burning.
Assert that both sides agree on vent positions for a fixed seed — a cross-check, not a
screenshot, is what proves that half.
