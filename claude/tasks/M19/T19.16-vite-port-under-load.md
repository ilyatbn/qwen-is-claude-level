# T19.16 — `vite did not report a port within 90 s` under sustained load (v7)

Milestone: M19 · Depends on: nothing · Size: ~100 lines, most of it measurement

**Booked out of T19.14.** That task carried two unrelated deliverables; the first — the
"join race" — turned out not to exist (the roster log was reading a stale variable, fixed
in `ca3c8de`). This is the second, and it was **not reproduced and not measured**, so it is
split out rather than left as a silently unfinished half of a ticked task.

## Deliverable

`vite did not report a port within 90 s`, observed under sustained browser load. Decide
which of these it is, **with a measurement**, and act on the answer:

- vite is genuinely slower to bind under load → the check must stop competing with the
  suite, **not** get a longer deadline;
- or the box was saturated by something that should not have been running → the finding is
  about the machine, not the code.

## Notes

- **The 90 s deadline must not be raised to make this pass.** `CLAUDE.md`: a wait hardcoded
  against a tunable is a test that expires, and a gate that fails on a coin flip gates
  nothing. Raising it converts a fast failure into a slow one.
- **A serial loop cannot reproduce this and must not be used as the gate.** T19.14's
  Done-when was `for i in $(seq 1 10); do node scripts/e2e.mjs two-clients; done` — one
  check at a time, which is the *idle-box* case. This defect was predicted in the forward
  sweep before T19.14 was implemented and is the reason this task exists separately.
  Whatever proof this task ends with must put the box under **concurrent** load.
- Two load models are already available and they are not equivalent — see the T19.15
  journal entry, where 8 CPU spinners moved `hud-timer` in the *opposite* direction from
  the real browser suite. Prefer the real suite as the load, or justify the synthetic one.
- **Check the box is idle before measuring and for leaks after.** A leaked load generator
  ran for 3 h 47 m during M19 and saturated the machine while an agent asserted it was
  quiet; `scratchpad/loadgen.sh` is the design that does not leak.
- Related and possibly the same family: `bullets-visible` is journalled as a load-flake
  suspect, and `hud-timer` fails ~1 in 20 **on an idle box** with the cause unfound.

## Tests

- The failure is **reproduced at least once under a named, measured load model** before any
  fix is written. If it cannot be reproduced, say so plainly and close the task on that —
  an unreproducible failure that nobody can trigger is a finding, not a fix.
- Whatever changes, the proof runs the check under concurrent load, not serially.
