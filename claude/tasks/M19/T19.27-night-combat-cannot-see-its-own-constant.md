# T19.27 — `night-combat`'s flashlight assertion is blind to its own constant (v7)

Milestone: M19 · Depends on: nothing · Size: small

**Found during T19.22, in a falsification that did not fail.** The builder set
`FLASHLIGHT_FOV_MULT = 1.0` — neutralising the flashlight entirely — and the check **passed**,
reporting `110.0 -> 110.0`.

## Why it cannot fail

The assertion is, in effect:

```js
want = nightOff * k.FLASHLIGHT_FOV_MULT
```

Both sides read the same constant. Set it to 1.0 and `want` becomes `nightOff`, which is
exactly what the unlit radius already is — so the check agrees with itself and reports success
while the feature is switched off.

**This is `docs/76` §G6 live in a gate check**: pinning every assertion to the constant makes
the suite immune to the *implementation* drifting, and blind to the *constant's value*
changing. `ITEM_SPAWN_INTERVAL` 14 → 42 passing all 1296 gate tests is the same shape; this is
the first instance found inside a browser check rather than a unit test.

**Pinning is still right and `CLAUDE.md` still forbids hardcoding 1.5 here.** The fix is not to
stop pinning — it is that a tunable whose *value* is the feature needs one assertion of a
different kind beside the pinned one.

## Deliverable

Give the flashlight's effect a claim that survives its own multiplier being neutralised.
Options, none pre-chosen, but **say which and why**:

- **A structural claim**: with a flashlight the night radius must be **strictly greater** than
  without one. That is the sentence the feature actually promises, it needs no number, and it
  reds the moment the multiplier reaches 1.0.
- **A basis pin** in the style of `capacity.rs::max_rooms_carries_its_basis`: assert the
  constant against the claim its own doc comment makes, so changing the number without
  re-measuring shows up in the diff.

The first is cheaper and catches the case that was missed. The second catches a *retune*, which
nothing in the repository currently catches for any constant.

## Watch for

- **Keep the pinned assertion too.** It catches the implementation drifting away from the
  constant, which is a different failure and a real one. Two assertions, two jobs — *derive, do
  not add a fourth flag* applies to logic, not to coverage.
- The same blindness will exist wherever a check computes its expectation from the constant it
  is testing. **Sweep the browser checks for that shape while you are here** and report what
  you find rather than fixing them all in this task.

## Tests

- **Falsify by neutralising the constant, not by breaking the code**: set
  `FLASHLIGHT_FOV_MULT = 1.0` and the check must go red. That is the exact case that passed.
- The existing radius assertion still reds when the *implementation* is broken — the T19.22
  falsification (`110.0 -> 110.0, not 165.0`) must still fire.
