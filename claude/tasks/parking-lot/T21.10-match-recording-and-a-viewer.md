# T21.10 — Match recording, and something to watch it with (v9)

Milestone: M21 · Depends on: nothing hard · Size: **large — split it, see below**

**Asked for by the coordinator**, for three reasons in their words: *"1. For you to be able to
learn how real players play to enhance the bots later. 2. Bug and issue reproductions. 3. A
replay feature where you can just watch a game, and each player."*

## Read this before designing anything: most of it already exists

**Do not start from scratch.** The recording engine is built, deterministic and in use. What is
missing is smaller and different from what the brief implies.

| piece | state today |
|---|---|
| a recorded format | **exists** — `replay.rs`, versioned (`REPLAY_VERSION`), 21 command types |
| what it captures | **exists** — `Join Ready Unready SetScale SetBots SetStartKit SetRoundSeconds Input UseItem SelectSlot Fire VoteRestart Leave Checkpoint DropUnready UseHeal UseBatteryPack QuickThrow MoveItem DropItem StartWithBots` |
| deterministic re-simulation | **exists** — `src/bin/replay.rs`, headless, no clock |
| divergence detection | **exists** — a state hash every `CHECKPOINT_STRIDE` (600 ticks), and the binary reports **the tick where two runs first diverge** rather than "mismatch" |
| recording in production | **off** — `record_replay` defaults to `false`, `RECORD_REPLAY` turns it on |
| **a way to watch one** | **missing entirely** |

So **reason 2 is already served** and reason 1 largely is: a recorded round replays exactly, and
the binary's own header describes the workflow — *"the map broke around two minutes in" →
replay to tick 7200, dump the PNG, look at it.* **Reason 3 is the real work.**

## The three pieces, and they are separate tasks

### A. Turn recording on, and decide what that costs

`record_replay` is `false` by default. Turning it on for real matches is a *policy* change with
consequences nobody has measured:

- **Size and retention.** Measure bytes per round at the shipping configuration before choosing
  anything. A checkpoint is ~800 bytes and there is one every 10 s; inputs dominate and scale
  with players. **Report the number; do not estimate it.**
- **Where files go, and who deletes them.** A server that fills its disk is a worse outage than
  no replays.
- **Privacy.** A recording contains player names. Say what is retained and for how long.
- **Cost on the tick.** Recording happens on the room's thread. Measure it against the 16.7 ms
  budget — `metrics.rs` already reports `tick_p99_ms`.

### B. The viewer — this is reason 3 and the only genuinely new thing

Re-simulate a replay and **render it**, rather than dumping a PNG. The client already has
everything needed to draw a world; what it has never had is a world that came from a file
instead of a socket.

- **Follow any player, switch between them, free camera.** The brief asks for "each player".
- Scrub, pause, step. A bug repro is worth little if you cannot stop on the frame.
- **The renderer must not be forked.** A second draw path that diverges from the game's is how
  you get a viewer that shows something the players never saw. `SandboxScene` versus
  `GameScene` is the existing precedent for how easily two paths drift — check what it cost.

### C. The bot-training export — reason 1, and the one to define last

Do not design this until A has produced real files. What a training pipeline wants from a
recording is a question about the pipeline, and there is no pipeline yet. **Booking it is
correct; specifying it now is not.**

## Watch for

- **`REPLAY_VERSION` is a compatibility record.** It bumps when an old recording would load, run
  and **silently disagree** — not for a new command tag, which leaves old files replaying byte
  for byte. If recordings are kept across releases, that guarantee becomes load-bearing in a way
  it has never been: today's files live for one debugging session.
- **A replay is only as deterministic as the sim.** Every constant retune is a break — two
  landed in one day recently. If recordings are retained, decide whether old ones are migrated,
  re-simulated once and frozen as video, or simply expire.
- **`docs/40` has no catch-up rule and `docs/41`'s replay section is thin.** Whatever lands here
  wants an amendment.

## Tests

- A recorded real match re-simulates to an identical state hash at every checkpoint. That is the
  existing guarantee; assert it against a **multi-player** recording, since the fixtures today
  are one human plus bots and bots emit no commands.
- The viewer renders a frame that matches what the recording says the world looked like —
  **assert on rendered pixels** (`docs/72` §C2) with a control region and a control frame, not
  on scene state. Four "I cannot see it" bugs shipped here past a green suite for exactly that.
- Switching the followed player changes the camera **and** the frame; a control that it does not
  change the simulation.

## Done when

Split this before starting. **A** is a measurement and a policy decision. **B** is the feature.
**C** waits for A. A single task covering all three would be several files and well past 250
lines, which `CLAUDE.md` says to split rather than discover at 800.
