# T20.03 — Host promotion works and nobody is told (v8)

Milestone: M20 · Depends on: T20.01 shares one of its causes · Size: ~100 lines

**No doc section governs this.** Reported: *"if the host leaves the waiting room, the next
active player should be promoted to host. If no other players are there, close the lobby."*

## Read first
- `crates/game-server/src/room.rs:1170-1176` — `settings_owner`, and its doc comment
- `crates/game-server/tests/lobby_state.rs:258-272`, `tests/private_lobby.rs:304-345`
- `client/src/net/lobby.ts:282-294` — `RosterRow`
- `crates/game-server/src/registry.rs:347-372,434-453` — `empty_since`, `reap`

## What already works — do not rebuild it

**Promotion is already correct on both departure paths that exist.** `settings_owner()` is
derived per call — its doc comment says *"when the host leaves the answer moves on its
own"* — and both `leave_room` (`session.rs:481-499`) and disconnect (`session.rs:947-965`)
free the seat and rebroadcast via `Command::Leave` → `note_lobby_change()`.

Two tests already pin it: `the_owner_moves_on_when_the_host_leaves` and
`the_settings_pass_to_the_longest_seated_when_the_host_leaves`, which also asserts the room
code and privacy survive. Ordering is **`joined_at`**, not vec position and not seat id —
`a_rejoiner_with_a_recycled_seat_id_does_not_inherit_the_settings` pins that.

**Closing an empty lobby also already works**, on a delay: the registry stamps
`empty_since` on the last detach and `reap` drops the room after `ROOM_EMPTY_TTL = 30.0`,
checked every `ROOM_REAP_INTERVAL = 2.0`.

## So what is actually missing

1. **The third departure path does not notify.** `sweep_unready` frees seats without
   `note_lobby_change()` — the one case where promotion happens server-side and no client
   is told. **That is T20.01's fix; do not duplicate it here.** This task depends on it.
2. **Nothing on screen names the host.** `RosterRow` carries `seat/label/ready/bot/you` and
   no host marker; `MenuScene.ts:314-320` renders classes `seat/ready/you/bot`. A promoted
   player gets working arrows and no idea why, and the old host gets dead arrows with no
   explanation.

## Deliverable

- The roster shows **who the host is**, and it updates when the host changes.
- Confirm — with a test, not by reading — that promotion survives the T20.01 path once that
  lands.
- If `ROOM_EMPTY_TTL`'s 30 s delay is not what "close the lobby" should mean, say so with
  the measurement; do **not** change a reaping constant without one.

## Notes

- **Resist adding a `host` field to a seat.** `settings_owner` is derived precisely so
  three flags cannot disagree — derive the marker from it.

## Tests

- The roster marks exactly one host, and the mark **moves** when the host leaves — with a
  control that the mark is not simply on seat 0.
- A browser check: two clients, the host leaves, and the survivor's screen shows the arrows
  enabled **and** the host marker on itself.
