# T20.01 — The host is swept out of its own lobby (v8)

Milestone: M20 · Depends on: nothing · Size: ~150 lines

**No doc section governs this** — it is a defect against existing behaviour. Reported:
*"about 30 s to a minute into hosting a private match, the host stops being able to change
the settings if the match hasn't started. 'Could not join (only the host can change the
settings).'"*

## Read first
- `crates/game-server/src/room.rs` — `settings_owner` `:1170-1176`, `check_settings_change`
  `:1446-1455`, `sweep_unready` `:1864-1884`, its call site `:2765`
- `client/src/net/lobby.ts:62,80-81` — `joinErrorMessage`
- `client/src/scenes/MenuScene.ts:105-152` — `enterLobby`

## The cause, already established

`settings_owner()` is **derived**: the non-bot seat with the smallest `joined_at`. Nothing
about it is time-based. **What changes at 30 s is the seat list.**

`sweep_unready` frees every seat with `!seat.ready` older than `READY_TIMEOUT_SECS = 30.0`
(`constants.rs:231`), and it runs **unconditionally every tick, lobby or match**
(`room.rs:2765`). `Seat.ready` is the handshake latch set only by `Command::Ready`
(`room.rs:1576-1587`) — and **a private-lobby host never sends it until they press the
button.** `MenuScene.enterLobby` sends `join`/`create_room` and nothing else; the lobby's
only `ready` is the tick-box at `MenuScene.ts:366`, and `GameScene.ts:1026`'s comes after
`map_init`.

So the host is swept at t≈30 s, `settings_owner()` becomes `None`, and every arrow is
refused.

**Why the screen still lets them press it:** `sweep_unready` does not call
`note_lobby_change()` and its return value is **discarded** at `room.rs:2765`. No
`lobby_state` rebroadcast, no `player_leave`, no `ctx.detach`. Compare `Command::Leave`
(`room.rs:1701-1708`), which does notify. The client keeps a stale `settings_owner`,
`ownsSettings` still returns true, and the arrows stay enabled.

**Two knock-on effects, both in scope:**
- The freed id goes onto `Seats::free` (`room.rs:658-663`), so the next joiner gets the
  ghost host's id and `SessionMap::insert` (`session.rs:140-151`) evicts the ghost's
  mapping. The host's socket then has no player id — same bug, different text
  (*"Could not join (not seated)"*).
- `ctx.detach` is never called, so `RoomEntry.humans` stays ≥1 and the seat-less room is
  never reaped.

**The error text is a second defect.** Settings refusals emit `lobby_error`
(`session.rs:526-546, 579-681`), and the client routes it into `joinErrorMessage`
(`MenuScene.ts:133-135`), whose default branch is `` `Could not join (${reason}).` ``.
There is no `lobbyErrorMessage`.

## RULING — `docs/74` §E3 decides this, and it decides it against the code

**Added after the forward sweep. This is not a free choice.** `docs/74-amendments-v6.md:110`,
§E3 Private lobbies:

> **No timeout, ever.** A private lobby waits as long as its players do.

A thirty-second eviction from a private lobby is precisely the timeout §E3 forbids, so **the
code is out of spec and the reported bug is that violation biting a real player.** The
earlier draft of this task offered "decide which and say why" — withdrawn. §E3 governs.

**The control at `private_lobby.rs:276-283` asserts behaviour §E3 forbids** — that a
never-handshaken seat *is* swept **in a private lobby** — and the same test's doc comment
cites §E3 as the reason the *other* half must not sweep. The file argues both sides.

**Move the WHOLE test to a non-private room — not just its control.** An earlier draft of
this ruling said to move the control alone. That is wrong, and wrong in the exact way the
test exists to prevent. The test is two assertions in one private room:

- `:268-274` — ready, un-ready `bo`, sweep, assert nothing dropped. *Un-readying does not
  arm the sweep.*
- `:276-283` — the control: seat `never`, sweep, assert `never` dropped. *The sweep fires at
  all, so the assertion above is about the toggle.*

Once a private lobby is never swept, `:268-274` passes **because the sweep is disabled**,
not because the `ready`/`consent` split works. Falsify it: collapse the two fields back into
one at `room.rs:1580-1581` and it still passes. That is precisely what the test's own doc
comment at `:252-255` says it was written to stop — *"Collapsing the two fields back into
one passed every other test in this file, so the split was carrying no assertion at all."*
Moving only the control leaves a green test with a stated purpose and zero coverage, under a
doc comment that has become false.

So: **both** assertions move to a non-private room, where the sweep is enabled and the
`ready`/`consent` split is genuinely under test again. Then add a **separate** private-lobby
test for the new §E3 behaviour — *the sweep never fires in a private lobby* — and give it a
non-private room as its control, because that new test asserts an absence and an absence
needs a presence.

## Deliverable

- **A private lobby is never swept.** Scope the sweep to rooms where it is legitimate — a
  started match, or a non-private room. The sweep must keep working there: it exists so a
  dead socket cannot hold a seat forever, and `room.rs:3199-3225` is that case.
- Whatever the sweep frees, it **notifies**: `note_lobby_change()` and the same detach the
  `Leave` path performs. A seat freed with nobody told is the bug behind the stale screen.
- A distinct `lobbyErrorMessage` so a settings refusal does not say *"Could not join"*.

## Notes

- **"The same detach the `Leave` path performs" was wrong in the earlier draft.**
  `Command::Leave` (`room.rs:1701-1726`) does **not** detach. Every `ctx.detach` is in the
  socket layer (`session.rs:496, 961, 1011, 1056, 1072`), and the sweep fires at
  `room.rs:2765` inside `async fn run`, whose scope holds `io` and `Arc<SessionMap>` but
  **no registry handle** — so `e.humans` cannot be decremented from there without threading
  one in. Reachable from the tick today: `SessionMap::sid_of` → `SessionMap::remove_sid`.
  **Do the `SessionMap` half, and do not claim the "room is never reaped" knock-on is fixed
  unless you actually thread a registry handle.** An unsupported journal line is worse than
  an unfixed knock-on.
- **The broadcast half is easier than it looks.** `take_lobby_update()` sits at
  `room.rs:2768`, three statements after the sweep — a `note_lobby_change()` inside
  `sweep_unready` is picked up on the very same tick. No plumbing.
- **And the guard is automatically shared:** `sweep_unready_for_test` (`room.rs:2383-2385`)
  is a bare delegate, so a guard added inside the private fn reaches all four test call
  sites.
- **After this change the sweep's lobby branch is unreachable in production at defaults —
  say so in the journal, or a later milestone deletes it as dead and finds two red tests.**
  Both surviving controls (`room.rs:3199-3225`, `replay.rs:198-203`) sweep a **public**
  lobby. But `room.rs:1557-1561` sets `starts_in = lobby_bot_timeout` the moment the first
  player is seated in a non-private room, default `LOBBY_BOT_TIMEOUT = 10.0`, and §E2 says
  it does not reset — against `READY_TIMEOUT_SECS = 30.0`. **A public lobby cannot live to
  30 s at default config.** So "the sweep must keep working for the case it was built for"
  resolves entirely to the **started-match** branch, which is what `room.rs:1861-1863`
  describes anyway: *"a client that fails to decode the map holds a slot forever"* — a
  client that received `map_init`. The public-lobby branch is kept alive by those two tests
  and by the env override at `room.rs:1558-1560`, and by nothing else.
- **`sweep_unready` records `ReplayCommand::DropUnready`** (`room.rs:1877`). Changing *when*
  it fires changes recorded streams. The pins are `tests/replay.rs:193-210` and `:377-410`
  — the second is bots, which can never send `ready`.
- **A third divergence from `Leave`, beyond the two named above:** Leave calls
  `self.round.forget(id)` (`room.rs:1708`) and the sweep does not, so a swept player keeps
  its round and vote state. Decide whether that matters here or book it.
- **Pin a hardcoded tunable while you are in there:** `room.rs:3210` is
  `sweep_unready(Duration::from_secs(30))` — a literal against `READY_TIMEOUT_SECS = 30.0`,
  when `room.rs:2592` already exposes `pub const READY_TIMEOUT: Duration` derived from it,
  in the same file.
- No test caught this because `lobby.mjs` never sits in a lobby for 30 s — its longest wait
  is 2 s.
- **The error-text half reproduces as written.** The `lobby_error` reasons at
  `session.rs:526-546` and `:579-681` are already full sentences, and `lobby.ts:80-81`'s
  default branch wraps them — so only the wrapper is wrong. A `lobbyErrorMessage` can pass
  most reasons straight through.

## Tests

- **A host that sits in a private lobby past `READY_TIMEOUT` can still change every
  setting.** Pinned to the constant, not to a literal, and it must actually wait it out.
- The control: a seat that is genuinely gone still frees, and the room still reaps.
- Whatever the sweep frees, a `lobby_state` reflecting it is broadcast — asserted on the
  client's view, not on the server's internal state.
- A settings refusal renders as a settings message, with a join refusal as the control.
