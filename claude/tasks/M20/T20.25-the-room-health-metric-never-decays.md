# T20.25 — The room-health metric never decays (v8)

Milestone: M20 · Depends on: nothing · Size: **small**, and it is the instrument

**Found by T20.14**, by trying to use `room_health` to answer "does per-tick cost grow with
the number of rooms" and discovering the reading cannot answer it.

## The comment and the code

`metrics.rs::record_room_tick` carries this doc comment:

> *A room's worst tick since it last reported. Decays, so a spike five minutes ago does not
> make a healthy server look permanently sick.*

and this body:

```rust
let e = m.entry(room).or_insert(0);
*e = (*e).max(micros);
```

**Both clauses are false.** Nothing resets the entry when it is reported —
`metrics.rs::room_health` reads `room_worst_us` and never clears it — and nothing decays it.
The only removal is `metrics.rs::forget_room`, called from `registry.rs` when a room is
**dropped**.

So `room_worst_us[room]` is a running maximum over the room's whole life. One 20 ms hiccup at
startup — a first tick, a descheduled thread, a neighbouring `cargo` build — makes that room
read "over budget" on `/metrics` for as long as it exists.

## What reads it

`metrics.rs::render` publishes both derived numbers:

```
tick_p99_ms_max_over_rooms {}
rooms_over_budget {}
```

`rooms_over_budget` is the count that `docs/71` §B2's capacity threshold is expressed
against. **A number that can only go up is not a health signal**, and the one place it is
consumed is a capacity decision.

This is `CLAUDE.md`'s *"a comment claiming an invariant is an intention too"* in the
monitoring layer: the comment is the only record of the intended behaviour, and nothing
re-validates it.

## What it cost T20.14

The load driver reported "worst room tick 6.90 / 7.84 / 8.56 / 8.69 ms" across runs of
different lengths and room counts, and **none of those numbers can be compared with each
other**: a running maximum grows with the number of samples taken, so a longer run reads
higher for reasons that have nothing to do with rooms. The driver's note now says so; it
cannot say anything about scaling.

`capacity.rs::rooms_do_not_get_more_expensive_as_more_are_added` is the test that *can*
answer the scaling question, and it is `#[ignore]`d — run through `scripts/ignored.sh`.

## Decide which, and say why

1. **Reset on read** — matches "since it last reported", and makes `/metrics` a sampling
   interface where two scrapes must not race. Note `render` calls `room_health()` **twice**,
   so a reset-on-read would zero the second call's answer; fix that at the same time or the
   two published numbers disagree by construction.
2. **A real decay** — a windowed or exponentially-decayed max, which is what the comment
   promises and what a dashboard wants.
3. **Rename it** to what it is (`room_worst_ever_us`) and leave the behaviour, if a
   lifetime high-water mark is genuinely the intent.

Option 3 is the cheapest and is not obviously wrong; what is wrong is the present state,
where the comment says one thing and the number does another.

## Done when

A unit test in `metrics.rs` pins the chosen behaviour — for 1 or 2, that a large sample
recorded and read is **not** still reported after a small one; for 3, that it is — **and the
test fails against the other choice.**

```sh
cargo test -p game-server && ./scripts/check.sh
```
