## The weight is probably not the problem

Measured shares today (spawn total 226, crate 250, buried 208; 19 drawable rows):

| item | spawn | crate | buried |
|---|---|---|---|
| medkit | 13.3 % | 10.0 % | 9.6 % |
| bazooka | 9.7 % | 8.0 % | 7.2 % |
| grenade | 8.9 % | 6.0 % | 7.2 % |
| pistol | 8.0 % | 3.2 % | 4.8 % |
| **battery_pack** | **6.2 %** | **7.2 %** | **5.8 %** |

It is already **5th of 19 on the ground and 2nd-equal in crates**. T19.05's melee
retirement *raised* it (5.04 → 6.19 % spawn, +23 % relative) with its raw weights untouched
— so **any change must be argued in shares, not raw weights**, or it re-litigates a number
that has already moved.

**Two of the four are already answered — do not spend a run on them.**

`constants.rs:539-543`, the doc comment on `ITEM_SPAWN_INTERVAL`, records a T11.13
measurement:

> *"**Paired with the `WORLD_ITEM_TTL` cut, so this is turnover and not accumulation**:
> simultaneous items are flat or lower at every scale, well clear of `MAX_WORLD_ITEMS`.
> Raising the rate alone would have pushed the live count into the cap, where eviction
> deletes what spawned two minutes ago instead of adding to it — churn that measures like
> density."*

That retires **cause 4** (the live count is well clear of the cap) and reframes **cause 3**
(the TTL cut was deliberate and paired, with a stated reason for not cutting further). It is
also a **pre-written refutation of the easy fix**: raising the rate alone was tried, and it
produces churn that *measures like density* — so a coder who "fixes" this with a magnitude
gets a number that looks better and a game that is not.

**Four candidate causes, in order:**
1. **Picking one up makes it invisible.** `items/world.rs:94-118` routes MEDKIT and
   BATTERY_PACK into `heals`/`batteries` counters (§C9), capped at `MAX_BATTERIES = 4`. It
   never becomes an inventory tile — only a small counter beside the bars. *"I've never seen
   any"* may be a HUD legibility problem.
2. **Volume.** `initial_items` is 8/14/20 by scale, then `ITEM_SPAWN_INTERVAL = 14.0` in
   batches of 1–2 over a 240 s round — on Large ≈ 45 draws, so **≈ 2.8 battery packs per
   round shared between everyone**.
3. `WORLD_ITEM_TTL = 70.0` — a ground item evaporates after 70 s.
4. `MAX_WORLD_ITEMS = 40` evicts the oldest non-crate.

## Cause 1, already checked for free — start here

`bars.ts:114-120`: `#hud-consumables` is `position:absolute; left:100%; bottom:0;
margin-left:8px` inside a `#hud-bars` that is `position:fixed; left:10px; bottom:56px`,
width 168 — so it lands at **x≈186, bottom-left. It is on screen**; "rendering
off-viewport" is not the answer. `bars.ts:138-141` renders `⚡ ${batteries} R`
unconditionally in 13 px monospace, so **a player who has never touched a battery is already
looking at `⚡ 0 R`.**

Independent supporting evidence, also free: `BATTERY_PACK` carries `max_stack: 3`
(`registry.rs:236`) while the pickup path routes it to a counter capped at
`MAX_BATTERIES = 4`. The item is *defined* inventory-shaped and *behaves* as a counter, and
the two numbers disagree about how many you can hold.

## The instrument you would need for causes 2–4 does not exist

**Say so rather than reaching for the one that does.** The share table and
`melee.rs:839-890` both measure `roll_item(&mut rng, col)` — no map, no clock, no TTL, no
cap. Causes 2, 3 and 4 all act **after** the draw, so that instrument is blind to 3 and 4
and cannot separate 2 from either.

What discriminates them is a **standing-population** measurement that is not in the tree:
items alive per tick over a simulated round, bucketed by item, plus TTL expiries and
`MAX_WORLD_ITEMS` evictions as **two separate counters**. Those three numbers separate
cleanly; nothing else does.

**So: settle cause 1 first, because it is free.** Only build the population instrument if
cause 1 is ruled out — and if you build it, it is the deliverable and the fix can wait.

## Deliverable

**Establish which cause it is, then fix that one.** Report the measurement either way. If it
is (1), the fix is on screen, not in the table.

## Notes

- `registry.rs:676-693 the_flashlight_is_the_most_buried_item` asserts
  `d.buried_weight < fl` where `fl` is **the flashlight's own** `buried_weight` — a
  *relative* rule that happens to read 25 today (`registry.rs:193`). Do not write 25 into
  anything; if the flashlight moves, a Note saying "under 25" is wrong and reads
  authoritative.
- `balance.rs:263-300` pins the zero-weight set exactly. Do not accidentally zero anything.
- `density_report`'s floors scale with `pool` = the count of rows with any nonzero weight,
  so changing a magnitude does **not** move them; adding or removing a drawable row does.

## Tests

- Whatever changes, a **population** claim: aggregate across seeds, not one draw.
- If the fix is the HUD, assert on **rendered pixels** with a control — a player holding
  none. **But mind the trap, because it is `hud-timer`'s failure verbatim:** if the change
  is one glyph (`0` → `1`) in 13 px monospace, `samplePatch` returns a **mean colour** of a
  rect and `assertChanged` defaults to `minDelta = 8`. **A single digit cannot move a rect
  mean by 8.** The coder then either drops `minDelta` until it fails on a coin flip or
  shrinks the rect into a glyph-alignment lottery — which is exactly how M19 lost a day.
  **So the fix must produce a change a rect mean can see**: a tile, an icon, a colour, a
  filled pip row — not a bigger digit. That is the right constraint anyway, since the
  diagnosis is "an invisible counter".
- `melee.rs:839-885` already asserts each item lands within ±30 % of its own share; it
  survives a weight edit and catches a mis-sum.
