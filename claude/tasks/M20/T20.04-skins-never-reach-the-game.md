# T20.04 — Skins never reach the game (v8)

Milestone: M20 · Depends on: nothing · Size: **larger than it looks** — three writers, a
rebuilt view, and a harness that cannot currently seed two skins

**No doc section governs the defect.** Reported: *"skins don't work. Everyone looks the
same. I set myself to a zombie in the menu and it doesn't change in game."*

## Read first
- `client/src/scenes/GameScene.ts:439-449, **493-507**, 549-555, 1015, 1558, **1556-1560**,
  **1579-1584**`
- `client/src/render/playerView.ts:116, 150-173, 290-292`
- `client/src/render/tombstones.ts:83,92` — the contrast that proves the pipeline works
- `client/src/scenes/SkinsScene.ts:126` — **the one construction site that already does it
  right**, `new PlayerView(this, this.choice.skinId)`. Copy its shape.
- `scripts/checks/pixels.mjs:1-20, 41, 62, 99, 109, 144` — the pixel harness already exists
- `scripts/checks/harness.mjs:212-243` — `openClient`, and the reason the test is hard

## The cause, established end to end

**The whole pipeline works up to the last step.** Menu → `localStorage` works
(`SkinsScene.ts:126,151-160` → `skins.ts:73-77`). `localStorage` → wire works
(`MenuScene.ts:192` → `connection.ts:177` emits `skin_id` on all four verbs). The server
stores it per seat (`room.rs:549,596-600`) and re-broadcasts it twice — `events.rs:459`
puts it in every `lobby_state` seat and `session.rs:1364` in `player_join`. The client
parses it into `LobbySeat.skinId` (`lobby.ts:204`). The art ships: `assets/skins.json` id 4
is "Revenant"/`character_zombie_`, and all ten `character_zombie_*` frames are in
`assets/atlas/chars.json`.

**`GameScene` then throws it away, in three places:**
- `:439-449` — the `lobby_state` handler stores only `{name, score, deaths}`. `p.skinId` is
  parsed and discarded.
- `:549-555` — `player_join` does the same; `p['skin_id']` is never read.
- `:1015` and `:1558` — `new PlayerView(this, 0)` for the local body **and every remote**.

So everyone is skin 0, "Recruit". `PlayerView.skinId` is `readonly` and consumed only in
the constructor — there is no `setSkin`, so the id must be known at construction.

**The contrast that proves it is not an asset problem:** tombstones *do* vary —
`tombstones.ts:83,92` use `v.skinId` off the `tombstone_spawn` payload. Graves are
personalised; players are not.

## There are THREE writers to `scores`, and the third is the dangerous one

The task originally named two. There are three, and they are written in three different
idioms:

- **`lobby_state`** (`:441-448`) **merges**: `const had = this.scores.get(p.seat)`, then
  `score: had?.score ?? 0`.
- **`player_join`** (`:549-554`) **clobbers**: `set(id, { name, score: 0, deaths: 0 })`,
  never reading the prior entry.
- **`score`** (`:493-507`) **reconstructs field by field** from a two-field payload,
  carrying forward only `name`.

**Add `skinId` to the map and forget the third and every `score` event resets every
player's skin to 0.** Score events fire on every kill.

**So keep `skinId` required and non-optional on the map's value type (`GameScene.ts:273`).**
Then the compiler flags the site you forgot. Make it `skinId?: number` and all three
compile, and only the pixels disagree — which is this bug again, one layer down.

*Out of scope but worth a journal line:* the merge/clobber split is **already** a live
defect for scores — a `player_join` arriving after a `score` event resets that player's
tally, because `:551` writes `score: 0` unconditionally. `:493-507`'s own comment describes
that bug being found once before (T9.06). Do not fix it here; record it.

## The view is rebuilt during a round, so the skin must be re-read

`GameScene.ts:1579-1584` **destroys** every remote absent from the current `sampled` set and
deletes it; `:1556-1560` reconstructs it on return. So the skin is not read once — it is
re-read on every rebuild, from whatever `scores` holds at that moment. That is what makes
the three-writers problem visible rather than theoretical.

It also answers the "drawn before `player_join` arrives" question, and **the answer is not a
free choice**: `PlayerView.skinId` is `private readonly` (`:116`), assigned once at `:152`,
consumed in the constructor. There is **no setter** — the only accessor is `get skin()`
(`:290-292`). So either the view is rebuilt when the skin becomes known, or a remote drawn
one frame early stays skin 0 until it next leaves the sampled set. Since `:1579-1584`
already rebuilds routinely, the cheap correct shape is to read
`scores.get(id)?.skinId ?? 0` **at the construction site** and force a rebuild when a
handler changes a known player's skin.

- A remote may be drawn before its `player_join` arrives. Decide what happens then and say

## The e2e harness cannot currently give two clients different skins — solve this first

`openClient` (`harness.mjs:212-243`) navigates to `?e2e=1&game=1&name=…`, the **dev path**,
which never touches `MenuScene`. On that path the skin comes from `GameScene.ts:935` —
`localStorage.getItem('deepcut.skin')`, read at scene create **immediately after `goto`**.
`openClient` takes `name` and `query` and **no skin**, and there is no seam: `page.evaluate`
(the pattern `lobby.mjs:44` uses) runs *after* `goto` and is too late, and `ctx.addInitScript`
appears **nowhere** in `scripts/`.

**So a two-client check built on `openClient` today puts both players on skin 0, the frames
match, and the assertion fails against a correct fix.** That is the shape that gets a
threshold loosened at 2am. Two ways out, both acceptable — **pick one and say why**:
`ctx.addInitScript` before `goto`, or a `skin` query param on the dev path beside the `name`
one `GameScene.ts:906` already reads.

## Tests

- **Assert on rendered pixels** (§C2): two clients with *different* skins, and the two
  players' regions differ **in the same frame**.
- **Use `scripts/checks/pixels.mjs`; do not write a fourth sampler.** `toScreen` converts
  world → screen through the **live** camera (never a fixed pixel), `samplePatch` reads,
  `colourDelta` compares. Its header documents the three traps this test must avoid.
  **One caveat:** `assertChanged` compares two frames of **one** page, which is the wrong
  shape for the main assertion — `colourDelta` is the primitive you want. `assertChanged`
  *is* the right shape for the **control frame**: a region the players do not occupy, before
  and after, asserted unchanged.
- `get skin()` (`playerView.ts:290-292`) already exists. It may be used as a **control** —
  the id reached the view *and* the pixels differ — but **never as the assertion**. The bug
  is precisely that the id was known and not drawn.
- Falsify at the live binding site: put `0` back at `GameScene.ts:1558` and the check goes
  red.

## Notes on why nothing caught it

`scripts/checks/skins.mjs` never enters a game — it steps the picker, checks the preview
and `localStorage`, and returns to the menu. `lobby.test.ts:232` asserts `skinId: 2`
survives parsing. Both are true and neither is the bug. **Nothing anywhere asserts a
rendered player's skin**, so a fix breaks no existing test — which is the whole problem.
