# T20.02 — A nickname you choose once (v8)

Milestone: M20 · Depends on: nothing · Size: ~120 lines

**No doc section governs this.** Reported: *"players should be prompted to set a nickname
(once, remember it in localStorage) when either joining or hosting a match. Don't just call
them 'dude'."*

## Read first
- `client/src/ui/skins.ts:13-15` (keys), `:18` (`MAX_NAME`), `:26`, `:33-45` (`readId`),
  `:48-58` (`cleanName`), `:60-77` (`loadChoice`/`saveChoice`)
- `scripts/checks/lobby.mjs:44`, `scripts/checks/m10-checkpoint.mjs:78`,
  `scripts/checks/skins.mjs:93-94` — **the browser fixtures that spell the keys out**
- `client/src/scenes/MenuScene.ts:189-194` — `identity()`
- `client/src/scenes/SkinsScene.ts:184-186,204-207` — the name input that already exists
- `crates/game-server/src/session.rs:298-311` — `sanitise_name`

## What is actually there

**There is no "dude" in the repo.** The default is **`'Player'`**, and it is defined twice:
`skins.ts:26` (`DEFAULT_CHOICE`) and again inline at `MenuScene.ts:189-194`, which reads
`localStorage.getItem('deepcut.name') || 'Player'` **directly** — bypassing `loadChoice` and
`cleanName` and re-spelling all three keys. That is the live binding site for every lobby
verb.

Everything downstream already works: `identityPayload` (`lobby.ts:305-312`) →
`Connection.connect` sends `name` on all four verbs → `sanitise_name` (1–16 chars, control
characters stripped, `bad_name` refusal) → `Seats::set_identity`. Names reach the roster
(`lobby_state.players[].name`) and the HUD (`GameScene.ts:435-444`).

**A name input already exists** — `SkinsScene.ts:184-186` — but it is buried behind the
Skins button and nothing prompts for it.

## Do not rename the `deepcut.*` keys in this task

The game was rebranded Deep Cut → SHRED in `916f26d`, so renaming the storage keys will
look like tidying. **It is a trap, and it is silent.** Three browser checks spell the keys
out as literals — `lobby.mjs:44` and `m10-checkpoint.mjs:78` **set** `deepcut.name` to seed
a named player, and `skins.mjs:93-94` reads `deepcut.skin`/`deepcut.stone`. Rename the key
and those fixtures seed a value nobody reads: the checks keep passing against the default,
and **this task's own "read it off the roster" test would be asserting `Player` against
`Player`.** That is the vacuous-fixture shape M19 hit twice.

The keys do not change here. If they ever do, those three `scripts/` sites are part of the
rename.

## Deliverable

- **Prompt once**, on the first join or host, when no name has been stored. Not a nag: once
  stored, never asked again.
- Persist through the **existing** helpers. `MenuScene.identity()` must stop re-implementing
  the read — route it through `loadChoice`/`cleanName` so a stored `"  "` or `"<b>"` cannot
  reach the wire raw.
- Remove the duplicated default. One `DEFAULT_CHOICE`.
- **Guard all three fields, not just the name.** `MenuScene.ts:192-193` is
  `Number(localStorage.getItem('deepcut.skin') ?? 0)` — `Number("banana")` is `NaN`, which
  `JSON.stringify` puts on the wire as `null`. `readId` (`skins.ts:33-45`) exists precisely
  to stop that and is bypassed for the skin and stone ids in the same six lines as the name.
  The server degrades safely (`as_u64().unwrap_or(0)`) but **the client renders its own skin
  from that same `NaN`**.
- **A fourth inline re-spelling the earlier draft missed:** `SkinsScene.ts:237-239`, inside
  `exposeDebugHandle`'s `stored:` probe, re-types all three raw key strings. That one should
  keep reading raw — reporting what is in storage is its job — but it should **import**
  `SKIN_KEY`/`STONE_KEY`/`NAME_KEY` rather than re-typing them.

## Notes

- **"Route it through `loadChoice`" is not executable as written — decide which way out.**
  `loadChoice(store, skinCount, stoneCount)` needs a skin count; `SkinsScene.ts:66` gets it
  from `skins()?.players.length` **after the atlas loads**, and `MenuScene` imports no skin
  registry at all and has no count. SUSPECTED that the atlas is not loaded at menu time.
  Two ways out, and this task wants you to **pick one and say why**: give `MenuScene` the
  atlas lookup, or split a `loadIdentity(store)` out of `loadChoice` that clamps ids without
  a count. Do **not** take the third way of adding another inline read — see the next note.
- **Share the function, do not add a second reader.** The bug this fixes is that
  `MenuScene` already has its own copy of the read; a prompt that adds a third is worse
  than what is there now.
- `GameScene.ts:906` uses `params.get('name') ?? \`player${random}\`` for the `?game=1` dev
  path and never reads `deepcut.name`; `:935` reads `deepcut.skin` inline for the same
  reason. Decide whether those join the shared path or stay dev-only, and say which.
- The server already refuses a bad name (`bad_name`). The client should not be able to
  produce one.
- **The server is not the backstop for the HTML half, and the task should say who is.**
  `cleanName` strips `<>` (`skins.ts:56`); `sanitise_name` (`session.rs:298-311`) does not —
  it trims, drops control characters and takes 16. So the client is the only guard against
  `<b>`, and `GameScene.ts:906`'s dev path bypasses it. State which side owns `<>` when you
  answer the dev-path question above.

## Tests

- With nothing stored, the prompt appears **once**; with a name stored it never appears —
  and the control: a stored name really is the one sent on the wire.
- **Store junk in all three keys** — name, skin, stone — directly in `localStorage`, and
  assert what reaches `identityPayload`. One test, three fields; `NaN` on the wire is as
  much a defect as `<b>`.
- A browser check: set a name, join, and read it **off the roster**, not out of
  `localStorage`.
