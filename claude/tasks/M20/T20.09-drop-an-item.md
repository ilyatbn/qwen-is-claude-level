# T20.09 — Right-click an inventory tile to drop it (v8)

Milestone: M20 · Depends on: nothing · Size: ~250 lines — a five-layer command

Wanted: *"right clicking an item in the inventory drops it near you."*

## Read first
- `docs/75-amendments-v7.md:147-155` (§F4.1) — **read this first; it is about the right button**
- `crates/game-server/src/room.rs:1667-1673` and `crates/game-core/src/world/mod.rs:2911-2930`
  — `MoveItem`, the pattern to copy
- `crates/game-core/src/items/world.rs:125-153,320-345`
- `client/src/ui/inventory.ts:76-83,100,131-149`

## There is no drop path today

Grepped: no `drop_item`, no `DropItem`, no discard. The **only** route from inventory to
ground is death — `PlayerState::die` returns the stacks and `resolve_deaths` scatters them
with a random angle, speed 60–140, `SpawnSource::Death`.

## Does right-click conflict with the backpack? Not physically — but read §F4.1

§F4.1 is explicit and recent: *"Left button fires. Right button opens the backpack"*,
recorded as considered-and-rejected. **Write this task against that clause, not around it.**

Mechanically the two gestures **are** separable: the backpack toggle is on the **Phaser
canvas** (`GameScene.ts:812-825`), while the inventory panel is **DOM**, `position: fixed`,
appended to `document.body`, with `pointer-events: auto` on the tiles. A right-click landing
on a tile never reaches the canvas.

**But `main.ts:88-91` suppresses `contextmenu` only on `game.canvas` and `#game`.** The
inventory root is `body`-appended (`inventory.ts:156`), so `contextmenu` bubbles
tile → `#inventory` → `body` and never through `#game`. The browser menu pops. Suppress it
on the tiles or the root.

**And the existing checks are structurally incapable of catching that**, which is why it
survived: `inventory-ui.mjs:64` and `:300` right-click at a hardcoded
`{ x: 640, y: 360 }` — a viewport-centre coordinate that lands on the **canvas**, where
suppression already works. Do not read that coverage as meaning anything here.

## The gesture is ambiguous by geometry — settle it, do not discover it

`inventory.ts:84` puts `pointer-events: none` on the panel **root** and only tiles get
`pointer-events: auto` (`:105`). So the moment this lands:

- right-click **on a tile** → drops the item;
- right-click **in the 6 px gap between tiles**, or on the panel's padding → falls through
  to the canvas and hits `GameScene.ts:812-825`, which **closes the backpack**.

Two different outcomes a few pixels apart, on a panel the player is deliberately aiming at.
That is *"sometimes it drops, sometimes it just closes"* — a bug report written before the
bug exists. **Settle it:** either the root takes `pointer-events: auto` while open and owns
its own close gesture, or the drop is delegated from the root with an explicit tile-hit
test. Both are decisions; pick one and say why.

## The trap that will waste your afternoon

`resolve_pickups` auto-collects anything within `PICKUP_RADIUS = 20.0`, and
`pickup_locked_until` is set **only** for `SpawnSource::Death` (`world.rs:146-150`,
`DEATH_DROP_LOCK = 1.0`). **A drop "near you" with no lock is picked straight back up on the
same tick.** Either add a `SpawnSource::Dropped` with its own lock or reuse `Death`'s.

**Two corrections to that.** First, **the new lock constant goes in `constants.rs`.**
`DEATH_DROP_LOCK` lives at `items/world.rs:23`, which already violates "every numeric
tunable lives in `constants.rs`" — put a new one beside it and you replicate the violation.
Moving the existing one is scope creep; journal it as a pre-existing gap (`STARTING_KIT` at
`state.rs:35` is the same class).

Second, **"it changes how the client draws it" was overstated — it does not.** Every client
read of `source` is a `=== 'Crate'` comparison (`itemSprites-math.ts:74,115,214`,
`itemSprites.ts:200`), and the parse is untyped with a fallback (`worldMirror.ts:58,309`).
A new `Dropped` variant flows straight through and draws as an ordinary item. **No client
change is required.** If a dropped item *should* look different, that is a new decision, not
a consequence of this one.

## Deliverable

The five-layer command, following `MoveItem` term for term: `inventory.ts` handler →
`connection.ts` sender → `session.rs` socket handler (`unwrap_or(255)` so a missing field is
a refusal) → `Command::DropItem` (enum, `Display`, handler) → `World::drop_item` beside
`move_item` → `GameEvent::Inventory` + `ItemSpawn`.

**It changes the simulation, so it must be recorded in the replay.** Highest tag in use is
21, so `DropItem` is tag 22.

**Do not bump `REPLAY_VERSION`, and here is the repo's own reasoning.** The doc comment at
`replay.rs:44-64` gives the policy across all three prior bumps: **v2** the header grew a
field, **v3** an old file *"would load, run, and diverge silently"*, **v4** the header grew
two fields. The rule is *bump when the header layout changes, or when an old file would load
and diverge.* A new tag does neither — the header is untouched, and a v4 file simply
contains no tag-22 commands, so it replays byte-identically. Tags are **explicit literals in
a match** (`replay.rs:172-194`), not derived from declaration order, so a new variant shifts
nothing; `tags_are_unique_across_every_variant` and `every_command_really_is_every_command`
guard both halves. **Bumping "to be safe" rejects every existing local recording** —
`decode` at `:624` refuses any version mismatch outright.

**The whole `STARTING_KIT` must be refusable — not "the shovel".** `state.rs:432-436`
filters on `!STARTING_KIT.contains(&s.item)`, and `STARTING_KIT` is `[ItemId; 1] = [SHOVEL]`
(`state.rs:35`). It is a **kit-wide** rule that happens to contain one item today. The
natural thing to write at a drop site is `if item == SHOVEL { refuse }` — identical now,
divergent the day the kit grows, and §F7's `all` start kit means the kit is a thing that
moves. **Refuse through the same predicate**; `registry.rs:557` already reads
`STARTING_KIT.contains` for a third purpose, so the shared shape is established.

## Tests

- The tile empties, **the server's inventory agrees**, and a world item exists at the
  player's feet — counted at both ends.
- **Click a tile by selector, never by coordinate.** The panel is `position: fixed;
  left: 50%; bottom: 34px`, occupying roughly the bottom ~130 px — clear of the existing
  checks' hardcoded `y: 360` today, but a coordinate-based drop test makes the two gestures
  distinguishable only by arithmetic that the next layout change breaks.
- The dropped item is **not** instantly re-collected. Control: after the lock expires it
  can be.
- Dropping a `STARTING_KIT` item is refused. Mirror `combat.rs:996-1053`, which already
  carries its own control at `:1045` (*"the consumable stopped spilling, so the weapon
  assertion above proves nothing"*) alongside its "and no shovel" at `:1051` — that pairing
  is the model.
- `inventory-ui.mjs:56-72,299-305` assert right-click opens/closes the backpack, and
  `:309-347` (§F4.1) asserts holding the right button for 1 s fires nothing with a
  left-button control. **A drop must break neither.** This check is the natural home for the
  acceptance.
