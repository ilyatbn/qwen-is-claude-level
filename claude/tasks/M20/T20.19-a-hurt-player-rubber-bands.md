# T20.19 — A hurt player rubber-bands, permanently (v8)

Milestone: M20 · Depends on: nothing · Size: small fix, **but read the second half**

**Found by T21.02's forward sweep. This is a live defect at HEAD, not M21's** — it predates
M20 and ships today.

## The mechanism, CONFIRMED by reading both call sites

The pure movement path already takes a speed multiplier, and **the two sides disagree about
its value**:

- **Server** — `world/mod.rs`, in `apply_inputs`:
  `let speed = self.players[idx].speed_multiplier();` passed into `apply_input`.
- **Client** — `game-wasm/src/lib.rs::apply_input` passes a literal **`1.0`** in that
  argument position.

`PlayerState::speed_multiplier()` lerps `HEALTH_SPEED_MIN` (**0.75**) → 1.0 by
`health / BASE_HEALTH`. So **a damaged player is predicted at full speed and simulated up to
25 % slower.**

`RECONCILE_EPSILON_PX` is **2.0**. A 25 % speed error at `WALK_SPEED` crosses that within a
couple of frames, so `prediction.ts` snaps and replays every pending input **every frame, for
as long as the player is hurt and moving.**

**And it cannot self-correct, because the client mirror never learns health.**
`set_player_state` takes only `x, y, vx, vy, grounded, fuel`; the TS `PlayerState` interface
has no health field; nothing sets one. The mirror's health is whatever it was constructed
with, forever. Health **is** on the wire — `codec.rs`'s per-player block carries it — it
simply never reaches the mirror.

SUSPECTED on magnitude, CONFIRMED on mechanism: the two call sites are unambiguous.

## The rule this violates, stated precisely

Not *"the client must know everything"*. The line is: **everything `apply_input` reads must be
identical on both sides.** Darkness is exempt because nothing predicts darkness. Health is
exempt **as a value** — until it feeds `speed_multiplier()` *inside* `apply_input`, at which
point it stops being exempt. That is this bug.

## Deliverable

Make the client compute the same multiplier the server does. That means the mirror must learn
health, which is a change to `set_player_state` and the `PlayerState` interface.

**Do not "fix" it by removing the multiplier from the server**, and do not widen
`RECONCILE_EPSILON_PX` — the epsilon is doing its job; it is reporting a real divergence.

## Tests

- **The instrument already exists.** `prediction.ts` counts `corrections`, `lastCorrectionPx`
  and `snaps`. Assert that a **hurt** player moving produces no more corrections than a
  healthy one — with the healthy case as the control, or "few corrections" passes for a
  client that never predicts at all.
- A unit test that client and server multipliers agree at several health values, pinned to
  `HEALTH_SPEED_MIN`.
- Falsify at the live binding site: put `1.0` back and the correction count goes up.

## ⚠ CHECK FIRST — T20.11 may already have done some of this

T20.11 (fall damage) was in flight when this was booked, and its working tree grew to include
**`client/src/net/prediction.ts`, `client/src/core/index.ts`, `client/src/render/feel-math.ts`
and both scenes** on top of eight Rust files — precisely the files this task names.

Two readings, and they want different responses:
- **Innocent:** T20.11 was told the landing-sound bug *"falls out of this one"*, because the
  impact speed `integrate` must return is the number that cue needs. `feel-math.ts` is where
  it lives, so client files are expected.
- **Overlap:** `prediction.ts` and `core/index.ts` are this task's own subject. T20.11 may
  have wired health into the mirror **without knowing this was booked.**

**Baseline, measured at `f6da974` so the comparison is airtight rather than re-derived later:**

| site | at `f6da974` |
|---|---|
| `game-wasm::apply_input` speed argument | literal **`1.0`** |
| `set_player_state` params | `id, x, y, vx, vy, grounded, fuel` — **7, no health** |
| TS `PlayerState` fields | `x, y, vx, vy, grounded, fuel, moveState` — **no health** |

**Read these three rows at the two named symbols. Never off a whole-file count.** Both files
are full of the word `health` for unrelated reasons, and the counts point in *opposite*
misleading directions:

- `client/src/core/index.ts` → `grep -c health` is **2**, both in a different interface and a
  damage-event `hits` array, **not** the mirror's `PlayerState`. A reader checking the count
  concludes the mirror already has health and drops a real finding.
- `crates/game-wasm/src/lib.rs` → `grep -c health` is **15**, every one of them elsewhere;
  `set_player_state` and the interface are clean. A reader checking the count raises a false
  alarm.

So the count talks you out of the finding in one file and into a phantom in the other. **Read
`set_player_state`'s parameter list and the `PlayerState` interface directly.** **A number that is *about* the thing is not
the thing** — the same invariant as reading a filtered listing as a population.

**And note `crates/game-wasm/src/lib.rs` holds BOTH sites** — `apply_input`'s literal `1.0`
and `set_player_state`. Any task plumbing something new through the wasm bridge has a
legitimate reason to be editing exactly that file, which is precisely what makes it the place
health gets wired in passing.

**So before starting, check two things:**
1. Does the client mirror now carry **health** (`set_player_state`, and the TS `PlayerState`
   interface)?
2. Does `game-wasm`'s `apply_input` still pass a literal **`1.0`** where the server passes
   `speed_multiplier()`?

**If both moved, this task is done or nearly so — close or re-scope it rather than
re-implementing.** **If only one moved, that is a half-fix and worse than neither**: the
divergence persists while looking addressed, and the correction counter would still climb.
Say which you found.
