# T20.07 — The flashlight is wired to nothing, and the new one is passive (v8)

Milestone: M20 · Depends on: nothing · Size: large — read the dead ends first

**This reverses a design `docs/72` §C13 specifies.** Today the flashlight *shrinks* ambient
sight and buys a cone; the wanted behaviour is the opposite. **Flag the conflict and
proceed** — the coordinator asked for the new behaviour explicitly, and this file records
what it overrides.

Wanted: *"when picked up, it increases your view/light radius by 50 % at night and makes the
heavy fog background 20 % more visible. It doesn't have to be the active item, just in the
inventory. It doesn't take energy."*

## Read first
- `crates/game-core/src/world/cycle.rs:83-93` — `fov_radius`, and `constants.rs:173-181`
- `client/src/render/lightmap-math.ts:42-50` — `fovRadius`, the **live** copy
- `client/src/render/weather-math.ts:181-183`, `client/src/render/weather.ts:138-151`

## The headline: the flashlight currently does nothing at all

Four separate "built and wired to nothing" defects sit on this path. **Fix them or the
change is invisible:**

1. **Six** production sites hardcode **`flashlightOn: false`** — not the two an earlier
   draft named: `GameScene.ts:1480`, `:1548`, **and `SandboxScene.ts:649, :796, :1071,
   :1102`**. **Both gating checks are in play**: `fog-visible.mjs` uses
   `openClient`+`enterBattle` so it exercises **GameScene**; `night-combat.mjs` uses
   `regenerate`/`setTime`/`fire` so it exercises the **sandbox**. Fix only the two
   GameScene sites and `night-combat` looks at four unchanged hardcodes.
   **And there is a trap behind that:** `night-combat` is one of the two survivors of the
   retired flake list (seven bare `waitForTimeout`s). A coder who changes night vision, sees
   it behave oddly, and reaches for the known-flake explanation **will be wrong, and the
   handoff's own material will help them be wrong.**
2. `FLAG.flashlight` (`client/src/net/codec.ts:300`) has **no production reader** — only
   two test references.
3. `collectLightSources` (`lightmap-math.ts:120-181`), where the cone and remote cones are
   built, has **no production caller** — `GameScene.ts:1497-1510` builds `lights` by hand.
   This is the same defect **T19.20** books for the hazard path; coordinate, do not
   duplicate. Note it already calls `fovRadius` internally (`lightmap-math.ts:130`), so if
   it is ever wired up it inherits the flashlight radius for free — and becomes a **seventh**
   site, whose `flashlightOn` comes from `WorldLights` rather than a hardcode.
4. `Connection.sendToggleFlashlight` has **no caller**; `GameScene.ts:837` binds `keydown-F`
   to `sendFire()`. `button::FLASHLIGHT` and `flashlight_pressed` have **no server
   consumer**. The only live route is `G` → `use_item`.

## Which side owns the radius: the client

`game_core::world::cycle::fov_radius` has **no production caller** — only the wasm bridge,
used by a test to pin the TS copy. The real radius is `lightmap-math.ts:42` (`fovRadius`),
called from `GameScene.ts:1480-1485` and `:1548-1553`. The server *does* own the fog
number: `vision_multiplier` quantised to a byte at `codec.rs:312`.

## Deliverable

- **Held anywhere in the inventory**, not toggled and not the active slot. `flashlight_on`
  changes meaning from "toggled on" to "carries one".
- **+50 % radius at night**, gated on `night > 0` — a new constant replacing
  `FLASHLIGHT_AMBIENT_MULT`'s 0.65. **Both copies move together**: `cycle.rs:83` and
  `lightmap-math.ts:42` are pinned to each other by `lightmap-math.test.ts:227-240`.
- **Fog veil 20 % more visible. Grow `fogVeilAlpha`'s argument — do not pre-scale
  `strength`.** An earlier draft offered both; the second is wrong. `weather.ts:142` stores
  `this.lastFogAlpha`, and `debug().fogStrength`/`fogAlpha` are **asserted** by
  `weather-visible.mjs:250,253` and read by `fog-visible.mjs:72,78`. Pre-scaling would make
  `fogStrength` mean "the effect's strength, discounted by a flashlight" — two meanings in
  one number — and those checks would silently start measuring something else.
- **"20 % more visible" is not a number yet — pick one and name a constant.**
  `FOG_SCREEN_ALPHA` is 0.8, so it could be `alpha × 0.8 = 0.64`, or `alpha − 0.2 = 0.6`, or
  a 20 % increase in *transmitted* light (`1 − a`: 0.2 → 0.24, i.e. alpha 0.76). **Three
  different pictures.** Choose, justify, and put it in `constants.rs` — the same discipline
  the radius bullet already applies.
- The client must learn who carries one. **The wire bit is free; the field behind it is
  not.** Bit 4 is written at `codec.rs:283` into the **live snapshot**, and the replay stores
  commands plus a header — **no snapshot bytes** — so redefining what the bit *means* costs
  the replay nothing. But `p.flashlight_on` is **hashed** (`world/mod.rs:3049`, inside
  `state_hash`'s per-player block). So:
  - **(a) Derive at the encode site only** — leave the field alone, write
    `p.inventory.has(FLASHLIGHT)` into bit 4. Hash unchanged, tag 7 still works, **no
    `REPLAY_VERSION` question at all.**
  - **(b) Change the field's meaning, or delete it** — changes the hashed value for anyone
    carrying a flashlight, so every recorded replay diverges at the first checkpoint after a
    pickup. **That is a real bump**, by the repo's own recorded rule: `replay.rs:44-64` says
    v3 was bumped because an old file *"would load, run, and diverge silently"*.

  **Take (b), and delete the field.** (a) leaves `flashlight_on` as a live latch nothing
  reads — a field that means two things, which is the rule this repo has paid for.
  **⚠ Do not carry T20.09's answer across.** That task adds a *command* and must **not**
  bump; this one changes *hashed state* and must. Same-sounding question, opposite answers.
- "Costs no energy" is **already true** — a Utility use touches neither battery nor stack.

## Tests that assert the opposite — these must be replaced, not deleted

- `lightmap-math.test.ts:63-68` — *"shrinks ambient sight when the flashlight is on"*,
  `on ≈ off × FLASHLIGHT_AMBIENT_MULT`. **Directly contradicts the new design.**
- `lightmap-math.test.ts:148-153` — *"it is a trade"*. Same.
- `:137-145` and `:157-170` — the cone and remote cones. **If the cone goes, decide
  deliberately**; it is a design change beyond the brief, so say so rather than deleting it
  in passing.
- `cycle.rs:199-215`; `combat.rs:1113-1126 the_flashlight_toggles_without_being_consumed`
  and `:1053`; `codec.rs:841,891,907,918`; `localInput-math.test.ts:34,52`.
- `replay.rs` tag 7 `ToggleFlashlight` — retiring the command is a `REPLAY_VERSION`
  decision (currently 4).

## Tests

- A carried flashlight widens the radius at night and **does nothing by day** — the control.
- The veil is measurably lighter with one held: **rendered pixels**, control region, control
  frame.
- **Falsify at the live binding site — and name which site, per check.** "Put
  `flashlightOn: false` back" is unfollowable with six candidates, and picking the wrong one
  is the M19 trap verbatim (*"seven falsifications proved nothing because they edited a path
  the test never used"*). Falsify a **GameScene** site for `fog-visible` and a **sandbox**
  site for `night-combat`, and say which you used.
- **Rebuild the wasm before trusting `lightmap-math.test.ts:227-247`.** That test is the
  only thing keeping the two `fov_radius` copies honest, and it compares TS against
  `coreFovRadius` — the **built** binary. Change the Rust without rebuilding and it goes red
  against a stale artifact, at which point the tempting move is to "fix" the TS back to the
  old formula. An instrument is only valid for the code it was built against.
