# T20.13 — Two rooms, and one of them never starts (v8)

Milestone: M20 · Depends on: nothing · Size: unknown — **diagnose before designing**

Reported: *"at the end of the game, if one player stays and votes to play another match, and
another one leaves and starts a new quick match, they both appear on the list. The replay
player gets a new match, but the player in the public lobby gets an empty screen — like a
new match does not start. But if I refresh the stuck page and start another quick match it
starts fine. Maybe the backend tries to start 2 matches at the same time and fails? There
should be like a queue for starting new matches."*

## Read first
- `crates/game-server/src/round.rs:105-113,168-181` — `restart_wins`, and when it resolves
- `crates/game-server/src/registry.rs:396-427` — `quick_match`
- `crates/game-server/src/room.rs:2497` — `restart`; `:213,260-268` — `started`/`has_started`

## What the code makes possible

- **The replay vote resolves only when the `Ended` window closes** — `round.rs:168-181`,
  gated on `phase_time_left() <= 0.0`, with `ENDED_SECONDS = 20.0`. Throughout that 20 s the
  room still has a world, so `has_started()` is **true**.
- `restart_wins` **ignores its `connected` argument** (`let _ = connected;`), so a **single**
  remaining "yes" restarts the round. On restart, `started` is set true again for the whole
  next round.
- `quick_match` skips any room where `e.private || e.handle.has_started() || e.humans >=
  max_players`. So the player who exits and hits Quick Match **cannot** rejoin the room they
  left — `create(scale, false)` mints a second room.
- Room #1 still holds the replaying player, so `empty_since` is `None` and `reap` never
  touches it. **Both rooms persist**, up to `MAX_ROOMS = 32`.
- The private case is unconditional: `e.private` alone makes quick match skip forever, so a
  private replay plus a quick match **always** yields two rooms.

## "They both appear on the list" is almost certainly not a second bug — do not chase it

Read the sentence grammatically: *"if one player stays and votes to play another match, and
another one leaves and starts a new quick match, **they** both appear on the list."* The
antecedent of *they* is *"one player… and another one"* — **two players, not two rooms**.
There are exactly two client-visible lists of players, the end-of-round `ResultsScreen` and
the Tab scoreboard, both fed from `this.scores`. The clause is most likely **describing the
setup** — both players finished the same match together, on the scoreboard he was looking at
when he pressed the buttons.

**This matters because the alternative reading is a trap.** There is no client-visible room
browser, and `crates/game-server/tests/lobby_state.rs:340 no_room_list_producer_survives` walks `src/` and fails
if any `room_list` emit exists — it was deliberately removed. A coder who reads "list" as a
room listing concludes one is missing and builds it, **pushing against a guard that exists
to stop exactly that.**

**⚠ REOPENED — the dismissal below was argued on the wrong path. Read this first.**

An earlier draft dismissed the roster reading like this: *"`player_leave` is broadcast on a
bare socket close and `dropRemote` does `scores.delete(id)`, so a departing player IS
removed."* That is true **and irrelevant**: it is the path where the **other** player leaves.
The reporter's path is the one where **you** leave and re-enter, and on that path:

`GameScene.ts` `scores` is a **constructor field initializer**, and Phaser runs the
constructor **once**. `create()` never clears it, SHUTDOWN never clears it, and the only
removal is per-id in `dropRemote`. The `lobby_state` handler **seeds rather than overwrites**
by its own comment and never removes a seat absent from the new roster.

**So: exit from results → quick match → the new match's Tab scoreboard and results screen
still list the previous room's players, with their old scores and deaths.** That is *"they
both appear on the list"*, literally, and it is a real defect on the exact path the report
describes. **Chase it.**

Second-order, crossing T20.04: `scores.get(this.me)?.skinId` is read at three sites, so a
re-entering player whose new seat id collides with a stale one renders the **previous
occupant's skin** until the next `lobby_state` lands.

*(The dismissal is kept above because the reasoning is instructive: a check that is correct
for one path and silently inapplicable to another is how this was missed.)*

## The one thing to find

**"The player in the public lobby gets an empty screen."** Two rooms existing is not by
   itself a hang. Find why the *second* room never starts a match, and why a **refresh** then
   works — that difference is the diagnosis. Suspects worth checking, none confirmed: the
   session→player mapping after `leave_room` + a fresh `quick_match` on the same socket
   (`SessionMap::insert` evicts by `*p != player`, `session.rs:140-151`); whether the new room
   ever reaches the seat count it waits for; whether a stale subscription leaves the client
   waiting for a `map_init` that went to the old room.

## Deliverable

**Diagnose first, and report the mechanism before changing anything.** The user's own guess
— *"maybe the backend tries to start 2 matches at the same time"* — is a hypothesis, not a
finding; treat it as one. If a start queue turns out to be the right shape, it should follow
from a measurement, not from the guess.

Also settle whether `restart_wins` ignoring `connected` is intended. A single voter
restarting a round for a room that everyone else has left is at least worth stating.

## Only four fields are cleared on re-entry, and about thirty are not

The in-flight diff nulls four fields in SHUTDOWN. **Everything in `GameScene` with a
`= value` initializer survives re-entry** — beyond `scores`: `phase`, `me`, `roundTime`,
`serverRoundTime`, `timeLeft`, `phaseEndsAt`, `health`, `heals`/`batteries`, `shieldOn`,
`poisoned`, `meAlive`, `slots`, `observed`, `joinCode`, `invOpen`/`scoreboardOpen`/
`selectedSlot`, `mapSeed`/`roundSeed`, `seq`/`acc`/`stepAcc`/`inputsSent`, `fuel`,
`teleportCharge`, and the `readonly` instances `fog`, `death`, `repeatFire`.
(`padViews`/`mapObjects` are safe — reassigned in `onMapInit`. `liveConn` is safe — MenuScene
sets a fresh one per handover.)

**Adding four lines to a hand-written teardown that already has seven is the defect, not the
fix** — "share the guard, or share the function". The durable shape is one
`resetForNewRound()` at the top of `create()`.

## The `?game=1` flag has the same defect, and its check is vacuous over it

The in-flight fix appends `TitleScene` to the **`?menu=1`** scene list. **`?game=1` still
returns `[GameScene]` alone**, and `GameScene` has two `scene.start('Title')` calls — the
results exit and the escape quit. `ScenePlugin.start` queues `stop(current)` then
`start(key)`, so a missing key leaves **no running scene**: a blank page.

And `escape-menu.mjs` reaches the game through `?e2e=1&game=1`, clicks `#escape-quit`, then
asserts `document.querySelector('canvas') !== null`. **Phaser's canvas element outlives every
scene, so that assertion passes on the blank page it was written to catch.** It has been
green over exactly this defect on the sibling flag.

Fix both flags — or better, make the invariant structural (any dev scene list containing
`GameScene` also contains `TitleScene`) and replace the canvas probe with an assertion that
`#start-game` came up.

## The reproduction harness already exists — use it, do not build a fourth

**`scripts/checks/lobby.mjs:353-388` is a reproduction harness for exactly this class of
bug**, and the earlier draft listed it only as something at risk. Its own comments say so:
*"Two seats, two rooms, one lobby — invisible to every assertion above"* and
*"indistinguishable on the roster, and still two rooms on the server"*. It pairs two
instruments — `namesOf(c)` (`:363-364`), `debug().scores` mapped to names, because *"who each
client can see is the thing that cannot be true across a room boundary"*, and `/healthz`'s
`rooms` count (`:381-386`) as the server-side counterpart.

And `:358-362` records **why the obvious instrument is wrong**: *"`debug().seed` is the local
core's seed, not the round's… an assertion on it passes for two clients in two rooms, which
is precisely the failure being hunted."* A pre-recorded instrument failure for this exact
bug shape.

**The measurement to run:** two clients, play to `Ended`, one presses Exit **on the results
screen** and then Quick Match, then read `debug()` on the stuck client and `/healthz`. That
is the Deliverable's diagnosis, and the harness for it is written.
