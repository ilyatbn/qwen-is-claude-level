# T20.12 — Hats and sunglasses (v8)

Milestone: M20 · Depends on: **T20.04** — do not start before it · Size: ~250 lines

Wanted: *"add new skin customizations: hats, sunglasses. Make a few each."*

## Read first
- `client/src/render/tombstoneTextures.ts:11-14,31,40,51` — **the closest precedent**
- `client/src/render/playerView.ts:149-192,230`
- `client/src/ui/skins.ts:13-20,37,62,73`, `client/src/scenes/SkinsScene.ts:124,150,181-217,224-244`

## Depends on T20.04 — and the reason that bites is not the one you would guess

The obvious justification is that `GameScene` hardcodes `new PlayerView(this, 0)`, so no
per-player appearance reaches the renderer. True, but the part that will actually cost you
is this: **`PlayerView` is destroyed and rebuilt repeatedly during a round.**
`GameScene.ts:1579-1584` destroys every remote absent from the sampled set and
`:1556-1560` reconstructs it, and its appearance fields are `private readonly`, set only in
the constructor, with **no setter**.

**Accessory ids added as constructor arguments inherit that exactly.** Whatever T20.04 lands
for re-reading the skin on rebuild, **T20.12 must extend to `hatId`/`glassesId` in the same
place** — and if T20.04 solves it by re-reading `scores.get(id)?.skinId` at the construction
site, then these ids must live in **the same map**, which is the map with three writers.
Otherwise accessories are correct on first draw and revert to bare-headed on the next
rebuild.

## There is no art, and none is available

- `assets/atlas/chars.json` holds 50 frames: 5 characters × 10 poses. No accessories.
- Kenney's `platformer-characters` pack has **no** hats, glasses, helmets, caps or crowns —
  those searches return only sounds.
- **`../sprite_packs` holds no character art** — it is `bushes`, `clouds`, `crystals`,
  `rocks`, `ruins`, terrain and sky only. **Not usable here.**

**So accessories are drawn procedurally**, and there are three working precedents.
`tombstoneTextures.ts` is the closest: canvas-drawn variants in an array keyed by wire id,
`tombstoneArt(id)` falling back to id 0, and a `draw()` helper that no-ops if the texture
exists. **Inherit its stated design rule** (`:11-14`): variants *"differ in **silhouette**
rather than in palette. A skin picker whose options differ only by colour is a picker with
one option."* At `PLAYER_W = 16` a hat is ~10 px wide — silhouette is everything.

## The wire already proves the pattern twice

`skin_id` **and** `tombstone_skin_id` are two cosmetic `u16`s the server carries and never
interprets (`state.rs:105-108`: *"the server never knows what it looks like"*), threaded
through join → room → `player_join`/`lobby_state` → replay. **`tombstone_skin_id` is the
precedent to copy.**

## RULING — new fields. The packing option's only advantage does not exist.

An earlier draft called this an open pick and said the clean option touches *"the versioned
replay binary"*. **That is false.** `grep -c tombstone crates/game-server/src/replay.rs`
returns **0**: `ReplayCommand::Join { name, skin_id }` (`replay.rs:89`, encoded `:460-468`)
carries `skin_id` and **not** `tombstone_skin_id`. So in the exact case this task points at
as its precedent, the repo has already decided that **a cosmetic id which cannot affect the
simulation does not enter the replay.**

The honest comparison is therefore:
- **New fields** — `room.rs`, `session.rs`, `events.rs`, client parse. **Not `replay.rs`,
  and no version bump.**
- **Packing** — nothing on the wire, but one field means two things, against a rule this
  project has paid for.

Packing was only ever attractive because of a cost that is not there. **Take the new
fields**, and follow `tombstone_skin_id` term for term — including its *absence* from the
replay.

(For completeness: packing would have been replay-transparent — `put_u16`/`c.u16()`
round-trip whatever bits are set. It is rejected on the field-means-two-things rule, not on
a wire problem.)

**No snapshot change either way — CONFIRMED.** `grep -n skin crates/game-server/src/codec.rs`
returns nothing. Appearance arrives once on join.

## Notes

- The offset arithmetic belongs beside **`spriteScale`, which is in `skins-math.ts:137`** —
  not in a `playerView-math.ts`. Put the two halves in different files and they drift.
  (`overshoot = 1.55` is `spriteScale`'s default parameter, so `playerView.ts:166` passes
  only two arguments.) Note `PlayerView.ANCHOR_Y` is **0.9** (`playerView.ts:123`), overridden
  from `skinDef.anchor.y` at `:160`; the 0.86 an earlier draft quoted is one skin's value in
  `skins.json`, not a number in the code.
- **Three tasks are now growing one signature.** `loadChoice(store, skinCount, stoneCount)`
  already takes two counts; T20.02 routes `MenuScene.identity()` through it, T20.04 needs the
  skin out of it, and this task adds two more counts. That is how a function ends up with
  five positional arguments — **pass a `Choice`-shaped object instead.**
  Good news: accessory counts come from procedural array lengths (like `TOMBSTONE_ART.length`),
  **not** an atlas, so `MenuScene` can get them synchronously with no atlas load.
- `setState` already calls `this.body.setFlipX(left)` — the accessory needs the same flip and
  a mirrored x if it is offset.
- The preview **must** go through `PlayerView` (§B12: rendering it any other way *"would make
  this screen advertise a character the game does not draw"*).
- `MenuScene.identity()` reads localStorage directly with `Number()`, bypassing `readId` —
  accessories added there inherit that bug. Route through the helper. (T20.02 touches the
  same line; coordinate.)
- `exposeDebugHandle()` is the browser check's surface; new pickers need new fields there or
  `skins.mjs` cannot see them.

## Tests

- Per §C2, an accessory needs a **rendered-pixel** assertion with a control — the same
  character **without** a hat — not a `debug()` field. `skins.mjs` already arrives through
  the menu button deliberately (§A39); extend it.
- Silhouettes are distinguishable: two hats must differ in rendered pixels, or the picker has
  one option.
- Persistence round-trips through `readId`'s `String(n) === raw` check, with junk refused.
- **Do not reach for an atlas frame that "reads as a hat".** `tombstoneTextures.ts:1-9`
  records that `verify-assets` now **rejects** the mistake that preceded it — decor frames
  that turned out to be 98 % opaque terrain tiles. Procedural art sidesteps that guard;
  borrowed art will meet it.
