# T21.13 — The restarted round never announces itself (v9)

Milestone: M21 · Depends on: nothing · Size: ~200 lines across
`crates/game-server/src/room.rs`, `crates/game-server/src/round.rs` and one browser check

**Reported from play by the coordinator**: *"i saw the match doesnt really end at 0
and like 10 seconds before i already see the menu for 'play again'. and after the
match restarts the timer has more time that was needed."*

Three symptoms were named. **Two of them have one cause and it is confirmed; the
third I could not reproduce and this file says so rather than inventing one.**

## Touch only

- `crates/game-server/src/room.rs`
- `crates/game-server/src/round.rs`
- `scripts/checks/rematch.mjs` (or a new check, registered in `scripts/e2e.mjs`)
- `client/src/ui/results-math.ts` and `client/src/ui/results-math.test.ts` — **doc
  and premise only**, see *Tests at risk*. No behaviour change is needed on the client.

## What was found

### Defect 1 — a restart changes no phase, so no `round_state` goes out

`docs/41` §3 states the contract twice: *"`round_state` is broadcast on every phase
change and once a second during `Playing` so a client that missed a transition
self-corrects"*, and *"majority … → new round on a new seed, scores reset to 0,
phase → `Warmup`"*.

The second round never sends that message.

- `world/mod.rs::set_phase` opens with `if self.phase == phase { return; }` — it has
  since T6.01 (`git show 4c831ef`), and the early return is before the
  `GameEvent::RoundState` push.
- A world is **born in `Warmup`**: the struct literal in `world/mod.rs::with_generator`
  sets `phase: RoundPhase::Warmup`.
- `room.rs::restart` builds its world with `World::with_generator` and then calls
  `world.set_phase(RoundPhase::Warmup)`. **Same phase, so it is a no-op.** Nothing
  between the two touches `phase` — `grep -rn "set_phase" crates/game-server/src/`
  returns seven call sites and only `room.rs::generate_world_task`'s `Lobby` is on
  the first-round path.

The first round is fine for a reason that is easy to miss: `room.rs::generate_world_task`
sets the fresh world to `Lobby` and drains, so `room.rs::begin_round`'s
`set_phase(Warmup)` is a **real** transition and does announce. `restart` does not go
through `begin_round` at all — it re-implements `seat_bots` + `set_phase(Warmup)`
inline, which is the *share the guard, or share the function* rule, and
`begin_round`'s own doc comment already asserts the invariant it does not hold:
*"Seat bots and enter `Warmup`. **The one place a round begins.**"*

**What the player sees.** `GameScene.ts` writes `this.phase` in exactly two places
(the `conn.on('round_state', …)` handler and `onWelcome`) and `this.phaseEndsAt` in
exactly one (that same handler); `resetForNewRound` only runs from `create()`, which
a server-side restart does not trigger. So for the whole `WARMUP_SECONDS` of every
restarted round the client still holds `phase = 'ended'` and the *previous* round's
`Ended` deadline:

- `results-math.ts::shouldShowResults` is phase-only, so `results.ts::ResultsScreen::update`
  keeps the **"Play again" panel on screen for ten seconds after the new round has
  already started** — and it was already up for the 20 s vote window, so the panel is
  continuously up for `ENDED_SECONDS + WARMUP_SECONDS` = 30 s with a live match
  running under the last ten.
- The top-right clock (`GameScene::refreshHud` → `hud.ts::Hud::update`) and the panel
  read the *same* number, `secondsUntil(this.phaseEndsAt, this.roundTime)`. With the
  shipped constants the stale deadline is `250 + 20 = 270` and the new world's round
  time is 0, so at the instant of the restart the clock jumps **0:00 → 4:30**, falls
  to 4:20 across the warmup, then drops to 4:00 when the `Playing` announcement
  finally lands. The strip banner (`scoreboard.ts::phaseBanner`) reads
  *"Round over — 4:30"* over the new map.

That is symptom **(c)** exactly — *"after the match restarts the timer has more time
that was needed"* — and it is the best available reading of symptom **(b)**: the
"play again" menu is on screen for ten seconds of a round that is already running.

### Defect 2 — the once-a-second re-broadcast dies permanently at the first restart

`round.rs::RoundController` holds `last_state_at: f32`, compared in `tick` against
`now = world.round_time`. It is initialised to `NEG_INFINITY` in `new` and assigned
in one place; `grep -rn "last_state_at" crates/game-server/src/` returns four lines
and **none of them is a reset**. The controller outlives every world — `grep -n
"self\.round\b" crates/game-server/src/room.rs` shows it is only ever borrowed,
never reassigned.

A restart hands the controller a world whose `round_time` is back at 0 while
`last_state_at` still holds round one's ≈ 249. `now - self.last_state_at >= ROUND_STATE_INTERVAL`
then needs `round_time >= 250.x`, and round two's `Playing` window *ends* at 250.0.
So round two emits **zero** periodic `round_state` messages, `last_state_at` is never
updated, and every later round is blocked the same way. It is not a shortened-round
artefact: round *N+1* always starts its clock at 0 while round *N* stopped
broadcasting at `WARMUP_SECONDS + round_seconds − ε`, so the condition can never be
met again at any `ROUND_SECONDS`.

**Count it at both ends**: the same trap sits on the other exit. `RoundOutcome::ToLobby`
→ `room.rs::return_to_lobby` drops the world, and the next match installs one whose
`round_time` is also 0. A reset written only into the `Restart` arm fixes one of the
two paths. The general statement is *the world's clock went backwards*, and that is
what the guard should say.

Consequences: `GameScene`'s `this.timeLeft` — the strip's `formatClock(this.timeLeft)`
and the instrument `scripts/checks/hud-timer.mjs` validates the rendered digits
against — freezes for the whole of round two. And the safety net `docs/41` §3 names in
so many words (*"so a client that missed a transition self-corrects"*) is gone from
round two onward: a client that misses the single `Playing` announcement now keeps the
results panel up for the **entire** round rather than for one second.

### Symptom (a) — NOT confirmed

*"the match doesnt really end at 0"*. I could not find a mechanism that makes the
server end late or the round-one clock disagree with it, and I am not going to assert
one:

- `world/mod.rs::phase_time_left` is `phase_started_at + d - round_time`, and the
  phase advance at the foot of `world/mod.rs::step` runs **after** `round_time += dt`
  with the pre-step phase latched, so `Playing → Ended` fires on the first tick at or
  past `phase_started_at + round_seconds`. Exact.
- In round one the panel and the clock are driven from one `phase` and one
  `phaseEndsAt`, written in one handler, so they cannot disagree by ten seconds.

What *is* true and may be what was being described: the top-right clock is a **phase**
clock, not a round clock, so the moment the round ends it re-arms at 0:20 and counts
the vote window down again — nothing on screen says the match is over except the
panel. And from round two the transition into the new round is announced by nothing at
all (defect 1). **Start here, and if a genuine late end shows up under a fix for 1 and
2, it is a separate task.**

## Do not

- **Do not route `restart` through `install_world`.** It looks like the tidy fix and it
  is not: `install_world` sets `world.tick = self.lobby_tick` (its comment explains why
  — one clock over a room's life, and a replay stamps commands with the room's tick).
  A restart currently resets `tick` to 0, every replay checkpoint hash for round two is
  computed against that, and `results-math.ts::phaseDeadline` has a branch that exists
  solely to survive it. Changing the tick baseline is a different task with different
  tests.
- **Do not make `set_phase` announce unconditionally.** `grep -rn "\.set_phase(" crates/
  --include=*.rs | wc -l` is 66, most of them test fixtures, several on a world already
  in that phase; an unconditional push emits duplicate transitions rather than fixing
  the missing one.

The shape that fits what is already here: give `restart`'s fresh world the `Lobby`
phase before it is installed and let `begin_round` make the real transition, so there
is one place a round begins and its doc comment becomes true.

## Tests

**1. The restart announces the round (`crates/game-server/tests/round.rs`).**
Drive a room to a majority restart and collect the events the restarting tick returns;
assert one is `GameEvent::RoundState { phase: Warmup, .. }`.
*Control (the collector can report absence):* the same collector over an ordinary
mid-warmup tick finds none. Without it, a collector that matched anything would pass.
*Control (the collector can report presence):* the same assertion over the **first**
round's start passes today — so a red subject and a green control locate the defect in
`restart` rather than in the instrument.
Note before writing: `grep -rn "RoundState" crates/ --include=*.rs` returns 14 lines
and **not one of them is in a test file**. Nothing in this repository has ever asserted
that this message is sent.

**2. The periodic re-broadcast survives a restart (`crates/game-server/tests/round.rs`).**
Count `RoundState` events across round one's `Playing` window and across round two's,
and assert the two counts agree within one. *That comparison is the control* — a bare
"round two emits some" is satisfied by the single transition message, which is emitted
today. Pin the expectation to `ROUND_STATE_INTERVAL`, not to a literal.
*Second control, the other exit:* the same count across a `ToLobby` → new-match cycle.
A fix written into the `Restart` arm alone leaves this one red.

**3. `RoundController::tick` when the clock goes backwards (unit, in `round.rs`).**
Feed one controller a world at `round_time` 250 and then a fresh world at 0, and assert
it broadcasts within `ROUND_STATE_INTERVAL` of the second world's start.
*Falsify at the live binding site:* the thing to break is `last_state_at`, the field
`tick` actually reads — not a constructor default and not a copy in the test.

**4. Rendered pixels — the panel is gone when the round restarts** (`docs/72` §C2;
extend `scripts/checks/rematch.mjs`, which already reaches a real restart with two real
clients, or add a check beside it). `.results-screen` existing in the DOM is not the
assertion — `round-end.mjs`'s header records that every DOM assertion passed while the
screen was invisible.
- *Subject:* within ~1 s of the server leaving `Ended`, a sampled patch over the region
  the panel occupies shows the game, and the element is gone by `round-end.mjs`'s
  `screenUp()` definition (laid out, not `display:none`, not transparent).
- *Control frame:* the **same patch during the vote window**, where the panel must be
  present. "The overlay is gone" otherwise passes for a page that never drew it.
- *Control region:* a patch away from the panel in both frames, so a frozen or black
  canvas is reported as a stalled box rather than as a pass.
- Take the restart moment from the **server** (`/healthz` or the round two `map_init`),
  never from a sleep timed against `ENDED_SECONDS` — *a wait hardcoded against a
  tunable is a test that expires.*

**5. Rendered pixels — the clock at the start of the restarted round.**
Read the digits out of `#hud-timer` (the DOM text, as `hud-timer.mjs` does) at a moment
when the server's new world is in `Warmup`, and assert they are `<= WARMUP_SECONDS + 2`.
Today it reads 4:30.
- *Control:* the identical assertion during **round one's** warmup, which passes now —
  so the check discriminates the restarted round from the first one rather than merely
  being true.
- *Both ends:* cross-check the rendered seconds against the server's own
  `round_state.time_left` for the new round, the way `hud-timer.mjs` already does.
  `ROUND_SECONDS - serverRoundTime` is **not** a valid instrument here; that derivation
  is short by the whole warmup and once reported a correct timer as 9 s fast.

**6. The strip clock keeps falling in round two.**
Sample `debug().timeLeft` several times across round two's `Playing` and assert it
falls. *Control:* the same series across round one, which falls today. A single pair is
satisfied by a number that moves once.

## Tests at risk

- `round.rs::round_state_is_rebroadcast_about_once_a_second_while_playing` — a *fresh*
  controller with `last_state_at = NEG_INFINITY`, so it cannot see defect 2 and will
  not move. It is the test that looks like it covers this area and does not; do not
  read it as coverage.
- `tests/round.rs::a_majority_restart_starts_a_new_round_on_a_new_seed_with_zeroed_scores`
  and `::without_a_majority_the_room_returns_to_lobby` — both green today and both
  green with the bug, because they assert on `room.phase()` and never on what was sent.
  If `restart` starts sharing `begin_round`, these are where a seat- or bot-handling
  regression shows up first.
- `client/src/ui/results-math.test.ts::phaseDeadline across a restart` — **its premise is
  wrong today.** Both cases feed `round_state { tick: 1, warmup, … }`, a message the
  server does not send on a restart, and being pure functions they pass forever. They
  become *true* once defect 1 is fixed. Keep them; fix the premise in the comment.
- `client/src/ui/results-math.ts::phaseDeadline`'s doc comment claims the stale anchor
  produced *"Warmup — 0:00 for the entire warmup of every round after the first"*. It
  cannot have: reaching that banner needs `phase === 'warmup'`, and no `round_state`
  arrives. Today's symptom is *"Round over — 4:30"*. Correct the comment rather than
  copying it forward — a comment claiming an invariant is an intention, not a
  measurement.
- `scripts/checks/rematch.mjs::started` waits for `["warmup","playing"]` within
  `ENDED_SECONDS + WARMUP_SECONDS + 20` s. It passes today only because `playing`
  eventually arrives, so it has never been able to tell a restart that announced itself
  from one that did not. Expect it to go green *sooner*, not differently — which is why
  the new assertions have to be added rather than relied on.
- `scripts/checks/hud-timer.mjs` validates the rendered digits against `debug().timeLeft`.
  It runs one round only, so it is unaffected; it is also the reason defect 2 has never
  been caught.
