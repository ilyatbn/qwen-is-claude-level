# T21.11C — The gun platform: the barrage and the magazine (v9)

Milestone: M21 · Parent: `T21.11-the-gun-platform.md` · Depends on: **T21.11B**
Size: ~200 lines

## What this ships

A mounted player can fire. The platform holds 500 rounds, fires 4 at a time at a
high rate, and when it is empty it is empty.

## Rulings

* **500 rounds per platform.** A map resource worth fighting over, not a free
  weapon three times a round. Pin `GUN_PLATFORM_AMMO` at the constant **with that
  reason in the doc comment** — `CLAUDE.md` records that pinning a test to a
  constant cannot detect the constant itself moving, so the reason is the only
  thing that survives.
* **When it is empty it is empty.** Dead scenery: it keeps its collision and its
  cover and does nothing. It does **not** despawn, and it is still mountable —
  the coordinator wants an item to refill it later, so leave the ammo a mutable
  world value rather than baking "empty forever" into the shape.
* **Ammo is per platform, not per occupant.** A second player finds what the first
  left.

## The barrage — decided here, as the parent requires

**Four bullets in one volley, spawned in the same tick across a fixed angular
fan.** Not a rapid sequence of four.

The reasons, in order:

1. The coordinator's words are *"a barrage of 4 bullets at a time"*. "At a time"
   is simultaneous.
2. The reference art has three barrels. A volley reads as barrels firing together;
   a sequence reads as one barrel cycling.
3. **It reuses the existing path exactly.** `world/mod.rs::fire_from_slot`'s
   `Delivery::Bullet` arm draws a muzzle angle and calls `projectiles.spawn`, then
   pushes a `ProjectileSpawn` event. Four of those in a loop is four ordinary
   bullets — same flight, same collision, same renderer, same `LOOK` entry. A
   sequence would need a queue that survives across ticks, which is new state,
   new hash content and a new way to diverge.

So: `GUN_PLATFORM_BARRAGE` (4) rounds per volley, `GUN_PLATFORM_FAN` for the
spread, `GUN_PLATFORM_COOLDOWN` between volleys. Every one in `constants.rs`.

**The bullets must be the existing projectile path, not a new one.** A second
bullet implementation is how two things that should look identical stop matching.

## Watch for

* **Ammo is world state and belongs in the state hash**, or a replay diverges the
  first time somebody fires. Find where the hash is folded and add it; then assert
  two worlds given the same inputs still agree after a volley.
* **The fan must be deterministic.** `muzzle_angle` draws from `self.rng`; four
  draws in a loop is fine and reproducible, a fixed fan needs no draws at all.
  Decide which and say so at the code. Either way: never `thread_rng`.
* **A volley at 3 rounds left fires 3, not 4, and does not go negative.** Decide
  and state whether a partial volley is allowed; `AddResult::Partial` is the
  precedent in this repo for "the caller must be told the leftover".
* **The muzzle is the platform's, not the player's.** A mounted player does not
  move, so the origin is the platform position — but the *aim* is still theirs.
* **Fire rate and the existing cooldown.** `try_fire_slot` gates on the player's
  `fire_ready_at`. A platform gun that used it would be throttled by whatever the
  player happens to be holding. Give the platform its own cooldown and say why at
  the code.

## Tests

* Firing consumes ammo, `GUN_PLATFORM_BARRAGE` at a time.
* At zero it stops firing, and the platform keeps its collision and stays
  mountable. **Control**: it fired before it ran out.
* Ammo is per platform — a second occupant finds it as the first left it.
* A volley spawns exactly `GUN_PLATFORM_BARRAGE` projectiles, and they are the
  same weapon id the registry names. **Count the thing at both ends.**
* Determinism: same seed, same inputs, same state hash after several volleys.
* **Rendered pixels** for a volley in flight, with a control frame before the
  trigger. Bullets have shipped invisible on this project before — `docs/72` §C2.
