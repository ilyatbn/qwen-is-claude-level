# T21.24 — An optional FPS counter in the options menu (v9)

Milestone: M21 · Depends on: T21.16 (the options panel) · Size: small

## Why

Asked for directly by the coordinator, after checking the High Quality fog in a
real browser and finding **the frame rate did not drop the way the headless
measurement claimed**:

> *"i checked the fog the fps doesnt really drop like you said. maybe its a wsl
> thing. ignore framerates for now. but add an optional fps counter if possible
> in the options menu."*

So this is an instrument for a person, not for a test. Its job is to let someone
decide for themselves whether an effect costs anything on **their** machine.

## Also: retire the frame-rate assertion

`scripts/checks/fog-shader.mjs` currently fails under `FPS_FLOOR`. **Delete that
assertion and the constant.** Keep the number in the `log` line — it is useful to
see — but nothing may fail on it.

The reason is not that the coordinator said to ignore it. It is that the number
is not trustworthy where it is measured: headless Chrome under WSL, on a box that
may be running a gate. *A gate that fails on a coin flip gates nothing* — and
this one would fail on a measurement we have direct evidence is wrong, which is
worse than a coin flip, because it would be believed.

## What to build

1. **A second setting**, beside `HIGH_QUALITY_KEY` in `client/src/ui/settings.ts`.
   Follow the existing shape exactly: a key, a module-level cache, a read in
   `loadSettings`, an `is…`/`set…` pair, and an `on…Change` subscription. Default
   **off**.
   - `loadSettings` must read it. T21.16 shipped a setting nothing loaded at
     boot, and its gate passed because nothing consumed the value yet.
2. **A second button** in `client/src/ui/optionsPanel.ts`, matching
   `#options-quality` in structure and in how it paints itself *from the setting*
   rather than from a local flag.
3. **The counter itself.** It must appear in the real game, not only the sandbox
   — the sandbox already has a debug HUD and that is not what was asked for.
   Phaser's `game.loop.actualFps` is the number. Put it somewhere it does not sit
   on top of the HUD, and make sure it does not follow the camera oddly.
   - Update it on a timer, not every frame: a counter that rewrites text 60 times
     a second is itself a cost, and a number flickering through three digits is
     unreadable. Round it.
4. Live, like the quality toggle: switching it on shows the counter **now**,
   without a reload.

## Tests

- **A browser check that the counter appears and disappears with the setting**,
  asserted on **rendered pixels** (`docs/72` §C2) with a control region — the
  text is a visible feature, and `debug()` saying it exists is the exact
  substitution this project keeps getting caught by. The control region is any
  part of the screen the counter does not occupy.
- The counter shows a **plausible** number. Not a pinned one — that is a machine
  measurement and pinning it would be a wait against a tunable by another name —
  but it must be a positive number under some sane ceiling, or a counter that
  renders `NaN` passes.
- The setting survives a reload (it is stored), and defaults off.
- Unit tests for the settings accessors, alongside the existing ones.

## Watch for

- **Do not gate this behind High Quality.** Someone comparing the two needs the
  counter in both, and that is the whole point of it.
- Check the counter is destroyed with the scene and its subscription
  unsubscribed, or each round leaks one and a setting flip wakes the dead ones —
  `WeatherLayer` had exactly this and it is worth copying its `destroy`.

## Touch only

`client/src/ui/settings.ts`, `client/src/ui/optionsPanel.ts`, the scene that owns
the game HUD, a new `scripts/checks/*.mjs` plus its line in `scripts/e2e.mjs`,
`scripts/checks/fog-shader.mjs` (to remove the assertion), and the client unit
test file for settings.

## Done when

```sh
npm --prefix client test -- --run && ./scripts/check.sh
```
