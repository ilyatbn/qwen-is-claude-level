# T21.16 — An options menu, and the High Quality toggle (v9)

Milestone: M21 · Depends on: nothing · Size: ~250 lines, **no shaders in this task**

Asked for by the coordinator: *"Might as well make it a toggle in an options menu."*

This is the foundation every shader task hangs off. It ships **no visual change**
on its own, and that is the point: the switch exists and is proven to persist and
to reach the renderer before anything starts reading it.

## Read first

- `client/src/ui/escapeMenu.ts` — there is already an **Options** button, wired to
  nothing and labelled *"Options — coming soon"*. That is the hole to fill.
- `client/src/ui/skins.ts` — how this project persists a player choice
  (`localStorage`, a `readId` that falls back on junk). **Follow it**; a second
  persistence idiom is a second thing to get wrong.
- `client/src/render/worldView.ts` — where the render layers are built, i.e. what
  has to read the setting.

## Deliverable

- An **Options** panel behind that button: DOM, screen-space, like every other
  overlay here (`docs/70` §A35). It is an overlay, **not a pause** — the round
  keeps running, exactly as the inventory and death screens do.
- One setting for now: **High Quality**, a boolean, default **off**.
- Persisted the way skins are. A junk or missing value reads as **off**.
- Readable from the renderer without a scene reaching into the DOM — a small
  accessor module, the way `assets.ts` exposes the manifest.

## Watch for

- **Default off is load-bearing.** Shaders only run on the better graphics mode;
  the whole reason this toggle exists is that some machines cannot run them. A
  default of on would make those machines worse the day the first shader lands.
- **The toggle must be live, not load-time**, or the player has to restart to see
  a change they just made. Decide what happens to already-built layers when it
  flips and say which at the code — rebuilding the world view is the blunt
  option and probably the right one.
- **Nothing may read it yet.** A setting with no consumer is fine here; a setting
  with a *half* consumer is not. Wire the plumbing, not the effects.
- `escapeMenu.test.ts` exists and asserts the current buttons. It will move.

## Tests

- The toggle persists across a reload. **Control**: a fresh profile reads off.
- Junk in storage reads as off rather than throwing.
- The renderer sees the value the menu set — counted at both ends, not by reading
  the same variable twice.
- The panel opens and closes, and **the round keeps running while it is open** —
  the assertion that it is an overlay and not a pause.
- **Rendered pixels** (`docs/72` §C2): flipping the toggle with nothing consuming
  it yet must change **nothing** on screen. That is this task's real claim, and
  the control frame is the same scene with the toggle untouched.

npm --prefix client test -- --run && ./scripts/check.sh
