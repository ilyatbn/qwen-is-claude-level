# T21.11B — The gun platform: mounting and the input lockout (v9)

Milestone: M21 · Parent: `T21.11-the-gun-platform.md` · Depends on: **T21.11A**
Size: ~250 lines. The hard part is not the timer, it is the two prediction seams.

## What this ships

Standing on a platform for `GUN_PLATFORM_MOUNT_TIME` mounts you. While mounted
you cannot move and cannot reach your inventory. Holding jump for the same
duration dismounts you. **No gun yet** — that is C. A mounted player in this task
is a player who has given up mobility for nothing, and every test here says so.

## Rulings carried down from the parent

* **Dismount is holding jump for a second. This supersedes right-click**, and the
  reason is integration risk, not taste: `main.ts` suppresses `contextmenu` on the
  canvas and `ui/inventory.ts` binds it on the panel root *and* on every tile, so a
  world-level right-click would have had three consumers to not break. A mounted
  player cannot move, so `BTN_JUMP` has no other meaning in that state.
* **Reuse the mount timer for the dismount.** One held-duration mechanism, two
  directions. A second counter is a second thing to get wrong.
* **One occupant at a time**, enforced server-side. Two players sharing a gun is a
  race nobody has thought about.
* **Mounting does not disturb the inventory.** It is untouched and simply
  unreachable until you get off.
* **A mounted player can be shot, and that is the point.** No mitigation, no
  i-frames, no damage reduction.

## The one rule, and why it is one rule

> *"Mounting makes the inventory inaccessible, including health."*

**Do not write a list of banned keys.** `Q` heal, `R` charge, item use and slot
select must all refuse *because the inventory is unreachable*, not because each
grew its own check. That is `CLAUDE.md`'s *derive, do not add a fourth flag*, and
it is also what makes a sixth slotless action added next milestone covered on the
day it lands.

`GameScene`'s §C9 comment says `Q` and `R` are slotless and already refuse in some
states. **Find that refusal and add this state to it** — `grep -n` for it rather
than trusting the line number in this sentence. *Share the guard, or share the
function.*

## ⚠ The two seams that will bite

### 1. `apply_input` runs on both sides, and it must know

This is T20.19 / T20.21 exactly, and `TASKS.md`'s M21 header calls it *"the
recurring hazard"*: `apply_input` runs on the server **and** in the client's
prediction dozens of times a frame, and its purity is what makes prediction
correct. **A movement lockout the client does not know about ships as
rubber-banding, not as an immobile player.**

T21.02 already built the seam to use: `PlayerState::move_mods` derives a
`MoveMods` that both sides read, and `SNAPSHOT_PLAYER_BYTES` carries a passive
byte **derived at the encode site** — nothing stored, nothing hashed,
`REPLAY_VERSION` unmoved. **Mounted is another bit in that byte.** Do not open a
side channel and do not add a stored field the hash has to learn about.

### 2. Movement must be refused where movement is decided

*"A mounted player's movement input moves nothing"* is a claim about
`apply_input`, not about the input reader. Refusing the keypress client-side
leaves the server moving anyone with a modified client. Refuse it in the shared
rule, and let both sides run the same one.

## Watch for

* **`underfoot` is already written** (T21.11A extracted it). Mount eligibility is
  that plus the mount timer — do not write a second geometry test.
* **Stepping off resets the timer**, the way `TELEPORT_CHARGE` does. Copy the
  charge machinery's shape from `world/teleport.rs`; it has the reset, the
  per-life reset and the cooldown already reasoned about.
* **Death while mounted must dismount.** `respawn` clears `TeleportState`; find
  everything it clears and decide, explicitly, whether mount state joins it. It
  does — a corpse holding a gun that a live player then cannot use is a
  soft-locked platform for the rest of the round.
* **Disconnect while mounted must free the platform** for the same reason.

## Tests

* Standing for the mount time mounts you; standing for less does not. **Both
  halves** — an absence needs a presence.
* A mounted player's movement input moves nothing. **Control**: the same input
  unmounted moves them, or the test passes against a game where nobody can move.
* `Q`, `R`, item use and slot select all refuse while mounted and work when not —
  and assert them **through the closed-inventory rule**, so a sixth slotless
  action is covered without a sixth test.
* Holding jump for the mount duration dismounts; a shorter hold does not. Both
  halves.
* A second player cannot mount an occupied platform, and can once the first
  leaves.
* Dying while mounted dismounts, and the platform is then mountable.
* A mounted player takes damage normally.
* **The prediction seam:** the client's `apply_input`, given a mounted player,
  produces the same position the server does. The wasm mirror is where this is
  asserted for T21.02 and T21.03 — follow those.
* **Rendered pixels** (`docs/72` §C2) for the mounted state, with a control frame
  of the same player unmounted. *A player who cannot tell they are mounted will
  think the game has frozen* — this is the assertion that stops that shipping.
