## Findings, most severe first

### F1 — `a_space_map_ships_none_of_the_furniture_that_needs_a_ground` is satisfied by a build with three of its five guards deleted

**What the code does.** `map/meta.rs::generate_full_with` gains five `if space` guards, each with
a written ruling and a "Reverse it by": `wind` → `0.0`, `teleport_pads` → `Vec::new()`,
`gun_platforms` → `Vec::new()`, `buried_slots` → `Vec::new()`, `decorations` → `Vec::new()`.

**What the test claims.** `meta.rs::a_space_map_ships_none_of_the_furniture_that_needs_a_ground`
asserts all five are empty/zero on a space map at every scale, with a landscape control over 8
seeds asserting each collection is non-empty *somewhere*.

**The concrete failure.** The control rules out "nothing anywhere has pads". It does **not** rule
out "the guard does nothing". Only two of the five are shown to change anything:

- `buried_slots` — the ruling states a measured pre-guard count (1 / 7 / 10 on Small/Medium/Large),
  so that guard is proven live.
- `wind` — a `range_f32` draw over ±`WIND_MAX`, which is ~never exactly `0.0`, so that guard is
  proven live by construction.

For the other three the commit's own justification argues the opposite way: *"the sampler would
have returned almost nothing anyway (T22.05B's task file predicted zero)"*. And this same commit
removed the full-width floor crust from `GenOutcome.surface` (`space::arena_surface`) — the crust
is precisely the ground `standing_candidates` + `stands_on_ground` were finding when they returned
six pads. So after the surface filter, deleting the `teleport_pads`, `gun_platforms` and
`decorations` guards may leave all three collections empty anyway, and this test stays green.
That is *falsify at the live binding site* failing on the remedy rather than on the bug — the same
miss `CLAUDE.md` records three times in one milestone.

The `decorations` ruling is the sharpest case because its comment makes the claim explicitly and
nothing measures it: *"Note this is a ruling, not a consequence of the surface filter: the
filtered surface still has seated points on asteroid tops, so without this guard a space map would
ship props standing on rocks."* That sentence is a number nobody wrote down.

**One-site fix.** Add, beside that test, one assertion per unproven guard that calls the
suppressed sampler directly on a real space map and asserts it returns something — e.g.
`choose_decorations(&map.mask, &map.meta.surface_points, seed, theme)` is non-empty, and
`standing_candidates(..)` over the arena surface yields ≥ 1 seated point. Each is a statement the
guard's ruling already makes in prose. **Ask the same question of that remedy**: if
`choose_decorations` returns empty on a space map, the assertion goes red and tells you the
*guard* is decoration — which is the answer either way, and that is what makes it a valid guard
rather than a second unfalsifiable claim. Live binding site: the three `if space` expressions in
`meta.rs::generate_full_with`, not the test.

### F2 — "and floats there" is present tense, and nothing in space floats yet

**What the comments claim.** `items/spawning.rs::place_initial`: *"R14 puts every non-player body
at gravity scale 0, so an item rests exactly where it is put — which makes where it is put the
entire placement rule rather than a starting height."* `items/spawning.rs::SpawnSchedule::tick_crates`:
*"It arrives in open air inside the rim instead, from the same picker the items use, **and floats
there**. That is the supply crate this mode has: a thing you fly to rather than a thing you run
under."*

**What the code does.** `items/world.rs::WorldItems::step` calls `integrate(map, &mut body, 1.0,
false, dt)` — a literal `1.0`, unconditionally — and the comment directly above it says so in as
many words: *"Today this body falls at standard gravity in every mode, exactly as
`GravityMode::scale`'s doc comment says it does."* R10 assigns that signature change to `T22.11`.

**The concrete failure.** Inputs: a space round, any seed. `tick_crates` picks a point in open air
mid-arena; `WorldItems::step` then accelerates it downward every tick until it rests on the rim's
inner floor at the bottom of the bowl. Same for every initial and periodic item. So the shipped
behaviour of this mode today is *all loot slides to the bottom of the ellipse* — which is better
than the pre-task behaviour (outside the rim entirely) but is not the behaviour the two comments
describe, and it is the behaviour a player would see first.

**Nothing reports it.** All three new tests — `crates_spawn_inside_the_arena_in_space`,
`initial_items_land_inside_the_arena_in_space`, `periodic_items_land_inside_the_arena_in_space` —
assert `geo.inside(it.pos)` at the spawn tick and never call `WorldItems::step`. "It was placed in
open air" is exactly the intention; where it *is* a second later is the effect.

**One-site fix.** Two edits, no behaviour change. (a) Reword both comments to the tense
`items/world.rs::step` already uses — *"will float once `T22.11` lands (R14); today it falls to
the rim's inner floor"*. (b) In `crates_spawn_inside_the_arena_in_space`, step the items for a
couple of seconds and assert what is true **today** (still inside the rim, non-zero `vel.y` at
least once), so that when `T22.11` zeroes the gravity scale the test has to be revisited rather
than silently continuing to pass.

### F3 — the falsification that stayed green: what the assertion should be

**The builder's report.** Planting `Map::random_body_site`'s space arm left the test green,
because the covering assertions are *"inside the arena"* and the filtered surface also satisfies
that. Confirmed from the code: plant `random_body_site`'s `Some(geo) =>` arm to return
`self.meta.surface_points[range_i32(..)]` instead of `space::random_open_space(..)` and
`initial_items_land_inside_the_arena_in_space` still passes — every point in
`map.meta.surface_points` on a space map is inside the rim by construction
(`space::arena_surface` filters on `geo.inside`) and none of them is on the crust line, which are
the only two things that test checks. `periodic_items_land_inside_the_arena_in_space` checks only
`geo.inside`, so it also stays green. (`crates_spawn_inside_the_arena_in_space` would probably go
red on its `aabb_overlaps_solid` clause, but that is the crate's 24 px box catching it by
accident, not the assertion naming the subject.)

**What the assertion should be, precisely.** The subject is *"an item in space is placed in open
space, not on a surface point"*, and the predicate for that already exists and is exported:

    // in initial_items_land_inside_the_arena_in_space and
    // periodic_items_land_inside_the_arena_in_space, per item:
    assert!(
        map.body_fits_at(Point::new(it.pos.x as i32, it.pos.y as i32)),
        "{scale:?}: item at {:?} is not open space — `random_body_site` returned a \
         surface point", it.pos
    );

**And the control that makes it a claim rather than a restatement**, which is the half
`CLAUDE.md` demands of the remedy itself. The above is only worth writing if the two pools are
genuinely disjoint, so assert that separately and once:

    // The two pools a space map has are disjoint, so `body_fits_at` above can
    // discriminate. Every surface point is either on an asteroid top (within
    // `a.r + PLAYER_H` of a rock centre) or on the rim's inner face (within
    // `thickness/2 + PLAYER_H` of the centreline) — both of which
    // `space::is_open_space` refuses.
    assert!(
        map.meta.surface_points.iter().all(|p| !map.body_fits_at(*p)),
        "a surface point passes `body_fits_at`, so asserting it on an item rules nothing out"
    );
    assert!(!map.meta.surface_points.is_empty());

That second block is itself falsifiable: if `is_open_space`'s rock-clearance term
(`< a.r as f32 + clear`, `clear = PLAYER_H`) or its rim term
(`distance_to_rim < thickness * 0.5 + body_h`) is ever loosened, it goes red and says so. That is
the difference between a guard and a second claim.

### F4 — `a_map_with_no_asteroids_has_no_standable_rock` explains itself with the thing this commit deleted

**What it claims.** Doc comment: *"a space map with no rocks at all still has a surface, **because
the floor crust is one**"*. Assert message: *"the crust is gone, so this fixture no longer
falsifies what it was built to"*.

**What the code does.** The test calls `space::generate_once`, whose `surface` field is now
`arena_surface(&mask, &geo)` — `extract_surface` filtered by `geo.inside`. The floor crust sits at
`y = h − FLOOR_CRUST − 1`, which is outside the ellipse and is exactly what the filter removes.
Its neighbour in the same file, `the_arena_surface_drops_everything_outside_the_rim`, asserts
`assert_ne!(p.y, crust_line)` over every point of that same value. So two tests one screen apart
disagree about what `GenOutcome.surface` contains, and the one that is wrong is the one a reader
reaches for. The surface is non-empty here because of the **rim's inner face**, not the crust.

**Why it matters beyond tidiness.** The message is the one that prints when the fixture stops
falsifying anything, and it will send the next reader to look for a crust filter that is already
there. This is M22-FOUND-DEFECTS' eleven-of-thirteen shape, freshly minted by the commit that
catalogued it.

**One-site fix.** Reword the doc and the message at
`space.rs::a_map_with_no_asteroids_has_no_standable_rock` to name the rim's inner face.

### F5 — §C5's respawn is silently off in space, and the module that owns it asserts its own fallback is dead code

**What the code does.** The live death path is `world/mod.rs::resolve_deaths` →
`player::respawn::choose_respawn_pad`, not `choose_respawn`. `choose_respawn_pad` iterates
`map.meta.teleport_pads`; this task rules that list empty in space, so `best` is `None` on every
death, the function takes its fallback, and `resolve_deaths` increments `self.respawn_fallbacks`
once per respawn for the whole round.

**What the comments claim.** `player/respawn.rs`'s module doc: *"Pads fix both by construction …
an assertion that the fallback is dead code is worth more than the fallback."*
`resolve_deaths`' comment: *"`pad` is `None` only if every pad failed re-validation, which
indestructible pads make unreachable."* `World::respawn_fallbacks`' whole purpose is to make that
condition impossible to miss. In space it is the normal case.

**Severity is contained, and I checked why:** `grep -rn respawn_fallbacks --include=*.rs crates/`
shows it is read by exactly one test (`a_real_round_never_respawns_off_a_pad`, which builds a
`World::new` on the default generator) and is explicitly excluded from the state hash. So nothing
observable breaks. But this is *share the guard, or share the function*: `choose_respawn_pad`'s
dead-code claim is now conditional on a guard in a different file, and neither site says so.

**One-site fix.** One sentence at `resolve_deaths`' `choice.pad.is_none()` branch and one in
`player/respawn.rs`'s module doc, naming space as the mode where the fallback is the path, and
pointing at `meta.rs::generate_full_with`'s pad guard. Optionally a test that a space round's
`respawn_fallbacks` equals the number of respawns — which turns the silent case into a stated one.

### F6 — `Map::space_geometry`'s discriminator does not survive the wire

**What the doc claims.** *"`Some` is the whole of 'this round is in space' for anything holding a
`&Map`"*, derived from `meta.asteroids`, *"sound in both directions"*.

**What is true on a networked client.** `GameCore::load_mask` does `let mut meta =
self.map.meta.clone()` — it re-derives `surface_points` (correctly, through
`gen::surface_for` keyed on the gravity-derived generator) and carries everything else over from
whatever the core last generated locally. `MapInit.asteroids` *is* on the wire
(`game-server/src/codec.rs`, and `client/src/net/codec.ts` decodes it into `MapInit.asteroids`) —
but `client/src/net/worldMirror.ts::applyMapInit` installs pads and platforms and **never installs
asteroids**, and `grep -rn "set_asteroids"` over the repo returns nothing. So the client's
`meta.asteroids` is the local generator's list, not the server's.

**Why it is latent and not live.** `grep -n "choose_respawn\|place_initial\|resample_surface\|
SpawnSchedule\|random_body_site\|body_fits_at" crates/game-wasm/src/lib.rs` returns **nothing** —
no client path calls any of the three new predicates. So today this is a landmine, not a bug.

**Why it is worth filing anyway.** This task made an un-mirrored `MapMeta` field the mode
discriminator for three predicates, which is R11's finding #1 arriving at a new site, and the
first client-side caller of `body_fits_at` (prediction, a client-side respawn preview, a sandbox
check) gets the wrong rocks silently. The doc already names the fix: *"A `MapMeta.generator` field
would be the more direct spelling."* File it as the follow-up, or add a `set_asteroids` beside
`set_teleport_pads` and call it from `applyMapInit`.

### F7 — `scripts/checks/minimap.mjs` gates on wall-clock sleeps

The new block is a genuine rendered-pixel check with both controls `docs/72` §C2 asks for: a
control **region** (`belowRows` must contain `air`) and a control **frame** (the same seed at
standard gravity, asserted *not* to be `solid` in the same rows). Colours are read from the
canvas' `ImageData`, not from `debug()`. That part is right, and it is the deliverable the task
file said was missing.

The problem is timing. `grep -c waitForTimeout scripts/checks/minimap.mjs` reports **8** — the new
code adds a 600 ms sleep after `regenerate` and two 700 ms sleeps after the two `place` calls, per
probe, for two probes. Nothing polls an observable. This is M22-FOUND-DEFECTS #12's shape
(`smoke-shader` deciding on a wall clock) in a brand-new check. It fails in the safe direction —
under load the reveal has not happened, `space.rim.every(c => 'dark')` fires and the check throws
a clear message rather than passing — but "throws under load" is still a gate that fails on how
busy the box is. Fix: replace each sleep with `page.waitForFunction` on the condition the sleep is
waiting for (the classified rim rows containing something other than `dark`).

Minor, same file: the control frame goes vacuous if `Minimap.draw`'s palette ever moves. The three
RGB triples are hardcoded as string literals (`'8,10,18'`, `'122,104,78'`, `'32,46,68'`); a palette
change classifies every cell as `other`, so `land.rim.includes('solid')` is false and the control
"passes". The space assertion throws first so the run is still red — but the control is not the
thing that caught it. Worth reading the colours out of the page the way the check already reads
`SPACE_RIM_THICKNESS` out of `constants()`.

### F8 — two early-returns guard on a value their space path never uses

`items/spawning.rs::place_initial` still opens with `let surface = &map.meta.surface_points; if
surface.is_empty() { return 0; }`, and `::resample_surface` with the same two lines returning
`None`. Neither function touches `surface` again on the space path — both now go through
`map.random_body_site`. Inert today (a space map's arena surface is non-empty, and
`surface_points` is a generation-time snapshot that never shrinks), so this is a note rather than
a bug: it is a guard keyed to something other than what it protects, of the kind that becomes a
bug the first time the two diverge. If it is kept, say at the code that it is the landscape
precondition.
