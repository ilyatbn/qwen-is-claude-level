# T22.04C — The local player's plume follows the thrust input, not velocity

Milestone: M22 · Depends on: **T22.04B** · Size: ~120 lines · Origin: the harsh review of T22.04
(F5), filed by T22.04B, 2026-09-23. **Not built yet.**

## The bug

T22.04 points every plume off **velocity** (`thrusterPlume-math.ts::plumeDir`), because the wire
carries one "thrusting" bit (bit 2) and no direction. That meets the rule as the task wrote it —
*opposite the way you travel* — and misses the physics whenever thrust and velocity disagree:

- **Braking.** Drifting right and thrusting left draws the plume on the **left**; the exhaust
  should be on the right, where the push comes from. Bots brake on purpose (`R5`).
- **Climbing out of a well.** A player thrusting *up* off an asteroid while still falling
  toward it draws the plume **above** — the wrong side, in `T22.11`'s core situation, which is
  exactly when a player is reading the plume to see whether the escape is working.

## Do

- **The local player** points the plume opposite the **thrust input** the mirror stepped with
  (the held direction, as `apply_input` saw it), not the body's velocity. The input is on the
  client; derive the direction from the same input the core consumed — not from the keyboard a
  second time, or it is a second spelling of the thrust vector (`R11`).
- **Remote players stay on velocity.** The input is not on the wire, and adding it is a new
  snapshot field for a cosmetic — `T22.04`'s reason for no bit 7 applies twice over.
- Idle, and thrust with no direction held (if that exists): keep T22.04's fallback.

## Tests

- **Braking, on rendered pixels:** drift one way, thrust the other, freeze; the plume is on the
  **velocity** side, against the hidden-plume control frame. This arm is red today — watch it
  fail first. Copy `scripts/checks/thrusters.mjs`'s `arm`.
- The DOWN/UP arms there must stay green (thrust and velocity agree in them).
- A remote's plume still follows velocity: `thrusters-match`'s remote arm stays green.
