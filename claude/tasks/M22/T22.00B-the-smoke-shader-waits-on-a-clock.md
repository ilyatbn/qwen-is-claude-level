# T22.00B — `smoke-shader` waits on a wall clock, so load decides whether it passes

Milestone: M22 · Depends on: nothing · Size: ~30 lines · Origin: two sightings during M22,
2026-09-20 and 2026-09-21

**Not M22 work, and it blocks M22's batch gates**, like `T22.00`. Numbered alongside it for
the same reason.

## The evidence, both sightings

| | in the 58-check suite | alone on the same tree |
|---|---|---|
| 2026-09-20 | `changed 1.0 % of its pixels in 300 ms against 0.0 % flat — it does not animate` | `animates (11.8 % against the flat cloud's 0.0 %)` |
| 2026-09-21 | `changed 0.5 % … against 0.0 % flat` | `animates (9.9 % against 0.0 %)` |

A factor of ten to twenty, both times. **Every other assertion in the check passed in the
suite runs too** — including `painted cloud against no cloud: 86.8`, so the cloud was drawn
and the shader was live. Only the animation claim failed. Neither commit that was in flight
touched any client or render file.

## The cause is named in `CLAUDE.md` already

```js
await sleep(300)
```

`scripts/checks/smoke-shader.mjs` grabs a frame, **sleeps 300 ms of wall clock**, grabs
another, and asserts the painted region changed more than the flat one. Under a loaded box the
browser renders fewer frames in those 300 ms, so the pixel delta collapses toward the flat
control and the assertion inverts.

That is *"a loaded box makes every wall-clock assertion a coin flip"*, and **a gate that fails
on a coin flip gates nothing.**

## Why neither of the two obvious remedies

- **`flaky: true`** deletes the only assertion in the repository that says the smoke shader
  *moves*. The check would still prove the cloud is *drawn* — which is the weaker half, and
  the half that was never in doubt.
- **`serial: true`** is an **unfalsified remedy**, and there is evidence against it: the
  `teleport` row directly above this one in `tasks/flaky-test.md` went red **in the serial
  tail, at load ~10**, so the tail is not an idle box. Proving `serial` cures it costs a full
  suite run per trial, which is the loop `CLAUDE.md` forbids.

`CLAUDE.md`'s own instruction for this case is the third option: *"Remove such an assertion or
fix its cause; do not weaken it."* **Fix the cause.**

## Deliverable

**Count rendered frames, do not wait on a clock.** Advance a fixed number of frames — hook
`requestAnimationFrame`, or poll a frame counter the page already exposes — and take the second
sample when that many have actually been drawn. Load then changes how *long* the check takes,
which is harmless, instead of changing what it *measures*, which is the bug.

Give the frame wait a generous timeout so a genuinely frozen shader still fails rather than
hanging, and make that failure say *"the page drew N frames in M s"* — distinguishing "the
shader does not animate" from "the box never rendered", which is the distinction this check
has been unable to make for two sightings.

## Check first, because it may not be alone
`grep -rn "sleep(" scripts/checks/ | wc -l`, then read every hit. Any other check that samples
two frames across a wall-clock gap has the same defect and should be listed in your report —
**do not fix them here**, one task, one file. `fire-shader.mjs`, `explosion-shader.mjs` and
`beams-shader.mjs` are the obvious neighbours.

## Tests

- **Run it before you start**, alone, and watch it **pass** — that is the problem, and say so.
- **Falsify the remedy under the condition that breaks the original**: reproduce the failure
  by loading the box (a few busy processes) and confirm the *old* form fails while the *new*
  form passes. If you cannot reproduce the load failure, say so plainly rather than declaring
  the fix good — an unreproduced bug with a confident fix is the shape this file exists to
  refuse.
- **Falsify at the live binding site**: disable the smoke shader's animation and confirm the
  new form goes red naming it. A frame-counting wait that passes for a frozen shader is worse
  than the clock.
