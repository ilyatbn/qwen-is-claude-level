## Findings

### F-1 — `Forces::falling`'s `zero_g` half is a behaviour change with zero assertions behind it (T22.11A, most severe)

**What the code does.** `physics/resolve.rs::Forces::falling` sets
`zero_g: matches!(mode, GravityMode::Space)`. Before this commit all four steppers passed a
literal `false` alongside the literal `1.0`. So R48's change has **two** halves, not one: the
scale (`1.0` → `mode.scale()`) and the contact rules (`false` → space-dependent). Inside
`integrate`, `forces.zero_g` selects between the R4 contact-from-below grounding probe *and*
switching `ground_snap` off, versus `ground_snap` on and no probe. For a non-player body that
reaches `items/world.rs::WorldItems::step` or `world/tombstones.rs::Tombstones::step`, the
result is written straight back out — `it.grounded = body.grounded`, `t.grounded = body.grounded`
— and `WorldItems::step` pushes onto `landed` off it, which is the §C7 "crate drawn in mid-air"
channel.

**What it claims.** `Forces::falling`'s doc: *"the contact rules have to move with the scale,
and spelling it out at four call sites is four chances to move one and not the other."* Each of
the four new tests repeats the framing in its own doc.

**The concrete failure.** All four tests measure **vertical displacement only**, from a body
placed at rest with zero velocity:

- `items/world.rs::a_dropped_item_falls_at_the_players_rate_in_every_gravity_mode` — `it.pos.y - start.y`
- `weapons/placed.rs::a_mine_falls_by_the_match_gravity_and_hangs_in_space` — `m.body.pos.y - 40.0`
- `world/tombstones.rs::a_grave_falls_by_the_match_gravity_and_floats_in_space` — `t.pos.y - 40.0`
- `world/animals.rs::an_animal_falls_by_the_match_gravity_and_not_at_all_in_space` — `b.body.pos.y - 40.0`

In `Space` the body has `vel == ZERO` and `gravity_scale == 0.0`, so it does not move and the
`grounded` probe answers `false` under **either** value of `zero_g`. The three `precondition`
asserts are `!grounded`, which is also satisfied either way. I grepped every occurrence of
`GravityMode::Space` across `items/`, `weapons/placed.rs`, `world/tombstones.rs` and
`world/animals.rs` at `c401def` — eleven lines, seven of them in `items/spawning.rs` — and not
one of them reads `grounded`. Nothing in the tree asserts the contact half.

Inputs → wrong outcome: set `zero_g: false` in `Forces::falling`. A dropped weapon drifting
sideways onto an asteroid top in space has `vel.y == 0.0` exactly, `move_y` returns at
`dy == 0.0` before probing, nothing grounds it, `WorldItems::step` re-integrates it every tick
for the rest of the round and never pushes it onto `landed` — a crate that is visibly at rest
and that every observer is told is still moving. The suite stays green.

**One-site fix.** Add a fourth arm to
`items/world.rs::a_dropped_item_falls_at_the_players_rate_in_every_gravity_mode`: spawn an item
in `Space` with a purely horizontal `vel`, step it into a rock, assert `it.grounded`, with the
same item in open air as the presence/absence control.

**How the fix could fail.** If the fixture gives the item any downward velocity at all, `move_y`
grounds it on the ordinary path and the assertion passes with `zero_g: false` too — it would
then be testing `move_y`, not the R4 branch. The fixture must hold `vel.y == 0.0` exactly, and
the control arm (same item, open space, not grounded) is what says the probe is discriminating
rather than always-true.

### F-2 — the nominated control pair is one control, and the second half cannot see this refactor at all (T22.11A)

**What it claims.** Commit message: *"Controls: `a_resting_body_is_bit_identical_after_600_ticks`
and the golden table both pass untouched."* The task file and R45 say the same.

**What the code does.** `crates/game-core/tests/golden.rs` hashes map masks from
`generate_terrain_with` / `generate_with` — its own module doc calls it *"golden mask hashes"*
and `cases()` iterates seeds × scales × generators. `integrate` cannot move a map mask. So
"the golden table did not move" is true and is evidence of nothing about this commit.

That leaves exactly one cross-build bit-identity anchor:
`resolve::a_resting_body_is_bit_identical_after_600_ticks` — one body, flat floor, standard
gravity, settled, peak `vel.y` of `GRAVITY * SIM_DT` ≈ 23 px/s, never sub-stepping, never
airborne. Every other determinism assertion I found compares **the same build against itself**
and is structurally incapable of detecting a refactor that changed physics:
`movement_scenarios::the_same_inputs_from_the_same_state_are_byte_identical_every_time`,
`movement_scenarios::replaying_from_a_midpoint_reaches_the_same_state_as_running_straight_through`,
`world_step::the_same_seed_and_inputs_give_the_same_state_hash_after_1000_ticks`, and the
`delivery.rs` `state_hash` pair. There is no stored golden of world state.

**Paths that changed shape with nothing pinning them across builds:** the sub-stepping path
(`substeps` fires above 1 px/tick; the resting body never reaches it), `clamp_to_world`, the
knockback path (`weapons/explode.rs` and `weapons/melee.rs` write `body.vel` outside
`integrate`), wings at `gravity_scale == 0.0` under `Standard`, and the jetpack.

**The honest half, and it lowers the severity.** Reading the code, the player path *is*
bit-identical. The new line is `body.vel += forces.accel * dt` with `accel == Vec2::ZERO` at
every construction site, i.e. `x + 0.0`, which is exact for every finite float **except**
`-0.0`, which becomes `+0.0`. I checked whether that sign can matter: `move_x` and `move_y`
both open with `if dx == 0.0 { return }` (and `-0.0 == 0.0`), and grep for `signum` /
`is_sign_negative` on a velocity across `physics/`, `player/` and `items/world.rs` returns
nothing. The `max_speed` branch is `None` everywhere and dead. So the risk is low and the
*evidence* is thin, which is the finding.

**One-site fix.** No code change. Strike "and the golden table" from the control claim wherever
it appears (commit message is immutable; `M22-RULINGS` R10 and R45 are not), and record in R45
which paths were **not** pinned, so `T22.11B` does not inherit a belief that "bit-identical"
was measured broadly. The cheap real control, if one is wanted, is a new
`resolve::a_falling_body_is_bit_identical_through_the_substep_path` with a literal expected
position — but note that is a golden of this build, so it proves nothing about the *previous*
build and must be labelled as forward protection only.

**How that could fail.** A literal-position golden written today is pinned to today's code, so
it cannot retroactively confirm T22.11A. Only a run against `876cb9d^` can, which is
Deferred #2's neighbour and belongs to whoever next has the box.

### F-3 — T22.05C's F2 assertion moves with the constant it names, and its comment says it does not (T22.05C)

**What the code does.** In `items/spawning.rs::crates_spawn_inside_the_arena_in_space`:

```rust
assert_eq!(
    space_moved == 0,
    GravityMode::Space.scale() == 0.0,
    ...
);
```

**What it claims.** The comment directly above: *"The assertion is pinned to
`GravityMode::Space.scale()` rather than to 'did not move', so it reports the mechanism coming
apart in **either** direction — a stepper that stops reading the mode, or a scale that stops
being zero."* The twin comment at `SpawnSchedule::tick_crates` repeats it.

**The concrete failure.** Plant `GravityMode::Space.scale()` 0.0 → 0.5. RHS becomes `false`.
Crates then fall, so `space_moved > 0` and LHS is `false` too. `assert_eq!(false, false)`
**passes.** This is precisely CLAUDE.md's measured `ITEM_SPAWN_INTERVAL` shape: the assertion
moves with the constant, so it cannot report the constant. The first direction the comment
claims is real (revert `WorldItems::step` to a literal `1.0` and LHS goes false while RHS stays
true → red). The second is not.

The repository is still covered — `constants.rs::every_gravity_mode_has_a_multiplier` asserts
`GravityMode::Space.scale() == 0.0` directly, with its own message about not restoring standard
gravity. So this is a **wrong sentence beside working code**, not a coverage hole. That is
exactly the class `M22-FOUND-DEFECTS` catalogues eleven of, written into the commit that was
supposed to be closing them.

**One-site fix.** Split the biconditional: `assert_eq!(space_moved, 0, ...)` for the effect, and
if a local pin is wanted, `assert_eq!(GravityMode::Space.scale(), 0.0)` above it as its own
line. Then delete the "either direction" clause from both comments, or narrow it to the one
direction that holds.

**How the fix could fail.** `assert_eq!(space_moved, 0)` on its own is an absence assertion —
satisfied by a stepper that moves nothing. It keeps its presence control, `ctl_moved > 0` on the
same 60 crates at `Standard`, which is already there and already correct. Do not drop it.

### F-4 — F3's addition to `periodic_items_land_inside_the_arena_in_space` cannot run under the plant it was written for (T22.05C)

**What the code does.** The new `body_fits_at` assertion sits **inside** `for it in ...`.
`assert!(seen > 0, "no periodic items spawned at all")` follows the loop.

**What it claims.** The comment beside it: *"The same F3 assertion, and here it names a failure
the count guard below would otherwise report as 'nothing spawned'."*

**The concrete failure.** Trace the plant the review named — `Map::random_body_site`'s space arm
drawing from `map.meta.surface_points`. `items/spawning.rs::resample_surface` is what periodic
spawns go through, and it does:

```rust
let Some(p) = map.random_body_site(rng) else { continue };
if !map.body_fits_at(p) { continue; }
```

Every surface point fails `body_fits_at` — which is exactly what the new
`the_two_pools_a_space_map_has_are_disjoint` proves. So all `PERIODIC_ATTEMPTS` are rejected,
`resample_surface` returns `None`, no periodic item ever spawns, `seen` stays 0, **the loop body
never executes**, and the test dies on `seen > 0` with "no periodic items spawned at all" — the
same wrong message, unchanged. The new assertion is dead under the one input it was added for.

The builder's own commit message half-says this (*"it dies on its own `seen > 0`, which names
the wrong thing, so that test got the assertion too"*), but the remedy does not follow from the
diagnosis: adding an assertion behind a guard that fires first changes nothing.

**Contrast, and this half works.** `initial_items_land_inside_the_arena_in_space` *does* improve,
because `items/spawning.rs::place_initial` has no `body_fits_at` re-check — it calls
`random_body_site` and accepts the point — so the planted surface points are actually placed, the
loop runs, and the new assertion fires naming the subject. That is a real fix and I am not
disputing it.

**One-site fix.** The defect is the guard's message, not the missing assertion. Replace
`assert!(seen > 0, "no periodic items spawned at all")` with something that separates the two
causes — e.g. count schedule firings and successful placements independently, and report
"the schedule fired N times and `resample_surface` rejected every draw" distinctly from
"the schedule never fired".

**How the fix could fail.** If the new guard calls `resample_surface` itself to get its number,
it becomes a restatement of the function under test rather than an observation of the schedule.
It has to instrument the *schedule*'s two stages, or it is the same defect in a second spelling.

### F-5 — `Forces::gravity` has no production caller, and its doc says it is what every caller passes (T22.11A)

**What it claims.** `Forces::gravity`'s doc: *"This is what every caller that used to pass a bare
`f32` passes now."*

**What the code does.** Every use of `Forces::gravity` at `c401def` is inside
`#[cfg(test)] mod tests` in `physics/resolve.rs`. The callers that used to pass a bare `f32` are
the four steppers — now `Forces::falling(gravity)` — and `player::apply_input`, which builds a
struct literal because R10 forbids forwarding a partly-overwritten `Forces`. **Zero** of them
pass `Forces::gravity`. CLAUDE.md: *"grep for the production callers of anything you build; a
test calling the function is not a caller."*

**One-site fix.** One sentence in the doc: say it is the fixture constructor, and name
`Forces::falling` and `apply_input`'s literal as the production spellings. Do not change the
code — R10 explicitly rejects the alternative.

**How the fix could fail.** It cannot; it is a sentence. But note that `Forces::gravity` being
test-only is also *why* the `max_speed` plants in R50 had to be done by editing it — the plant
reached only tests, which is a second reason R50's conclusion is right.

### F-6 — R14's `Animals::tick` row is unimplemented and now has no owner (coordinator item)

**What the ruling says.** R14's table: `world/animals.rs::Animals::tick` → **"no animals at all
in space"**, and *"this also answers the `birds.rs` row of `T22.05B`'s table."*

**What the code does.** `world/mod.rs::step_animals` passes `playing` as `active` with no mode
test. Grep for `Space` / `Generator` in `world/animals.rs` returns only the new test and one

suppresses either in space.

**What T22.11A did with it.** `an_animal_falls_by_the_match_gravity_and_not_at_all_in_space`'s

spiders spawn on the rim and asteroid tops in a vacuum and, with `gravity_scale == 0.0`, hang

**One-site fix.** A coordinator decision, not a code change by a builder: either give the row an
owner (a one-line gate in `World::step_animals` keyed on the generator, plus the same for birds)
or amend R14 to say animals stay and why. Either is one commit.

**How that could fail.** A gate on `self.gravity == Space` rather than on the generator would
desync from `MapGenerator::Space` if the two ever come apart — R15 says the generator is
*derived* from the mode, so key it to the same thing R15 keys.

## What I checked and found clean

Do not redo these.

- **No test was removed.** `tests/movement_scenarios.rs`: 21 `#[test]` before, 21 after, and the
  sorted `fn` name lists `diff` identically. `tests/delivery.rs`: 16 and 16, likewise identical.
  The 313-line churn in `movement_scenarios.rs` is entirely the `PLAIN_STEP` / `step_under`
  fixture replacing repeated argument lists.
- **Both ruled counts.** `pub fn integrate(map: &Map, body: &mut Body, forces: Forces, dt: f32)`
  — four. `apply_input` — eight named parameters, read out in full. R44 and R10's "that is a
  finding" conditions are both met.
- **`grep -c 'too_many_arguments' crates/game-core/src/player/mod.rs` → 1.** The Done-when
  expected 0, which R51 rules cannot hold at eight parameters. The builder reported it rather
  than gaming it, and `MovementState::step` correctly *lost* its own `#[allow]` when it dropped
  to six parameters.
- **R45's `Default` prohibition, in substance.** No `impl Default`, no `#[derive(Default)]`, no
  `..Default::default()` on `Forces`, `Env` or `MoveStep`. Every occurrence of the word in
  `resolve.rs` and `player/mod.rs` is prose explaining the absence. On the harder question — is
  a named constructor a `Default` wearing a name — the answer is *mostly yes, honoured*:
  `Env::field_free` is reachable by a caller who does not know what to pass, and
  `movement_scenarios.rs::step_under(gravity)` is a fixture generator that will hand a future
  `Space` test a field-free world. But `player/space.rs::plain`'s doc **states the hole in as
  many words** — *"it is the thing these 20 tests cannot see… every assertion below stays green
  for a build in which `Forces::accel` is never read"* — and both production sites carry a
  comment saying `field_free` is a claim that is true today and is the line `T22.11B` changes.
  That is the substance R45 asked for, not the spelling.
- **Every `Forces`/`Env`/`MoveStep` construction site**, enumerated at `c401def`: two production
  `Env::field_free` (`world/mod.rs::World::apply_inputs`, `game-wasm/src/lib.rs::GameCore::apply_input`),
  four production `Forces::falling` (the four steppers), one production struct literal
