# T22.00F — Two server assertions that failed under load

Found by T22.00E's after-loop (06ac11d, 2026-09-27; `gate-t2200e-*.txt`), at 1-min load up to ~96. Not the
handshake family — these assert **what the server did**, not timing, so each is a candidate real bug.

## Do
- **`checksum.rs`: mask mismatch at seq 143 (1/130).** Two clients disagreeing on the carved mask is the determinism
  guarantee the whole project rests on. Reproduce under the same load loop, capture both masks + the carve log at the
  mismatch, and name the cause: a real divergence (order of carves applied, a carve landing in a different tick, a
  float path), or the test reading one side mid-update. Fix the cause; a test-side read race gets fixed in the test
  with the proof that it is one.
- **`in_progress.rs`: `player_join` announced for a refused joiner (1/130).** A refused joiner must never be announced
  to the room. Find the ordering that lets it happen (announce before the refusal decision? a join racing the
  match start?) and fix it at the server.
- Also measure and record, without fixing unless the cause is a server bug: `integration.rs` inventory count 19/130,
  `checksum.rs` ready-window carve count 3/130 — are these timing budgets under load (name the budget and the
  measured wait) or behaviour?
- Each fix gets a test that goes red under a plant of the bug.

`crates/game-server/**`, `crates/game-core/**` (only if the divergence is there — say so), `tasks/`

## As-built (builder, 2026-09-27)
Instrumented first (`T2200F_DIAG` prints at each assertion), then the loaded loop (`gate-t2200f-{before,inv,after}.txt`:
the `integration`/`in_progress`/`checksum` binaries, 4 copies each × 12 rounds beside 12 spinners, load to ~84).
- **Mask mismatch — a test-side read race, not game-core.** Reproduced once (`gate-t2200f-inv.txt`): `server_seq 144
  a1 145 a2 145 above1 1 above2 1 filtered_matches_server true`. The server was read, then the inboxes — which by
  then held one more carve (a loaded room still draining fires). Cut at the server's sequence the clients matched it
  bit for bit. Fix in the test: `checksum.rs::client_hash_at` (replay ≤ `server_seq`), used by both mask-vs-server
  comparisons. New `the_comparison_is_cut_at_the_server_s_sequence` forces the carve after the read; plant (uncut
  replay) red: *"compared past the server's sequence 0 (inbox reaches 1)"*. **Determinism is not in question.**
- **Refused joiner "announced" — test-side.** The failing read was `joins_before 0, joins_after 1`: the room's one
  bot (`bot_count: 1`) is announced in the same room-loop pass as `map_init`, after it, and the total was read the
  instant `map_init` landed. A bo announce would have read 2 against 1. Now counted by name (`"bo"` → 0) with a
  presence control (the bot's `player_join` arrives). Plant (server emits `player_join{name:"bo"}` before refusing):
  red, payloads listed.
- **Inventory 2-vs-1 — a server bug, fixed.** Both payloads bo's own, identical, same tick, no pickup. `session.rs::seat`
  sends `welcome` and *then* reads the world for the joiner's inventory and item/grave/weather catch-up; a start
  pressed on `welcome` gave that read a world, so the joiner got everything the match-start broadcast had already
  sent. Both reads now gated on the `join_info` snapshot `welcome` described (`map_bytes.is_some()`). The test now
  bounds inventories by `1 + own pickups/deaths` seen on the wire. Before 33/48, after 0/48.
- **Ready-window carve count (7–8 < 10):** 1/48 before, 0/48 after; not a server behaviour we can see — the count is
  taken after a 400 ms quiet settle (8 × 50 ms) that a loaded room can stall through. Left asserted; its failure
  message now also reports the count 3 s later and the server's `carve_seq`, so the next sighting names itself.
- Totals, same loop: before 34 failing tests in 144 binary runs; after **0 in 144**.
