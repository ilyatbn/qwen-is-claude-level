Milestone: M22 · From the traced review of T22.10F (`1ed96a3..0587320`) · Coordinator ruling, recorded below.

## The defect
The review classified every counted correction in `breach-vortex` and `radiation-match` (6 page-runs): **80 "ack 0"**
— the server stepping a body before any input had reached it (worst 20.9 px); **10 "startup trim"** — the client's
first frame sent 14 inputs, the jitter buffer dropped 11 (worst 63.7 px); 9 snapshot rounding (≤ 2 px); no stand-in
mismatch. Elsewhere real stand-in mismatches (a client holding JUMP stood in against a server stand-in of 0; 18–20 px),
because the server began claiming seqs at the first input's arrival **with zero lead**: R89's jitter buffer was never
built, so any input a tick late was a stand-in. The review also planted "a stand-in steps against a released previous
input" and nothing went red, and saw three check reds at HEAD: `breach-vortex`'s pull (a trim mid-pull, 6.44 px),
`thrusters-match`'s after-bell jump (6.26 px vs 4), `radiation-match`'s pixel control (6.7 / 7.2).

## Ruled (coordinator)
1. Server: the expected seq starts at newest − `INPUT_BACKLOG_TARGET` on the first input and after any trim; no
   stand-in for a player who has never sent an input (pick the behaviour the client predicts; no hover mid-round —
   spawn-before-first-input is the only exempt window, bounded). Re-measure `teleport`'s stand-in rate.
2. Client: the fixed-step clock's first frame elapses 0. Predictor: "ack 0 while inputs pending" and "ack advanced more
   seqs than server ticks since the last snapshot (a trim)" are hitch events, out of the maxima, each with a vitest.
3. Test: a held JUMP stood in through silence jumps exactly once; plant red.
4. Re-run the three reds 3× each; attribute any still red from the log, never widen a bound.
5. Wire precision unchanged (rounding ≤ ~2.7 px, not the regression) — a candidate follow-up.
