# T22.04 — Thrusters: the energy cost and the burst you can see

Milestone: M22 · Depends on: **T22.03** · Size: ~200 lines · Origin: new, 2026-09-18

Asked for: *"moving in space requires using energy, from the spacesuits thrusters, so add a
cool animation to it so that if i move down, you can see a burst of energy coming from above
the player."*

## The one rule the animation has to get right

**The plume fires from the side opposite the direction you travel.** Move down, the burst is
*above* you. That is Newton and it is also what the owner asked for in as many words. Getting
it backwards is the kind of thing that looks fine in a still and wrong in motion, so this is
asserted on rendered pixels with the player's velocity as the control.

## Read first
- `client/src/render/ordnanceFx.ts` and `client/src/render/shaders.ts` — how T21.17 plumbed
  effects, and what a High-Quality-off fallback has to look like
- `client/src/render/playerView.ts` — `setState`, and how wings and boots are toggled per frame
  off snapshot bits rather than rebuilt
- `client/src/ui/jetpackReadout-math.ts` — the fuel readout this shares a resource with
- T21.36 — *"fire you can see"*: flames covered **85–108** of 192 burn-circle points with High
  Quality off. (**108 is the top of a measured range**, not the reading — `fire-shader.mjs`'s
  own comment says 85–108. And `render/ordnance-state.ts::LOOK.flame` describes the same
  measurement as *"unpainted"*, which inverts it: **report that comment as a defect, do not
  fix it here.**) The lesson is that the two render paths need the same assertion, not the
  same code.

## The thruster is now the basis for something else

`T22.11` gives every asteroid a pull at levels 1–5 and defines *"harder to escape"* against
**this** task's delta-v. So the fuel number chosen here sets whether level 5 is a challenge or
a death sentence, and `T22.11` asserts the ceiling — maximum well against maximum thrust —
because a well nobody can escape kills with no cause on screen. **Pick the number knowing it is
load-bearing, and put the basis in the doc comment.**

## Deliverable

- **The cost**, in `T22.03`'s fuel economy: thrusting consumes, idling does not. One constant,
  in `constants.rs`, and the readout already exists.
- **The plume**, drawn opposite the thrust vector, in **both** render paths. High Quality gets
  the shader; Canvas gets something that is unmistakably the same event. `T21.33` is the
  reminder that the owner's browser has run Canvas and that no check had.
- **A wire bit for the thrust direction**, derived at the encode site — **and the shape should
  be one bit plus velocity, not a direction.** The snapshot flags byte has **only bit 7 free**
  (0–6 are alive/grounded/jetpack/shield/flashlight/invulnerable/poisoned). The `move_mods`
  byte has five free bits but is explicitly *"what the mirror simulates with"*, so it is the
  wrong home for a cosmetic. **The snapshot already carries `vel.x` and `vel.y` per player**,
  so: one bit for *"thrusting"*, and the plume's direction derived client-side from velocity.
  It must be *derived*, not stored, or it is a third place that can disagree with `MoveMods`.

## Hazards

- **The four render combinations collapse to three, and a check that ignores this asserts the
  same picture twice.** Every shader predicate in the client is `webgl && isHighQuality()`, so
  on Canvas the High Quality toggle changes **nothing**. The distinct paths are
  **(WebGL, HQ on) = shader**, **(WebGL, HQ off) = flat**, **(Canvas, either) = flat**.
  Selection is `?renderer=canvas` (`client/src/main.ts::rendererType`, gated on `devSurface`);
  HQ is flipped with `window.__game.setHighQuality(v)`. Copy `scripts/checks/fire-shader.mjs`.
- **The plume is the first arbitrary-direction thing inside `PlayerView`.** `R7` does not
  forbid it, but the `setFlipX` pattern that boots and wings use — the pattern this file tells
  you to copy — **cannot express it**. `PlayerView`'s only rotation today is
  `this.weapon.setRotation(aim)`. Plan for that rather than discovering it at the shader.
- **`R22`**: `SandboxScene` cannot reach the space mode today, so the cheap home for this
  task's pixel assertions does not exist yet. Whoever lands first writes the `?gravity=` param.
- **Do not rebuild `PlayerView` to add it.** T20.12's `sameAppearance` rebuild guard exists
  because appearance fields are `private readonly` with no setter; a plume added at construction
  vanishes on the next rebuild. Toggle per frame, the way boots and wings do.
- **A player thrusting in two axes at once** has one plume or two — decide, and say which.
- **Nobody is thrusting when the round is over.** T21.30 froze input in `Ended`; the plume must
  freeze with it or a corpse fires its jets.

## Tests

- **Rendered pixels, with a control region and a control frame** (§C2). Thrust down, assert the
  bright region is *above* the player's centre and that a region below is unchanged.
- The same assertion **with High Quality off**, which is the half T21.36 caught.
- Fuel falls while thrusting and does not while idle — both ends, against the readout.
- No plume while `Ended`.
