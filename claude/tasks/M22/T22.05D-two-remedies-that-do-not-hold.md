## 1. The biconditional passes in the direction it claims to catch (F-3)

`items/spawning.rs::crates_spawn_inside_the_arena_in_space` asserts

```rust
assert_eq!(space_moved == 0, GravityMode::Space.scale() == 0.0, …);
```

and its comment — repeated at `SpawnSchedule::tick_crates` — claims it *"reports the mechanism
coming apart in **either** direction — a stepper that stops reading the mode, or a scale that stops
being zero."*

**Plant `GravityMode::scale`'s `Space` arm 0.0 → 0.5.** The right-hand side becomes `false`; crates
now fall so `space_moved > 0` and the left-hand side becomes `false` too; `assert_eq!(false, false)`
**passes**. Every term moved with the constant — `CLAUDE.md`'s measured `ITEM_SPAWN_INTERVAL` shape.
The first direction (a stepper that stops reading the mode) does hold.

The repository is still covered for the second direction by
`constants.rs::every_gravity_mode_has_a_multiplier`, so **nothing is broken** — what is wrong is the
sentence. Fix:

- `assert_eq!(space_moved, 0, …)` for the effect, **keeping** the existing `ctl_moved > 0` presence
  control on the same 60 crates at standard gravity. Do not drop it: without it this is an absence
  assertion satisfied by a build where nothing ever moves.
- If a local pin is wanted, `assert_eq!(GravityMode::Space.scale(), 0.0)` on its own line, where it
  cannot be cancelled by the term beside it.
- Narrow both comments to the direction that holds, and name
  `every_gravity_mode_has_a_multiplier` as what covers the other.

**Run the plant first and paste the pass**, then the plant again after the fix and paste the red.
An unfalsified fix here would be a third sentence with nothing behind it.

## 2. An assertion behind a guard that fires first (F-4)

`periodic_items_land_inside_the_arena_in_space` gained a `body_fits_at` assertion **inside** its
item loop, to replace a message `T22.05C` correctly diagnosed as unhelpful. It cannot run under the
plant it was written for.

Trace: under `Map::random_body_site`'s space arm drawing from `surface_points`,
`resample_surface` does `let Some(p) = map.random_body_site(rng) else { continue }; if
!map.body_fits_at(p) { continue; }`. Every surface point fails `body_fits_at` — which is precisely
what `T22.05C`'s own `the_two_pools_a_space_map_has_are_disjoint` proves — so every attempt is
rejected, nothing spawns, `seen` stays 0, **the loop body never executes**, and the test still dies
on `assert!(seen > 0, "no periodic items spawned at all")` with the same wrong message.

**The defect was always the guard's message**, and an assertion behind it changes nothing. Fix:
instrument the schedule's **two stages separately**, so *"the schedule fired N times and every draw
was rejected"* reads differently from *"the schedule never fired"*.

**How that fix could fail, and avoid it:** do not build the new guard by calling
`resample_surface` — that restates the function under test. Count the schedule's firings and its
successful placements.

Its sibling `initial_items_land_inside_the_arena_in_space` **does** improve under the same plant,
because `place_initial` has no `body_fits_at` re-check, so the planted point is actually placed and
the assertion fires naming the subject. That half is correct; leave it alone.

## Outcome (builder, 2026-09-22)

Both halves fixed in `crates/game-core/src/items/spawning.rs`; nothing else touched.
Every plant was run against the shipped text, and the reds are in the report.

**§1.** Before: planting `GravityMode::scale`'s `Space` arm 0.0 → 0.5 left
`crates_spawn_inside_the_arena_in_space` **green** (`EXIT=0`) while
`constants.rs::every_gravity_mode_has_a_multiplier` went red — F-3 confirmed exactly as
predicted. After: the biconditional is two lines, `ctl_moved > 0` kept as the presence
control, and both comments narrowed. Same plant now red on the pin, naming the constant;
reverting `items/world.rs::WorldItems::step` to `Forces::gravity(1.0)` is red on the effect
("60 of 60 crates moved"), so the two causes give different messages.

**§2.** Before: planting `Map::random_body_site`'s space arm to draw from
`map.meta.surface_points` killed `periodic_items_land_inside_the_arena_in_space` on
`seen > 0` / "no periodic items spawned at all" — F-4 confirmed, the in-loop `body_fits_at`
never ran. After: `fired` counts the schedule's deadline advancing and `seen` counts the ids
it returned, each with its own guard; `resample_surface` is not called by the test. Same
plant is now red on the placement guard at `fired == 40`, and dropping `tick_items`'
`self.next_item_at += ITEM_SPAWN_INTERVAL` is red on the *cadence* guard while items still
spawn — which is what says `fired` reads stage one rather than mirroring `seen`.

**Decided here.** (a) The local pin was kept (the task left it optional) because it is what
makes the two failures distinguishable *inside this test*. (b) The cadence guard's first
wording said "nothing below this line ran"; the deadline plant disproved it — items do spawn
— so it was rewritten before shipping. A false sentence beside an assertion is the defect
this task exists for.
