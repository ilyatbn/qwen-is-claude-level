## The client has **no** rocks, not stale ones (`R49`)

R11 said the client holds stale meta. It is sharper than that: `GameCore::new()` is
`generate(1, MapScale::Small)` on the **standard** generator, so `meta.asteroids` is **empty**. A
networked client today predicts against a field of exactly zero everywhere — not a wrong field, no
field. That is an easier failure to write a red-before-green for, so write it that way.

**Three layers remain, and `T22.05A` already shipped the hard one.** On the wire:
`game-server/src/codec.rs::encode_map_init` writes the asteroid section, `decode_map_init_parts`
reads it (pinned by `codec.rs::map_init_round_trips_every_asteroid_and_its_level`), and
`client/src/net/codec.ts` decodes `asteroids: MapAsteroid[]`. Missing:

1. `GameCore::set_asteroids` in `crates/game-wasm/src/lib.rs`
2. the `core/index.ts` wrapper
3. **one line** in `worldMirror.ts::applyMapInit`, which already calls `setTeleportPads` and
   `setGunPlatforms` two lines above — the precedent is its own neighbour

## The browser check, and it is the point of this task (`R63`)

`T22.11`'s Done-when named `node scripts/e2e.mjs asteroid-gravity`. It **does not exist**:
`grep -rn "asteroid" scripts/` returns 0. Write it.

`CLAUDE.md` is blunt about why: **for anything visible, assert on rendered pixels** (`docs/72`
§C2), with a **control region** and a **control frame** — *"four 'I cannot see it' bugs shipped
past 905 tests because every assertion checked simulation state."* The wells are currently proven
nine ways in simulation and zero ways on screen, which is exactly that shape.

So the check must assert a player is **drawn** moving toward a rock, not that `debug()` says so:
- **control region** — a patch of the frame the well should not affect;
- **control frame** — the same seed and start with the rock's influence absent (an asteroid-free
  space map, or a standard map), asserted **not** to show the motion;
- and **no wall-clock sleeps.** `page.waitForFunction` on the condition, never `waitForTimeout`.
  `T22.05C` removed 8 of them from `minimap.mjs` for this reason, and four checks went red in one
  gate purely from box load. A new check that fails when the box is busy gates nothing.

Read `scripts/checks/minimap.mjs` as the local model: it reads its palette out of the page rather
than hardcoding it, and every wait polls an observable.

## Prediction agrees with the server

The determinism half. `env_at` already lives in `attractors.rs` and **both sides call it** —
`T22.11B` chose that deliberately (*share the guard, or share the function*), and both prior
rubber-band bugs here were a mirror inventing its own value. So do not compose an `Env` on the
client; call the shared function with the rocks now installed.

- Drift a player through a field and assert client and server agree. `R36`'s hash covers `level`,
  `x`, `y` and `r`, so a mis-installed rock is visible to it — **use that**, rather than a
  position comparison with a tolerance you have to pick.
- **The ordering is load-bearing and untested at the seam.** `load_mask`'s comment asserts
  `set_gravity` arrives off `lobby_state` **before** `map_init`. The only test of that ordering
  calls `set_gravity` explicitly. Your setter lands in the same window: say at the code what
  happens if `map_init` arrives first, and assert it.

## Hazards

- **`Map::space_geometry`'s doc claims it is "sound in both directions"** and it is not, on a
  networked client, until this task lands. `T22.05C` added a sentence saying so. **When you land,
  delete that sentence** — a stale caveat is the same defect as a stale claim.
- **`float summation order`** — the client must sum the same contributions in the same order.
  `T22.11B` has a test for reversed order; make sure the client's list is the server's, sorted the
  same way, and say at the code what sorts it.
- The box must be yours for anything timed; `pgrep` yourself first.
