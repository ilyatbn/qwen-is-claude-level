## Recommendation

**Take (c) — the `Forces`/`Env` struct — but split T22.11 into three tasks, and change
the ceiling constant from `JETPACK_THRUST_UP` to `JETPACK_THRUST_DOWN`.** (c) is the only
one of the three under which `apply_gravity` keeps its early return, its `vel.y` and its
`MAX_FALL_SPEED` clamp untouched — which matters because those three things are the
*whole* of standard gravity and every one of the 16 tests that exercise them, and because
the vector path needs a magnitude clamp that `MAX_FALL_SPEED` cannot be (R10 is right on
all of this, and `no_tunnelling_at_ten_times_terminal_velocity_through_integrate` is a
real, existing tripwire that (b) would set off). The deciding reason against (a) and (b)
is the silent-break question: under both of them a new caller who passes `Vec2::ZERO`
gets a legal, silent "no field", and nothing in the tree reports it — which is the exact
shape of the twelve mechanisms this project has built and wired to nothing. Under (c) a
caller must name a `Forces`, and the one way to reintroduce the silent failure is to give
`Forces` or `Env` a `Default` — which is the thing `MoveMods::NONE`'s doc comment already
refuses in as many words, so the precedent for refusing it is in the same file.

Two riders, both load-bearing:

1. **T22.11 as written is ~15 files and cannot be one task.** CLAUDE.md's "~one file and
   ~250 lines… heading well past that means it needs splitting" is not close. The split
   that falls out of the rulings themselves is in §"The three shapes" below.
2. **The ceiling inequality in the task file and in R18 is against the wrong constant.**
   `JETPACK_THRUST_UP` = 2200 is the *strongest* axis; the binding direction is straight
   down, where the pack has `JETPACK_THRUST_DOWN` = 900. A well of 1500 px/s² passes
   R18's guard and still traps forever any player who ends up on the underside of the
   rock. Detail and arithmetic in §"The numeric basis".

## 3. The three shapes, costed

### (a) `Vec2` beside the scalar — `integrate(map, body, gravity_scale, accel, zero_g, dt)`

- **Files touched:** 6 Rust files minimum (resolve, player/mod, world/mod, wasm, the four
  steppers if R30/R14 are honoured) + 3 test files.
- **Production call sites changed:** 5 for `integrate`, 3 for `apply_input`.
- **Argument count:** `integrate` goes to **six**, `apply_input` stays at **nine**. This
  shape *violates R10 and R44 outright*, both of which say a builder who lands it has
  produced a finding.
- **A field that means two things?** No single field does. But *"what accelerates this
  body"* now has two answers, which R10 calls out and which is the same defect one level
  up. `resolve::integrate`'s own doc currently asserts the opposite — *"The force is
  `gravity_scale` and it stays the only answer to 'what accelerates this body'"* — so this
  shape makes a shipped comment false on the day it lands.
- **Share the guard, or share the function?** Neither. `MAX_FALL_SPEED` guards `vel.y` on
  the scalar path; the `Vec2` path has no guard at all and no place to put one that the
  scalar path would share.
- **Preserve state it is about to destroy?** No.
- **Can a second function drop the guard?** **Yes, and this is the shape's fatal
  property.** A new caller writes `Vec2::ZERO` and gets today's behaviour — a *legal,
  silent* "no field". Nothing in the tree reports it, ever.

### (b) Scalar replaced by a vector — `integrate(map, body, accel: Vec2, zero_g, dt)`

- **Files touched:** the same 6 + 3, plus `constants.rs`.
- **Production call sites changed:** 5, and each of the four `1.0` sites has to construct
  `Vec2::new(0.0, GRAVITY * scale)` itself.
- **What it destroys:**
  - `apply_gravity`'s `if gravity_scale == 0.0 { return; }` — there is no cheap exact test
    for "this `Vec2` means no gravity", and an epsilon here is a new source of drift.
  - The `vel.y`-only clamp. A magnitude clamp clamps *upward* too, and `apply_gravity`'s
    doc refuses that in as many words: *"Clamped on the way **down only**. Upward velocity
    is not clamped, so a strong knockback still launches properly."*
  - `no_tunnelling_at_ten_times_terminal_velocity_through_integrate` drives `vel.y = 9000`
    and `vel.x = ±5000` through `integrate` and would go red.
- **Preserve state it is about to destroy?** **Yes.** Four callers each re-derive the same
  gravity arithmetic. This project already has a comment about exactly that hazard, at
  `jetpack::thrust_delta`: *"`(-2200 + 900) * dt` and `-2200 * dt + 900 * dt` are not the
  same `f32`, and a physics function's arithmetic is not something to change while doing
  something else."* Four re-derivations of `GRAVITY * scale * dt` is four chances to get a
  different float on the client than on the server.
- **Can a second function drop the guard?** Yes — same as (a): `Vec2::ZERO` is legal and
  silent.

## 4. The three hazards: confirmed / refuted

### Hazard 1 — "`MAX_FALL_SPEED` clamps `vel.y` only, so sideways is unbounded" — **CONFIRMED, with one correction**

The clamp, quoted whole, is the `apply_gravity` body above: `if body.vel.y > MAX_FALL_SPEED
{ body.vel.y = MAX_FALL_SPEED; }`. Nothing else in `game-core` touches it.

**What I checked for an accidental horizontal bound.** I enumerated every production write
to `vel.x` in `game-core` (grep for `vel.x =`, `vel.x +=`, `vel.x.clamp`, classified against
each file's first `#[cfg(test)]`). The complete list of things that could bound a *player's*
horizontal speed:

| mechanism | symbol | does it bound? |
|---|---|---|
| wall collision | `resolve::move_x` — `body.vel.x = 0.0;` | Only on contact. In an open ellipse of vacuum, the rim is contact and the rest is not. |
| arena clamp | `resolve::clamp_to_world` — `body.vel.x = body.vel.x.max(0.0)` / `.min(0.0)` | Only at the `WALL_W` columns, which in space sit **outside** the rim (R16's lethal band). Not a governor. |
| thruster clamp | `jetpack::apply_thrust` — `body.vel.x = body.vel.x.clamp(-JETPACK_MAX_SPEED, JETPACK_MAX_SPEED)` | **No.** Guarded by `if thrust_x != 0.0 && before_x.abs() <= JETPACK_MAX_SPEED`, and its doc says so: *"A body already moving faster than the limit — a rocket jump at 800 px/s — is left alone."* |
| walk/drag | `movement::apply_horizontal` — `approach(body.vel.x, target, rate*dt)` | **Not reached.** `apply_input` skips it entirely while `space::floating`. |
| sub-stepping | `resolve::substeps`, `MAX_SUBSTEPS` 64 × `MAX_SUBSTEP_PX` 1.0 | Bounds **displacement**, not velocity: *"a body moving faster than 64 px per tick moves slower than requested rather than tunnelling."* |

So: **there is no horizontal speed governor, confirmed.** The one correction to the task
file's wording is that the *observable* motion is not unbounded — `substeps` saturates it at
64 px/tick ≈ 3840 px/s of travel at 60 Hz. What is unbounded is the `f32` in `vel.x`, which
grows forever, loses precision, and drifts between two sides that are adding N float
contributions in any order. So the hazard is real but it is a **determinism** hazard before
it is a "player flies off the map" hazard, and the fix is R10's `max_speed: Option<f32>` on
`|vel|`. R10's own three interactions for that value are all confirmed at the code:
`apply_thrust`'s per-axis comment refusing a magnitude clamp is there verbatim; diagonal
thrust reaches √(260²+260²) ≈ 368; `KNOCKBACK_MAX` is 320.

### Hazard 2 — "`apply_gravity` early-returns at scale 0, so the wells must go somewhere that return does not skip" — **CONFIRMED**

`GravityMode::Space.scale()` is `0.0` (`constants.rs::GravityMode::scale`), and
`jetpack::gravity_scale` multiplies all three regimes by it, so **every** space player
reaches `apply_gravity` with exactly `0.0` and it returns before touching `vel.y`.
`player/space.rs`'s module doc states the same thing as a table row: *"| gravity, and
`MAX_FALL_SPEED` with it | `resolve::apply_gravity` | the scale is `0.0` and the function
early-returns |"*.

Every place a player body's velocity is touched in a space tick, and where it sits relative
to that return:

| site | relative to the early return |
|---|---|
| `movement::apply_horizontal` | **before** `integrate`; skipped entirely while `space::floating` |
| `movement::try_jump` — `body.vel.y = -JUMP_VELOCITY * jump_multiplier` | **before**; live in space (R4 — you push off a rock, and `jetpack::spend_jump` charges for it) |
| `jetpack::apply_thrust` — `body.vel.x += thrust_x; body.vel.y += thrust_y` | **before**; the space engine (R42) |
| `movement::apply_flight` — assigns `vel.y` | **before**; wings only |
| `resolve::apply_gravity` | **the return itself** — dead in space |
| `resolve::move_x` / `move_y` | **after**, inside `integrate`, and they run regardless |
| `resolve::clamp_to_world` | **after**, inside `integrate` |
| `explode.rs` / `melee.rs` — `*p.vel += impulse` | outside `integrate` altogether, in `World::step` |

So the only place a field can go that is (i) inside the one function both sides run,
(ii) downstream of nothing that skips it, and (iii) upstream of `move_x`/`move_y` so the
same tick moves the body, is **in `integrate`, beside `apply_gravity`** — exactly R10's
ruling. Confirmed.

`jetpack::spend_jump` does **not** touch velocity — it is fuel only
(`state.fuel = (state.fuel - SPACE_JUMP_FUEL).max(0.0)`). The task's mention of it is about
the fuel economy, not the integration path.

`meta.asteroids` is **empty**, not merely stale. A networked client predicts against a
field of exactly zero everywhere. R11 describes this as "stale meta from an unrelated map";
the sharper statement is that the client has **no rocks at all** and would rubber-band on
every tick a player is in any well.

**R11's plumbing table is out of date, in T22.11's favour.** T22.05A already shipped the
wire and the decode:

- `game-server/src/codec.rs::encode_map_init` writes the asteroid section, `decode_map_init_parts`
  reads it into `parts.asteroids`, and `codec.rs::map_init_round_trips_every_asteroid_and_its_level`
  pins it.
- `client/src/net/codec.ts` decodes `asteroids: MapAsteroid[]` with `{x, y, r, level}`.

What is **missing**, measured (`grep -rn 'set_asteroids\|setAsteroids' crates/ client/src/`
returns nothing): the `GameCore::set_asteroids` setter, the `core/index.ts` wrapper, and
the `worldMirror.ts::applyMapInit` line. `applyMapInit` today calls
`this.core.loadMask(...)`, `this.core.setTeleportPads(m.pads)`,
`this.core.setGunPlatforms(m.platforms)` — and no asteroid setter. **Three layers, not
four, and the precedent for all three is `setTeleportPads` two lines above.**

**R36's debt is confirmed and its falsification target is clear.** `level` *is* in
`tests/golden.rs::meta_digest` (`h.update(&[a.level]);`), so generation drift is caught;
it is *not* in `World::state_hash`, so runtime cross-side drift is invisible. T22.11's
red-before-green is exactly: set one asteroid's level differently on the two sides and show
`state_hash` diverges.

## 5. The numeric basis and the ceiling inequality

### The constants, quoted

```rust
// ---------------------------------------------------------------------------
// Movement
// ---------------------------------------------------------------------------

pub const GRAVITY: f32 = 1400.0;
pub const MAX_FALL_SPEED: f32 = 900.0;
```

**Neither `GRAVITY` nor `MAX_FALL_SPEED` has a doc comment** — they sit bare under the
`// Movement` banner. Worth knowing before T22.11 is asked to write a "space terminal
speed" *"the way `capacity.rs::max_rooms_carries_its_basis` does"*: there is no existing
basis comment on the constant it is being contrasted with.

```rust
pub const JETPACK_MAX_FUEL: f32 = 5.0;
pub const JETPACK_DRAIN: f32 = 1.0;
pub const JETPACK_THRUST_UP: f32 = 2200.0;
pub const JETPACK_THRUST_SIDE: f32 = 1100.0;
pub const JETPACK_THRUST_DOWN: f32 = 900.0;
pub const JETPACK_MAX_SPEED: f32 = 260.0;
```

Also bare — the Jetpack block carries no doc comments on any of these six.

```rust
/// The furthest a player can climb in one unbroken effort:
/// `JETPACK_MAX_SPEED * JETPACK_MAX_FUEL * 0.6`. Falling is free; climbing is not,
/// which is why traversal edges are directed.
pub const JETPACK_CLIMB_BUDGET: f32 = JETPACK_MAX_SPEED * JETPACK_MAX_FUEL * 0.6;
/// A climb longer than this is only possible if it passes a standable surface point
/// on the way — that is where you land and refuel.
pub const LEDGE_REFUEL_RISE: f32 = JETPACK_CLIMB_BUDGET;
```

260.0 × 5.0 = 1300.0; 1300.0 × 0.6 = **780.0 px**. (Checked twice.)

**What `traversal.rs::analyse` does with it** — two things, both quoted:

```rust
    // Region edges are capped at the climb budget, so bucketing by it covers both
    // them and the (shorter) ballistic edges.
    let budget_sq = (JETPACK_CLIMB_BUDGET * JETPACK_CLIMB_BUDGET) as i64;
    let buckets = Buckets::build(mask, surface, JETPACK_CLIMB_BUDGET.max(1.0) as i32);
```

and, in the edge predicate,

```rust
            let region_edge =
                labels[i] != 0 && labels[i] == labels[j] && a.distance_sq(b) <= budget_sq;
```

So it is (i) the spatial-bucket cell size and (ii) the maximum length of a "same navigable
region" edge. `NavRegions`' doc explains why: *"A region edge is therefore only issued
between points within `JETPACK_CLIMB_BUDGET` of each other, and longer routes must chain
through intermediate surface points — which is exactly the 'land on a ledge and refuel' the
budget describes."*

Note a wrinkle R18 does not mention: **780 px is a budget derived under gravity.** It is
"climb at the governed 260 px/s for a whole tank", which prices the climb against a 1400
px/s² downforce. In space there is no downforce outside a well, so the same tank buys far
more *distance* — but inside a well the player is being decelerated the whole way, so
whether 780 px is conservative or optimistic as a well's reach depends entirely on the
falloff law. Using it as the cutoff radius is defensible and self-documenting; using it as
the *escape* criterion is not, because escape is an acceleration comparison (R18's own
point 2) and 780 is a distance.

### The ceiling inequality — and why the constant in R18 is the wrong one

Mechanism, from the code. `jetpack::thrust_delta` produces a **per-tick velocity delta**:

```rust
    if input.held(button::UP)    { thrust_y -= JETPACK_THRUST_UP * dt; }
    if input.held(button::DOWN)  { thrust_y += JETPACK_THRUST_DOWN * dt; }
    if input.held(button::LEFT)  { thrust_x -= JETPACK_THRUST_SIDE * dt; }
    if input.held(button::RIGHT) { thrust_x += JETPACK_THRUST_SIDE * dt; }
```

Down is `+y` (`apply_gravity` adds `GRAVITY * scale * dt` to `vel.y` and clamps
`vel.y > MAX_FALL_SPEED`). So the pack's available acceleration vector for one tick is one
of nine values `T(buttons)`, and the well contributes `a_well · (−u)` where `u` is the
outward radial unit vector — **both scaled by the same `dt` in the same
`apply_input` tick, so `dt` cancels**. The player can move outward iff

    max over button combinations of  T · u   >   a_well

For the three cardinal escape directions that maximum is:

| where the player is | outward `u` | best `T · u` | constant |
|---|---|---|---|
| on top of the rock | (0, −1) | 2200 | `JETPACK_THRUST_UP` |
| on the side | (±1, 0) | 1100 | `JETPACK_THRUST_SIDE` |
| **on the underside** | (0, +1) | **900** | **`JETPACK_THRUST_DOWN`** |

**The task file and R18 both assert the guard against `JETPACK_THRUST_UP` = 2200. That is
the strongest axis, and it makes the guard a statement about the *best* case.** A well of,
say, 1500 px/s² at the surface passes R18's assertion and still traps forever every player
who comes to rest on the bottom of the rock — with, in the task file's own words, "no cause
on screen and no message". The guard as specified is a claim reported through something
other than the thing it claims: it is named "escape is possible" and it tests "escape is
possible from the top".

**The inequality T22.11 should assert.** Let `a(n, r, d)` be the well's acceleration
magnitude for a level-`n` rock of bounding radius `r` at centre distance `d`, and let

    d_min(r) = SPACE_ASTEROID_CORE_FRAC * r + PLAYER_H / 2.0

be the smallest centre-to-centre distance a live player body can occupy — the core disc is
`SPACE_ASTEROID_CORE_FRAC` (0.75) of the bounding radius, the lumps only push you further
out, and `Body::pos` is the body's centre (`clamp_to_world` uses `body.size.y / 2.0`).
Then:

    max over n ≤ SPACE_LEVEL_MAX, r ≤ SPACE_ASTEROID_R_MAX  of  a(n, r, d_min(r))
        <  JETPACK_THRUST_DOWN

…scoped to `Attractor::Kind::Asteroid`, per R11, so `T22.12`'s black hole carries the
inverse. If the owner prefers the weaker guarantee ("you can always escape *upward*"), that
is a legitimate design call, but it must then be **written at the code that the underside
of a rock can be a trap**, because nothing else would say so.

### Worked numbers

Radii: `SPACE_ASTEROID_R_MIN` = 24, `SPACE_ASTEROID_R_MAX` = 64, drawn inclusively
(`rng::range_i32` uses `gen_range(lo..=hi)`). `PLAYER_H` = 28.0, so half is 14.0.

`level_for` is `base = 1 + t*(SPACE_LEVEL_MAX-1)` with `t = (r-24)/40`, plus jitter drawn
half-open on [−0.6, 0.6), rounded, clamped to 1..=5. So **level 5 requires `base + jitter ≥
4.5` with `jitter < 0.6`, i.e. `base > 3.9`, i.e. `t > 0.725`, i.e. `r ≥ 54`.** The
smallest level-5 rock has radius 54.

    d_min(54) = 0.75 × 54 + 14 = 40.5 + 14 = 54.50 px
    d_min(64) = 0.75 × 64 + 14 = 48.0 + 14 = 62.00 px
    d_min(24) = 0.75 × 24 + 14 = 18.0 + 14 = 32.00 px

**If the field is inverse-square**, `a(d) = k(n) / d²`, the ceiling binds at the *smallest*
level-5 rock:

    k(5) < JETPACK_THRUST_DOWN × d_min(54)²  =  900 × 54.5²  =  900 × 2970.25
    k(5) < 2 673 225  px³/s²

At that ceiling, the same well at 780 px (one climb budget out) delivers

    a(780) = 2 673 225 / 780²  =  2 673 225 / 608 400  =  4.39 px/s²

— **4.4 px/s² against an 1100 px/s² sideways thruster, i.e. nothing.** (Cross-check at the
largest rock: `2 673 225 / 62² = 2 673 225 / 3844 ≈ 695 px/s²`, comfortably under 900, so
r = 54 is indeed the binding case.) So an inverse-square well pinned to the escape ceiling
is either brutal at the surface or invisible at range; there is no setting at which it is
both escapable and felt. **That is an argument for a bounded falloff, not for a cutoff
radius.**

**If the field is linear to a cutoff**, `a(d) = a_surf(n) · max(0, 1 − d/R(n))`, then
`a_surf(n)` is directly the number the inequality bounds, the field is felt across the whole
of `R(n)`, and `R(n)` can be stated as a fraction of `JETPACK_CLIMB_BUDGET` — which gives
R18 exactly the "measured basis written into the doc comment" it asks for: *level n's reach
is `R(n) ≤ JETPACK_CLIMB_BUDGET`, so a full tank always clears the well's influence.*
I would spend the design call there. It also makes the hard-edge problem the task names
("a well with a hard edge is a wall you fall off") disappear, because the acceleration goes
to zero continuously at `R`.

### How many asteroids — N

Read out of the code, not run.

`SpaceParams::default_for(scale).asteroid_count = scale.params().asteroid_count`, and
`ScaleParams` gives:

| scale | target `asteroid_count` | floor the existing test asserts |
|---|---|---|
| Small | 14 | ≥ 11 |
| **Medium** (`DEFAULT_MAP_SCALE`) | **34** | ≥ 26 |
| Large | 64 | ≥ 48 |

**These are targets, not counts.** `place_asteroids` is rejection sampling —
`for _ in 0..(params.asteroid_count * SPACE_ASTEROID_TRIES)` with a `break` when the target
is met — so the realised N is data-dependent per seed. The floor column is derived from the
assertion in `space.rs::asteroids_exist_and_are_separated`:

```rust
            assert!(
                min * 4 >= params.asteroid_count as usize * 3,
```

i.e. the minimum over 12 seeds is at least ¾ of target (14→10.5→11; 34→25.5→26; 64→48).
**I have not run that test, so I do not know the realised distribution** — see the open
questions list, item 1. `SpaceParams::safe_for` halves it with a floor of 4, and
`used_safe_preset` is the path R17 warns ships silently.

**What that means for the cutoff question.** Worst case N × M = 64 × `MAX_PLAYERS` (6) =
**384 attractor-player pairs per tick**, on each side, at 60 Hz. That is a couple of
hundred thousand float operations a second for a dx/dy/length/falloff — small. So **a
cutoff radius is not needed for performance at this N**, and the task file's premise
(*"'Tons of tiny islands' means N is large"*) does not survive contact with the numbers:
N is 64, not thousands. The cutoff is a **gameplay and float-determinism** decision — it
bounds how many terms enter each sum and therefore how much order-dependent rounding
accumulates — and it should be argued on those grounds. (The per-tick *cost* claim needs
a measurement before anyone relies on it; see open question 3.)

### Keep passing while meaning something different — **the dangerous list**

1. **All 20 tests in `player/space.rs`.** They go through a local `step(map, st, buttons,
   mode)` that builds its own arguments. After the refactor that helper builds an `Env`,
   and the fixture map has no asteroids — so every zero-g assertion
   (`a_ceiling_takes_the_normal_and_the_tangential_survives_forever`,
   `thrust_ignores_health_and_boots_and_walking_on_a_rock_does_not`, R42's weld tests)
   stays green while describing a space with no wells in it. They are green now, they are
   green after, and **not one of them can report a field that never fires.** This is the
   single biggest hole and it is the reason the task's own first test ("a player near a
   level-*n* asteroid accelerates toward it, and one far away does not") has to be written
   against a fixture that actually has rocks.
2. **`resolve::gravity_clamps_downward_only` and
   `resolve::gravity_scale_zero_leaves_velocity_alone`.** Both pin `apply_gravity`, which
   shape (c) deliberately does not touch. They stay green *by construction* and say
   nothing whatever about the new path. Do not count them as a regression net for it.
3. **`resolve::a_resting_body_is_bit_identical_after_600_ticks`.** R10 nominates it as
   *the* control. It is one only if `Forces::gravity(1.0)` carries `accel: ZERO` and
   `max_speed: None`. If someone gives `Forces` a `Default` whose fields are zero/None,
   this passes and proves nothing about the well path — it would pass for a build where
   `accel` is never read.
4. **`space.rs::a_bigger_rock_pulls_harder_on_average`.** Its name says *pulls harder*; its
   body asserts that the mean **radius** rises with level. It cannot see the level→pull
   table at all, because that table does not exist yet — and once it does, this test will
   still not see it. This is the `density_report` near-miss shape verbatim: a test that
   looks like it covers the area, passing while the thing it is named for is untested.
5. **`codec.rs::map_init_round_trips_every_asteroid_and_its_level`.** It proves the levels
   reach the client's **codec**. It would stay green with `GameCore::set_asteroids` never
   written and the client's core holding zero rocks forever. "The levels are on the wire"
   standing in for "the client predicts with them".
6. **`client/src/core/index.test.ts`'s asteroid assertions** (`expect(core.meta.asteroids.length)
   .toBeGreaterThan(0)`). They go through `core.generate(...)` — the sandbox path. The
   networked path is `loadMask`, which as shown leaves `meta.asteroids` empty. The suite
   covers the case that works and not the case that is broken.
7. **`tests/delivery.rs`'s six mine assertions, and the items/tombstones/animals tests.**
   Threading a mode argument at `GravityMode::Standard` keeps all of them green while
   R14's space behaviour and R30's low-gravity behaviour are entirely untested. Adding the
   argument does not add the test — and R30's bug (loot falling at full speed in low
   gravity while the player floats) is *visible in a shipped mode right now*.
8. **Anything asserting the absence of a field.** The task file's own test list has
   "one far away does not accelerate". CLAUDE.md's rule applies directly: that assertion
   is satisfied by a build where the field is never applied at all. It needs the near-rock
   control in the same test, and the near-rock control needs to be red before the field
   lands.

One that **does** bite, and should be protected:
`resolve::no_tunnelling_at_ten_times_terminal_velocity_through_integrate` drives
`vel.y = 9000`, `vel.x = ±5000` through `integrate`. R10 is right that
`Forces::gravity(1.0)` must carry `max_speed: None` or it goes red — that makes it the one
existing test that can detect a `max_speed` leaking onto the standard-gravity path.
