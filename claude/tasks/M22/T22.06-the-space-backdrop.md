# T22.06 — The space backdrop: sun, moon, earth, stars, and they move

Milestone: M22 · Depends on: **T22.01** · Size: ~200 lines · Origin: new, 2026-09-18

Asked for: *"there's no day/light in space but the sun and moon and the earth and stars can be
the background and should move. there are no clouds or fog or anything like that."*

## Before anything else: the client will paint the whole arena as a cave

**`R33`, and it is `T22.05A`'s largest finding.** The terrain renderer decides whether to
paint the **cave backdrop** from whether air is reachable by a flood from the sky. **A closed
rim means none of the arena's interior air is.** Measured at seed 4242: inside the rim, **0 of
1 098 496 / 2 819 018 / 5 312 965 px are sky-reachable — 1.0000 enclosed on every scale.**

Over the *whole map* it is 0.590 / 0.654 / 0.684, because the band outside the rim and the sky
above it are open — **and that whole-map number is the misleading one.** Read the interior
figure.

Neither piece is a bug. The rim is closed by design and `T22.05A`'s `rim_is_closed` asserts
the same fact from the other side; the renderer's rule is right for every map that existed
before. **So space needs its own backdrop decision, and this task owns it.** There is an
`#[ignore]`d measurement in `map/gen/space.rs` carrying the numbers.

**And one quieter trap in the same area:**
`client/src/render/backdrop-real.suite.ts::DEEP_WINDOW` is keyed by `MapGenerator.V1` and
`.V2` with **no `Space` entry**, and it is not an exhaustive `Record` — so it typechecks today
and a space case added to that suite gets `undefined` rather than a compile error.

## What this switches off, and it is a lot

The sky stack is five milestones deep and almost none of it applies. **Switching it off is most
of this task**, and each of these is a separate decision with a live check behind it:

| today | in space |
|---|---|
| the day/night cycle (`docs/14`, `sky-math.ts`, the lightmap) | off — there is no day in orbit |
| clouds (T21.31A: seeded, world-space, drifting) | off — the owner said so |
| the fog effect and `fogVeilAlpha` | off — and it is a *vision* rule, not only a picture |
| ambient rain (T21.26/T21.31B) | off |
| the parallax mountain ridge (`parallax.ts`, T21.20, T21.33) | replaced |
| `SkyBand` and birds | see `T22.05B` |

**`night_darkens_the_world`, `living-sky`, `clouds`, `clouds-canvas`, `cloud-rain`,
`ambient-rain`, `fog-visible` and `fog-shader` are live checks over this area** — verified
2026-09-20, all eight registered, none `flaky`. **The list is incomplete.** Three more assert
over this area and matter more than some of the eight: **`sky`** (*"screenshot the sky at each
phase and assert it actually changes"* — the day/night gradient itself, the single most
directly contradicted check), **`canvas-renderer`** (the parallax **ridge** this task
*replaces*, and the Canvas half this task requires), and **`lightmap`** (*"free in daylight,
dark at night, and lit around the player"*). Four others touch it more loosely:
`weather-visible`, `m5-weather`, `birds`, `gate-ground`.

Each needs to either skip in this mode or assert the mode's own answer. The T21.39 precedent
is the shape: a check that reads the switch and skips its section, not a deleted check.
**`R22` is what makes that possible at all** — five of these are sandbox-only and
`SandboxScene` has no mode parameter today, so without a `?gravity=` param they are
structurally incapable of being in this mode.

**One symbol correction**: the class is **`ParallaxLayer`**, singular. `ParallaxLayers` never
existed — the typo originates in `032440f`'s commit message and was copied forward into
`JOURNAL.md` and this file. And the `worldView` trap only bites code that *reads* `worldView`
during `update`; `SkyLayer`'s bodies use `setScrollFactor` and are positioned by Phaser, so
they never touch it. Use `setScrollFactor` and the trap does not arise.

## Only the earth is new — and every existing body is gated on the cycle you are switching off

**Both facts are from the 2026-09-20 sweep and neither is in the original file.**

**`render/sky.ts` already ships sun, moon and stars.** Its first line: *"The sky: a five-phase
gradient, a sun and a moon on their arcs, and stars."* `SkyLayer` owns `sun`, `sunGlow`,
`moon`, `moonGlow`, `starGfx`, `stars`; it is already seeded
(`constructor(scene, seed = 0, themeId = 0)`, `sky-math.ts::starField(count, w, h, seed)`) and
already parallaxes at `SKY_BODY_PARALLAX` = 0.08. **Do not rebuild what ships.**

**But you cannot keep them by switching the cycle off, and this is the design collision:**

- `sky-math.ts::bodyPositions(u, …)` returns `sun = t <= 0.55 ? … : null` and
  `moon = t >= 0.5 ? … : null`. **The sun and moon are never both on screen**, and both stop
  moving the moment `u` stops advancing. The owner asked for sun *and* moon *and* earth *and*
  stars, all moving.
- `sky-math.ts::starAlpha(u, darkness, nightDarkness)` returns `byPhase * byDark` where
  `byDark = darkness / nightDarkness`. **Pin darkness to 0 for "no night" and the stars are
  invisible.**

So "turn the cycle off and keep the sky" gives you no sun for half the cycle, no moon for the
other half, and no stars at all. **Space needs its own motion driver for the bodies, decoupled
from `cycleU`.** That is the design call this task owes.

## The lightmap trap has a precise mechanism, and it is a falsy coalesce

Both consumers — at `GameScene::update` and `GameScene::renderRemotes` — read

    const darkness = this.serverDarkness || darknessAt(cycleU(this.roundTime), C().NIGHT_DARKNESS)

**`serverDarkness === 0` is falsy**, so a server sending darkness 0 to mean *"there is no
night in space"* is **silently overridden by the client's own 120-second cycle**. And
`darkness` also feeds `fovRadius`, so this `||` is exactly where the gameplay-visible vision
rule the original warned about actually lives.

## Deliverable

- Sun, moon, earth and stars, **moving**. The owner said "should move" — so movement is the
  feature, not the decoration, and a still frame cannot show it.
- Seeded off the map seed, so a seed looks like itself. **Read the seed from the wire**, not
  from `core.meta.seed`: the 2026-09-16 finding is that `loadMask` leaves a networked client's
  `meta.seed` at its startup value — measured as 1 across four rounds — and `meta.theme` at 0.
  `GameScene` passes `this.mapSeed` and `init.theme` for exactly this reason now.
- Both render paths. Canvas is not optional (T21.33).

## Hazards

- **A backdrop that moves with the camera instead of the world.** This is the `living-sky` bug
  (`032440f`): `ParallaxLayers.layout` read `camera.worldView.y`, which Phaser refreshes only in
  `preRender`, so the ridge trailed a moving camera by one frame's travel — probed at 9, 8, 6,
  5, 5, 3 px. The fix is `parallax-math.ts::liveViewY` and rig-before-sky ordering. **Anything
  new in this layer inherits that trap.**
- **`drawClouds` still culls on last frame's `worldView`** — recorded as harmless and open. If
  clouds go away here, check whether the new bodies copied the same cull.
- **The lightmap.** Night darkening is a gameplay-visible vision rule, not just a tint. Turning
  the cycle off must not silently leave the lightmap in a permanent state nobody chose.

## Tests

- **The bodies move**: two frames, a real gap, the same body at different pixels, with a
  control region that does not move (§C2's control frame and control region).
- No cloud, no rain, no fog veil, in this mode — each asserted as an **absence beside a
  presence** in the standard mode, or the test passes for a renderer that draws nothing.
- Canvas and WebGL both.
- The backdrop is seeded: two seeds differ, one seed repeats. **Compare against the wire seed**,
  and note that `terrain-seed.mjs` runs in the *sandbox*, where `meta.seed` is real — so it
  could not catch the networked bug. A networked-round assertion is what this needs.
