# T22.00G — `fog-visible` compares two values sampled from different clocks

Milestone: M22 (gate hygiene) · Depends on: nothing · Size: ~40 lines · Origin: `T22.00F`'s
builder, while correctly refusing to assume its task's own premise

## The coordinator's mis-attribution, corrected first

`T22.00F`'s task file — **mine** — told its builder that `fog-shader` had gone red at
*"veil 0.783 against a predicted 0.794"* and to check whether it was the same wall-clock defect.
**That assertion is not in `fog-shader` at all.** Measured: `grep -n FOG_SCREEN_ALPHA
scripts/checks/fog-shader.mjs` returns nothing; the pair lives in `fog-visible.mjs`, at
`Math.abs(s.a - k.FOG_SCREEN_ALPHA * s.s) > 0.01`.

I had also told the owner that this failure was **load**, because all four of that gate's failures
re-ran green on an idle box. That was true and it was not the whole story: re-running green does
not make a marginal instrument sound, and this one has a defect that load merely exposes.

## What is actually wrong, verified at the code

The check compares two numbers read from `debug()` in one call:

- **`fogStrength`** — `GameScene.ts`: `fogStrength: self.fog.strength(self.roundTime)`, computed
  **live, at the moment `debug()` is called**.
- **`fogAlpha`** — `GameScene.ts`: `self.world?.weather.fogAlpha`, which returns
  `weather.ts::lastFogAlpha`, a field written at the **last drawn frame** (`weather.ts`, the
  `this.lastFogAlpha = a` assignment in the draw path).

So one value is from now and the other is from the last frame that happened to render. They are
compared at a tolerance of **0.01**.

And the poll deliberately stops while the quantity is still moving: `for (…90…) { s = await
fogState(page); if (s.s >= 0.99) break; await sleep(500) }` — it breaks at 0.99, **on the ramp**,
not at rest. At the 13–20 fps these gate logs show, one frame of `FOG_RAMP` is worth several times
0.01.

**Evidence it is marginal rather than broken:** the tree's own logs read `veil alpha 0.785`
(`gate-t2202`), `0.798` (`gate-review2203`) and the `0.783` that failed. It passes when the frame
skew happens to be small.

## The fix is not more frames, and not a wider tolerance

`T22.00F`'s instrument — count drawn frames, take the maximum — **does not help here**, and the
builder said so rather than applying it out of habit. This is not a two-frame sample of a drifting
shader; it is one sample of two quantities off two clocks.

**Sample both ends from the same drawn frame.** Either have `debug()` report the `fogStrength`
that was used to produce `lastFogAlpha` (write it beside it in the draw path), or read both after
the ramp has settled so the skew cannot matter — and if you choose the second, say at the code why
breaking the poll at `>= 0.99` was wrong, because that is the line that made it possible.

**Do not widen `0.01`.** `CLAUDE.md`: *remove such an assertion or fix its cause; do not weaken
it.* The tolerance is doing real work — it is what would catch `FOG_SCREEN_ALPHA` drifting from
what the screen shows, and that is a relationship nothing else checks.
