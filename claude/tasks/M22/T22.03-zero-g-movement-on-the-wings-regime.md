## The wings seam already exists — this is the re-scope

`T21.06` was written 2026-09-06, before T21.03 shipped. **Check each of these before building
on it, but they were true at the time of writing:**

- `jetpack::gravity_scale(state, flying)` **already returns `0.0` when flying.** Its own
  comment names it *"the third regime"* and explains why it lives there and not at the call
  site: *"which gravity is this player under must have exactly one answer"*.
- `MoveMods.flying` is already derived by `PlayerState::move_mods`, already a bit on the wire,
  already read by `prediction.ts`. T21.02 built `MoveMods` precisely so a movement modifier
  could not be known to one side and not the other.
- T21.34 gave wings a **hover**: no input holds position, UP climbs, DOWN descends.

So the owner's *"reuse the wings mechanic"* describes a seam rather than proposing one. **Do
not add a fourth gravity regime.** Space is the flying regime with the damping removed and a
fuel cost added.

## What wings do NOT do, which is the actual work

1. **Momentum.** Wings *assign* vertical velocity outright (`apply_flight`); space must
   *accumulate* it and never damp it. `GROUND_FRICTION` and `AIR_DRAG` must not apply, and
   "set them to zero" is not the same as saying which code path runs.
2. **A collision rule — and `R1` rules it *stop*, which costs zero lines, which is the trap.**
   `resolve.rs::move_x` already zeroes only `vel.x` on a wall and `move_y` only `vel.y` on a
   floor or ceiling. That **is** R1: lose the normal component, keep the tangential, no
   restitution. So a test named *"a collision stops you along the normal and preserves the
   tangential"* **passes today, with your code deleted, under standard gravity** — it is
   testing the framework. The collision rule is a *ruling to record*, not a feature to build.
   **The test that earns its keep is the no-damping one**: velocity persists across N ticks
   with no input and no contact, with a standard-gravity control in the same test body.
3. **A fuel cost on horizontal movement.** Wings charge nothing. Here every input costs, which
   makes the fuel tank the whole resource economy of the mode. Say what refuels it and how
   fast, or the mode ends with everyone motionless.

## `GRAVITY = 0` will not compile, and does not need to

`constants.rs` carries `const _: () = assert!(2.0 * KNOCKBACK_MAX / GRAVITY < KNOCKBACK_FIRE_GRACE);`.
At zero, `x / 0.0` is `+inf` and const-eval fails; `JUMP_HEIGHT`/`JUMP_REACH` go infinite too.
**Zero-g is a scale of 0, not a constant of 0** — it compiles, it leaves the traversal consts
alone, and since T21.03 it is a shipped path with tests around it.

## The `grounded` problem, unchanged and still the design decision

`grounded` is cleared every tick and re-set only two ways: `move_y` needs strictly positive
`vel.y` **and** a blocking overlap, and `ground_snap` needs `was_grounded` already true. **So a
body that ever leaves the ground can never land again** — it is then permanently on
`WALK_ACCEL * AIR_ACCEL_FACTOR` and `AIR_DRAG` (120 against `GROUND_FRICTION`'s 1600, a 13×
difference in stopping power) with `try_jump` dead once coyote time expires. That is most of
*"movement just doesn't stop"* arriving **by accident**. Build it deliberately.

`grounded` gates jumping, friction, fall damage, `ground_snap`, step-up and the bot's entire
movement model. **Owner question 4.** If it is always false, all of those change at once; if it
is true on contact, "landing" happens constantly.

## Hazards

- **Do not fork `apply_input`.** Two movement functions is "share the guard, or share the
  function" broken at the largest possible scale. One path, branching on the regime.
- **Prediction, and the mirror cannot learn the mode today.** `client/src/net/prediction.ts`
  (not `client/src/core/`) gates on `local.moveMods !== snap.state.moveMods` plus a 2 px
  positional epsilon. **`moveMods` is an inventory-derived bitfield** — a match-level gravity
  mode cannot ride it without becoming a stored second answer, which is the third-flag shape
  `shield_until` and `flashlight_on` were both deleted for. **`GameCore` has no gravity field
  and no way to learn one; the precedent to copy is `GameCore::set_phase(&str)` /
  `Core.setPhase()`** — a per-match constant set from the snapshot, not a per-tick wire bit.
  Momentum that never damps then makes divergence **permanent** rather than self-correcting:
  under friction a mispredicted velocity decays; here position error grows linearly and
  without bound until `prediction.ts`'s `SNAP_PX` hard-snaps, which reads on screen as
  teleporting rather than rubber-banding. `game-wasm/src/lib.rs::the_client_predicts_a_flying_player_where_the_server_puts_them`
  is the existing template and its neighbours record that this exact bug has shipped three
  times. Say how reconciliation behaves before building.
- **Bots** (`R5` — in scope, and splittable). `bots/mod.rs` assumes walking, jumping and a
  ground. A bot in zero-g with a walking model never moves, and `balance.rs` measures that as
  a game with no fights. **Not optional scope.** `bots/mod.rs` is ~2700 lines and its movement
  step reads `me.body.grounded` in at least three places (the stuck-jump `wants_jump`, the
  jetpack climb gate, the descend gate). **R5 pre-authorises the split** — if this file heads
  past ~250 lines with bots still to do, write `T22.03B — bots in space` and say so. Do not
  finish at 800 lines.
- **Fall damage.** There is no fall. Either the mode disables it or impact damage becomes the
  *collision* rule and this task owns it.
- **The destructure guard will not fire for the state this task adds, and that is the trap.**
  `world/mod.rs::state_hash_coverage::every_field_of_world_has_been_considered_for_the_state_hash`
  is a `let World { … } = w;` with no `..`, so a new field **on `World`** is a compile error
  until it is classified. But this task's new state goes on `Body`, `JetpackState` or
  `PlayerState` — all of which live *inside* `World::players` — and those are hashed by a
  **hand-written per-player fold** in `World::state_hash` with **no tripwire at all**. Nothing
  will fail to compile if you add a field and forget it; the replay will simply diverge, green.
  **Add it to the fold by hand and say you did.** Note that `body.airborne_ticks` and
  `body.landing_impact` are already unhashed, as per-tick derived values — do not read that as
  permission unless your field is derived too.
- **The `World` gravity-mode field is `T22.01`'s**, not this task's; it is the one that breaks
  the destructure, and T22.01 classifies it.
