# T22.10F — A silent player hangs in the air

Milestone: M22 · Filed by T22.10E's builder, not fixed · Pre-existing (since §A30's one-input-per-tick rule).

## The defect
`World::apply_inputs` integrates only the players it has an input for this tick (outside `Ended`, where T21.30
steps every alive body a neutral tick). A player whose inputs stop reaching the world — a stalled tab, a TCP stall, a
frame of `MAX_FRAME_DT` — is **not stepped at all**: no gravity, no attractor field, no drift, no vortex pull, until
inputs arrive again. Every other client sees that body frozen in mid-air, and then catch up (T22.10D's two-a-tick
drain) when the burst lands.

## Evidence (cheap, taken)
`crates/game-core/tests/world_step.rs::t2210f_a_silent_player_hangs_in_the_air_today` — a body lifted
`8 × PLAYER_H` into open air, stepped one second (`SIM_HZ` ticks): sent a neutral input each tick it falls
(measured 224.78 px, landing); sent nothing it moves **0.00 px**. The test pins today's behaviour so this task turns it
red on purpose.

## The design question (for the coordinator)
1. **Neutral-integrate the missing ticks** (as `Ended` already does): the body falls on every screen. But the client
   predicted that tick with its *real* input, so when the late input arrives the server has already spent the tick on
   a neutral one — the input is either dropped (a snap by one tick of travel) or applied on top (the tick counted
   twice: §A30's speed-multiplier again).
2. **Leave the tick un-integrated and let T22.10E's catch-up credit pay for it** (today): the prediction stays exact,
   at the cost of the frozen body remotes see.
3. A hybrid: integrate neutrally after a grace of `INPUT_BACKLOG_TARGET` ticks, and have the credit refuse to pay for
   ticks that were integrated — so consumed + neutral never exceed ticks elapsed.

They interact: whatever (1) or (3) integrates must stop earning credit (T22.10E F-1's rule "credit accrues only while
alive and the phase accepts input" would gain "and the tick was not already integrated"), or a stall is paid twice.

## Done when
Decided by the coordinator; the characterization test flipped to the chosen behaviour, with a control.

## As ruled (R89, coordinator, 2026-09-24)
Neither of the three options above: **replace the catch-up credit with the standard one-simulated-tick-per-server-tick
model.** Every server tick every live player is simulated exactly one step — the next expected input if it has arrived,
else a **stand-in**: the player's last input's *held* state (movement buttons + aim; edges must not re-fire; `fire` /
`use_item` / `select_slot` are separate events and unaffected). The server keeps an expected seq per player that
advances one per simulated tick, real or stand-in; an input at or below the last simulated seq is discarded; future
inputs wait in a jitter buffer of ≈`INPUT_BACKLOG_TARGET`, the **oldest** excess dropped and the expected seq jumping
past them — one bounded correction after a hitch, never a standing delay, never two steps in a tick. The credit and its
rules are deleted. The ack is the last simulated seq. `Ended` keeps T21.30/T22.10E's neutral ticks (the stand-in rule
applies only while the phase takes input). Also folded in from the T22.10E review: (a) a reconcile that flips `alive`
stays out of the rubber-band maxima; (b) `thrusters-match`'s bell arm must see bo *moving* at the bell (speed ≥
`RECONCILE_EPSILON_PX`·`SNAPSHOT_HZ`), else `control:`; (c) a vitest for the results screen's catch-up cap; (d) catch-up
neutral steps use the last aim.

## As built (2026-09-24, `1ed96a3`, `45d8244`, `283f109`)
- **`World::apply_inputs`**: per player in id order, in a phase that takes input — drop queued seqs ≤ the last
  simulated (`prev_input`'s seq, now also `World::last_simulated_seq`, the ack); trim the future ones to
  `INPUT_BACKLOG_TARGET` + the one this tick runs, oldest first; run the next, or a stand-in
  `Input::new(next, newest.buttons, newest.aim)`. `newest_input` (replaces `input_credit`) is set in `queue_input` from
  every input received, **late ones included**, so a discarded late input still steers the next stand-in. Edges are
  `current` vs `prev`, so a repeated held input fires nothing. Dead players' ticks advance the seq too (no queue of
  inputs sent while dead waits for the respawn). Credit field, `set_phase` reset and `oldest_queued_seq` deleted.
- **Two departures from the ruling's letter, said at the code:** (1) a stand-in claims the next seq only while within
  `MAX_FRAME_TICKS` of the newest seq sent, and never before the first — past that the client has *lost time* (a frame
  over `MAX_FRAME_DT` is capped), its seqs can never catch the server's, and a claimed seq would discard every input it
  sends from then on; the body still steps, only the seq stops. (2) **seq 0 means "number it next"** in `queue_input` —
  bots and ~70 test sites queue seq 0 or restart at 1; the room rejects seq ≤ its last received (starting at 0), so no
  client input can carry it.
- **Client, found by the browser checks, not asked:** GameScene's fixed step ran on Phaser's `delta`, which clamps
  every frame of an unfocused page to 16.7 ms — a 15 fps headless page simulated a quarter of real time. Harmless when
  the server ran whatever arrived; under R89 every stand-in disagreed (226 ack-gap snapshots on one client). Now
  `performance.now()`. **The local body stands in exactly as the server does** (`Predictor.standIn`): a frame's
  inputs are produced at its end, for ticks the server already stood in for and acked, so on a slow page a snapshot
  acking seqs not yet pushed is the normal case; the predictor had compared it with the last pushed state, installed
  the server's and then applied the late inputs on top (a tick counted twice, corrected back every snapshot: 145
  corrections, 476 "ack gaps" in one `crates` run → 40 and 1). It now runs the same stand-ins (last pushed
  buttons/aim, within `MAX_FRAME_TICKS`) and skips those seqs when pushed. Consequence: the client's body now **trails**
  the server's by up to one frame (it led it) — `crates`' pickup bound gains one `MAX_FRAME_DT` of travel (measured
  72, 73, 73 px against a one-poll bound of 62, deterministic). And the Predictor treats as events (counted in `settled`, out of the maxima): the first ack (the
  server steps a new player before its first input; a space body drifts to its rock meanwhile — 62 px on
  `radiation-match`), a repeated ack while the phase takes input and the first new ack after it (lost time), and a
  results-screen re-anchor past the catch-up cap.
