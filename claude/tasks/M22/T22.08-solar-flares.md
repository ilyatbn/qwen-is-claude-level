## `BurnField` is the wrong home, and its own first line says so

`weapons/burn.rs` opens: *"Damaging ground zones"*. §F12's recorded reasoning is that a fire
which drifted off the ground *"would be a second fire"*. A flare is a **ribbon moving through
open space with no ground under it** — the exact thing that comment rules out.

**So: either this is a new hazard shape, or `BurnField` is generalised deliberately and its doc
comment is rewritten to say so.** Do not quietly widen a type whose comment argues against the
widening. Whichever is chosen, say why in the file.

**CORRECTED 2026-09-20 — the paragraph that was here was backwards.** It said `BurnField`
holds a burn-duration model shared by `FLAME`, molotov and lava. **All three left that file at
§F10.2**, and `burn.rs`'s own header says so: *"**§F10.2 took the fire out of it.** All three
of those are flames now … What is left here is the **toxic grenade's cloud**"*. `BurnKind` has
exactly one arm. The §F12 sentence above is also mis-quoted — its subject is a **toxic zone**,
not a fire.

**The model the owner actually described is `poisoned_until`.** *"Burns players touching it
for N seconds"* is a **per-player status that persists after you leave**, which is
`PlayerState::poison()` / `::poisoned(now)`, whose doc comment already states the rule you
want: *"Writing the deadline is the whole rule. Adding to it would stack."* Copy that.
`BurnField::tick`'s overlap test is disqualified anyway — its own comment says the
centre-plus-half-width circle *"is **not** safe for anything small"*, and a ribbon is small.
`flame::touching` is the right shape test. See `R27`.

## The scheduler seam is **half** the right shape — see `R28`

`enabled: [bool; KINDS.len()]` is per-instance and **is** already hashed. But **`with_enabled`
is private with zero production callers** — the only production constructor is
`EffectScheduler::new(seed, round_start)`, which hard-calls `enabled_from_constants()` and
takes no mode — and **`World.gravity` is read by nothing in production**. A per-mode table
needs a new public constructor *and* the mode threaded from `World`. That is real work, not a
constructor argument.

**Two guards go quietly blind on a space table.** `two_live_kinds_alternate` opens
`if live.len() != 2 { return; }`, so a three-kind space table makes it assert **nothing**, with
no signal; `a_draw_is_always_possible` reads the same constants table and is equally blind.
Both owe a space arm.

**And a one-kind table is a live bug**: `roll_kind` zeroes the last-run kind, so one live kind
reaches `pick_weighted` with all-zero weights, which **returns 0** rather than panicking —
`KINDS[0]` = `ToxicRain`, which is switched off. **The space table must have at least two live
kinds.** (`a_draw_is_always_possible`'s doc calls this *"the panic this rules out"*; there is
no panic. Report that, do not fix it.)

## The original section, whose hash and `REPLAY_VERSION` points still hold

On 2026-09-16 `EffectScheduler`'s `toxic_enabled` bool became `enabled: [bool; KINDS.len()]` —
a per-instance field, **already hashed**, injected through `with_enabled`, with
`enabled_from_constants()` as the only thing tying it to the constants. A hazard that exists
**only in space** is that array taking its value from the match setting.

**Two consequences to plan for, not discover:**
- Adding a `KINDS` entry changes the hash shape and moves `REPLAY_VERSION`.
- `two_live_kinds_alternate` pins that two live kinds under never-repeat produce a strict
  alternation. Space's table is a different set; the same arithmetic applies to it and the test
  should be read before the table is chosen.

## Your red-before-green: the load guard cannot run the mode you are making live

**`R43`.** Space's hazard table is **solar flares and meteor showers** — two live kinds,
because `R28` measured that a one-kind table reaches `pick_weighted` with all-zero weights and
silently returns `KINDS[0]`, which is `ToxicRain`, which is switched off.

**So meteor showers become live in space, and `world/mod.rs::a_shower_keeps_a_bounded_number_of_drops_in_the_air`
structurally cannot run that mode.** It loops Standard and Low, and **both its window and its
ceiling divide by `gravity.scale()`** — at scale 0 they are `inf`/NaN.

**And space is the worst case for the exact quantity it bounds.** With no acceleration a drop
falls at a constant `TOXIC_DROP_SPEED`, so flight time is `d / v` — longer than either measured
mode, therefore **more drops airborne at once and more `ProjectileMove` per second on the
wire**. `R29` said the guard must track the mode; this task is the one that makes the third
mode live, so the space arm and its constant-speed formula are yours.

## Hazards

- **Assert on effects, not intentions.** T21.25 is the precedent — **and the citation was
  backwards.** That check *does* read health bars, because T21.25 is the task that added them:
  it has a dry-sky absence control, a sheltered-player control, a `sawPoison` wire assertion
  and a threshold pinned to `TOXIC_POISON_DPS × TOXIC_POISON_DURATION`. *"Never read a health
  bar"* describes the file **before** T21.25, not after, and ~47 was the *prediction* — the
  finding was **66.3 health a shower over six seeds**. The check is also currently
  `disabled: 'T21.41'`, because toxic rain is off. **The lesson stands and the example is a
  good one, not a bad one.** A flare check must read health.
- **T21.36's coverage lesson**: with High Quality off, flames covered **85–108** of 192
  burn-circle points (108 is the top of a range — `fire-shader.mjs`'s own comment says
  85–108, and T21.36 itself reports 85/192 and 97/192). Painted fire must cover every damage
  point in **both** modes, asserted.
- **A moving hazard is a prediction question — and the code already answers it.** The hazard
  wire is `GameEvent::HazardSpawn { id, kind, x, y, r, duration }` and `HazardEnded { id }`,
  and **there is no move event**: `grep -rn "HazardMove\|hazard_move"` over `crates/` and
  `client/src` returns **0**, and `ordnanceFx-math.ts`'s hazard loop decays `ttl` and never
  moves `x`/`y`. So **the flare's position must be a pure function of (effect seed, elapsed
  time)**, evaluated in `game-core` and re-derived in TypeScript — the
  `render/weather-math.ts::LavaClock` precedent, whose doc records that until it existed *"the
  networked client drew none of it … no light during the jet, which is the only phase that
  damages you."* **This, not the doc comment, is the real reason `BurnField` could not have
  been widened** (`R27`).
- **`ordnanceFx-math.ts::hazardKind` maps to `'toxic' | 'smoke' | 'other'`**, so a new kind
  **silently becomes `'other'`** and draws as a neutral disc. Add the arm.

## Tests

- A player touching a flare **loses health**, and one beside it does not — the control.
- The burn lasts `N` seconds, pinned to the constant, and the constant's *value* is justified
  against a measured basis (`ITEM_SPAWN_INTERVAL`'s lesson: a suite pinned to a constant cannot
  detect the constant moving).
- The painted flare covers every damaging point, in both render modes.
- It appears in space and **never** in the other modes — with the control that it does appear
  when it should, or "never" is satisfied by a hazard that was never built.
