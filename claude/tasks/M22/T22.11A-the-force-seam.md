## Deliverable

`Forces { gravity_scale: f32, accel: Vec2, max_speed: Option<f32> }` and
`Env { accel: Vec2, max_speed: Option<f32> }` / `MoveStep { mods: MoveMods, env: Env }`, exactly
as R10 spells them. `integrate(map, body, forces, dt)`. `apply_input(..., step: MoveStep, ...)`.

`accel` is `Vec2::ZERO` everywhere in this task and `max_speed` is `None` everywhere. The field
arrives in `T22.11B`.

**`apply_gravity` is not touched** — it keeps its early return, its `vel.y`, its
`MAX_FALL_SPEED` clamp and its three tests. The field goes **beside** it, inside `integrate`,
on a path the `gravity_scale == 0.0` return does not skip. The scout confirmed that is the only
place that is (i) inside the one function both sides run, (ii) downstream of nothing that skips
it, and (iii) upstream of `move_x`/`move_y`.

## **No `Default`, and this is the whole ruling** (`R45`)

Do not give `Forces` or `Env` a `Default`, and do not add a `Forces::none()` that a caller can
reach for blindly. The precedent is four files away and says why, in `MoveMods::NONE`'s doc:
*"**Not a `Default` impl, on purpose.** A `Default` is what a caller reaches for when it does
not know what to pass, and 'a caller that did not know what to pass' is the literal `1.0` the
mirror carried for fifteen milestones."*

With a `Default`, every fixture gets a field-free world for free, the whole space suite passes
while testing a space with no wells in it, and R10's nominated control passes for a build where
`accel` is never read. `Forces::gravity(1.0)` is fine — it *names* what it is.

## `R48` — the one behaviour change, and it is a bug fix in a shipped mode

`Mines::step`, `WorldItems::step`, `Tombstones::step` and `Animals::tick` each pass a **literal
`1.0`** to `integrate`. `GravityMode::Low.scale()` is `0.5`. So **in a low-gravity match a
dropped weapon falls at twice the speed of the player who dropped it**, and low gravity has
been playable since `T22.02`.

Thread the mode to all four. **Its test is red first** — assert a dropped item's fall in `Low`
against the player's, before the fix, and watch it fail. That is the only assertion in this
task that starts red, and R14's space behaviour (scale `0.0`) lands with it.

Threading the argument does **not** add the test. The scout flagged this exact trap: the six
mine assertions and the items/tombstones/animals tests all keep passing at
`GravityMode::Standard` while `Low` and `Space` go untested.

## Hazards

- **`no_tunnelling_at_ten_times_terminal_velocity_through_integrate` is the tripwire.** It
  drives `vel.y = 9000`, `vel.x = ±5000` through `integrate`. It passes **only** if
  `Forces::gravity(1.0)` carries `max_speed: None` — it is the one existing test that can
  detect a `max_speed` leaking onto the standard-gravity path. Do not "fix" it if it goes red;
  it is telling you something true.
- **Do not re-derive the gravity arithmetic at four call sites.** `jetpack::thrust_delta`
  already carries the warning: *"`(-2200 + 900) * dt` and `-2200 * dt + 900 * dt` are not the
  same `f32`."* Four re-derivations is four chances at a different float on client vs server.
- **`MovementState` has zero production callers** but is `pub` and used by **35** `.step(` sites
  in `tests/movement_scenarios.rs`. It changes signature anyway.
- **Velocity is written outside `integrate` in three production places** — `jetpack::apply_thrust`,
  `weapons/explode.rs`, `weapons/melee.rs`. A `max_speed` inside `integrate` clamps them one
  tick late. That is tolerable and it is **not** this task's to fix; the real answer is a shared
  `Body::add_velocity`, which is bigger than this task. **Say it at the code** so the next
  reader does not think the clamp is tighter than it is.
- **Borrow fight, unconfirmed.** `World::apply_inputs` already does `let gravity = self.gravity;`
  for exactly this reason. Computing `env` before the mutable player borrow is expected to work;
  the scout did not compile it. If it does not, say what you did instead.

## Tests

- **The control, and it is the whole point:** `resolve::a_resting_body_is_bit_identical_after_600_ticks`
  passes **untouched**, and the golden table does not move. If either shifts, this refactor
  changed physics and must be reverted, not adjusted (`CLAUDE.md`: revert what you cannot
  explain).
- `R48`'s low-gravity assertion, red before green.
- The four steppers under `Space` put a body at scale `0.0` (`R14`).

**What these tests cannot report, and say so in the journal:** none of the 20 tests in
`player/space.rs` can see a field that never fires — they run on a fixture with no asteroids.
That hole is `T22.11B`'s to close, and its first test must use a fixture that actually has rocks.
