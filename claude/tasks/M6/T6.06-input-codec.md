## Deliverable

**TypeScript encode:**
```ts
export function encodeInputBatch(inputs: readonly Input[]): ArrayBuffer;
```

**Rust decode + sequencing:**
```rust
pub struct InputBatch { pub inputs: SmallVec<[Input; INPUT_REDUNDANCY]> }
pub fn decode_input_batch(bytes: &[u8]) -> Result<InputBatch, CodecError>;

/// Per-player sequence tracking. Rejects duplicates and stale inputs.
pub struct InputTracker { last_accepted: u32, accepted_this_tick: u8 }
impl InputTracker {
    pub fn accept(&mut self, input: &Input) -> bool;
    pub fn begin_tick(&mut self);
}
```

Layout:
```
u8 count (1..=INPUT_REDUNDANCY)
per input (7 bytes): u32 seq, u16 aim, u8 buttons
```
22 bytes at count 3.

## Notes

**Redundancy is what makes this robust**: each packet carries the last 3 inputs, so
a dropped packet costs nothing — the next one re-delivers the missing sequences.
This works only because the wire format is **held state, not edges**
(`docs/20-player-movement.md` §7); a lost edge would be gone forever, but a lost
"button is down" is re-established by the next packet.

`InputTracker::accept` rules:
- reject any `seq <= last_accepted` (duplicate or stale) — this is what makes
  redundancy free rather than a source of double-applied input;
- reject once `accepted_this_tick` reaches `MAX_INPUT_QUEUE` (8), and log at `debug`
  on `game::net` with the player id and the drop count;
- otherwise accept and update `last_accepted`.

`begin_tick` resets the per-tick counter.

The decoder handles untrusted input: reject `count == 0`, `count > INPUT_REDUNDANCY`,
and any buffer whose length disagrees with `count`. **Never panic** — a panic in a
decoder reachable from the network is a remote crash.

Bit 7 of `buttons` is reserved; mask it off on decode rather than rejecting, so a
future client that sets it degrades gracefully.

The client sends at the sim rate (60 Hz). At 22 bytes that is 1.3 KB/s up, which is
comfortable — do not batch further.

## Tests

**TypeScript:**
- `encodeInputBatch` with 1, 2 and 3 inputs produces 8, 15 and 22 bytes.
- With more than `INPUT_REDUNDANCY` inputs it sends only the last 3.
- With 0 inputs it produces nothing or is rejected by the caller (state which).

**Rust:**
- Round-trip: encode in TS (fixture), decode in Rust, every field matches.
- `count == 0` is rejected.
- `count > INPUT_REDUNDANCY` is rejected.
- A truncated buffer is rejected.
- A buffer longer than `count` implies is rejected.
- Bit 7 of `buttons` is masked off, not rejected.
- **Sequencing**: seq 1,2,3 all accepted; replaying 2,3 afterwards is rejected.
- Out-of-order arrival (3 then 2) accepts 3 and rejects 2.
- A duplicate seq is rejected.
- More than `MAX_INPUT_QUEUE` accepted inputs in one tick: the excess is rejected and
  the count resets on `begin_tick`.
- **Fuzz**: 10 000 random byte strings are all decoded or cleanly rejected, with no
  panic.
