## Deliverable

**Server:** every `MASK_CHECKSUM_INTERVAL` (5 s), broadcast
`mask_checksum { tick, hash }` where `hash` is the first 8 bytes of
`blake3(mask.words)`. On `resync_map`, send that client a fresh `map_init`,
rate-limited to once per 10 s per client.

**Client:** on `mask_checksum`, hash the local mask and compare. On mismatch, log
loudly and call `requestResync()`; on the fresh `map_init`, reload the mask and
rebuild every chunk.

```ts
export interface ChecksumStatus { state: 'matched' | 'mismatched' | 'resyncing';
                                  lastCheckedTick: number }
```

## Notes

**This should never fire.** Carve rasterisation is integer-exact and carves are
applied in `seq` order, so client and server masks are bit-identical by
construction. The checksum exists because the alternative failure mode is
catastrophic and silent: a one-pixel divergence surfaces hours later as "sometimes I
get shot through a wall", with nothing in any log to explain it.

So the value here is entirely in the **log line**. On mismatch, log at `error` with
the tick, the seed, both hashes and the carve `seq` the client last applied. That
single line turns an unreproducible complaint into a specific bug.

Rate-limit the resync: a client whose mask is genuinely broken would otherwise
request a fresh map every 5 seconds forever, and `map_init` is 20–60 KB.

The client hashes **at the tick named in the message**, not at the moment of
receipt. Snapshots and carves may still be in flight. In practice, hash when the
local carve sequence has caught up to the message's tick; if it has not within
500 ms, skip that check rather than reporting a false mismatch. A false alarm here
is worse than a missed one, because it trains you to ignore the alert.

During `resyncing`, suspend carve application and buffer incoming carves — applying
them to a mask that is about to be replaced is wasted work and confuses the sequence
counter.

Reuse `Mask::hash` (T1.01) on the server and `Core.maskHash` (T3.02) on the client,
so both hash the same bytes the same way.

## Tests

**Server:**
- A checksum is broadcast every `MASK_CHECKSUM_INTERVAL` and not more often.
- `resync_map` produces a fresh `map_init` reflecting the current damaged map.
- A second `resync_map` within 10 s is ignored and logged.

**Client:**
- A matching checksum leaves `state` as `matched` and requests nothing.
- A deliberately corrupted local mask produces a mismatch, an `error` log and a
  resync request.
- The log line includes the tick, the seed and both hashes.
- During `resyncing`, incoming carves are buffered, not applied.
- After the fresh `map_init`, the buffered carves apply and the hash matches.
- A checksum for a tick the client has not reached yet is deferred, not reported as
  a mismatch — this is the false-alarm test and it matters.
- A deferred check that never catches up within 500 ms is skipped silently.

**Integration** (in T6.13, but assert it here too if practical):
- Two clients firing 100 rockets end with mask hashes identical to the server's.
