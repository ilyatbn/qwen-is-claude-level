## Deliverable

```rust
pub enum Command {
    Join { socket: SocketRef, name: String, skin_id: u16 },
    Ready(PlayerId),
    Input(PlayerId, InputBatch),
    UseItem(PlayerId, u8),
    SelectSlot(PlayerId, u8),
    ToggleFlashlight(PlayerId),
    VoteRestart(PlayerId, bool),
    ResyncMap(PlayerId),
    Leave(PlayerId),
}

pub struct RoomHandle { tx: mpsc::Sender<Command> }
impl RoomHandle { pub fn send(&self, c: Command); }

/// Spawns the room task and returns a handle. The task owns the World outright.
pub fn spawn_room(io: SocketIo, config: Arc<Config>) -> RoomHandle;
```

The loop, exactly as the doc's §2:
```rust
let mut ticker = interval(Duration::from_secs_f64(1.0 / SIM_HZ as f64));
ticker.set_missed_tick_behavior(MissedTickBehavior::Burst);
loop {
    tokio::select! {
        _ = ticker.tick() => {
            drain_commands(&mut rx, &mut world);
            world.step(SIM_DT);
            flush_events(&io, &mut world);
            if world.tick % 3 == 0 { broadcast_snapshot(&io, &world); }
            maybe_send_checksum(&io, &world);
        }
        _ = &mut shutdown => break,
    }
}
```

## Notes

**One task owns the `World`. No locks on game state.** Socket handlers only parse
and push into the channel. This is what makes the simulation deterministic given the
same command sequence, which is what makes the replay system (T8.01) possible at
all. Do not reach for `Arc<Mutex<World>>` — if something seems to need it, that is a
signal to reconsider, not to add the lock.

`MissedTickBehavior::Burst` matters: if the process is descheduled for 50 ms the loop
catches up rather than silently running slow, so round time stays true to
wall-clock. If it falls more than 10 ticks behind, log `warn` on `game::sim` with
the lag — that is the signal the tick is too expensive.

**Set a `tracing::span` with `room` and `tick` once per tick**, so every log line
inside the loop carries them automatically rather than by remembering
(`docs/61-logging-debug.md` §2).

`drain_commands` must be bounded — `try_recv` in a loop with a cap (say 256) so one
noisy client cannot starve the tick. Per-player, at most `MAX_INPUT_QUEUE` (8)
inputs are accepted per tick; drop the excess and log at `debug` on `game::net`.

Graceful shutdown: on the shutdown signal, broadcast
`round_end { reason: "server_shutdown" }`, flush any replay file, and return. Docker
sends `SIGTERM` on `compose down`, so a clean path here keeps replay files intact.

v1 has exactly one room, spawned at startup. `RoomHandle` is the seam for a registry
later (`docs/41-server-loop-rooms.md` §9).

## Tests

`crates/game-server/tests/room.rs`:

- The room task starts and ticks at approximately `SIM_HZ` — measure over 2 s and
  assert within 5 %.
- A `Join` command seats a player and the world reflects it.
- A `Leave` removes them.
- Commands sent between ticks are all applied on the next tick.
- More than `MAX_INPUT_QUEUE` inputs from one player in a tick: the excess is
  dropped, and the tick still completes.
- A flood of 10 000 commands does not stall the tick loop beyond one tick.
- Snapshots are emitted every 3rd tick.
- The shutdown signal ends the task within 1 s and emits `round_end`.
- A panic in a command handler does not kill the room task (wrap handling in
  `catch_unwind` or assert the handler cannot panic — state which you chose).
- Log lines from inside the loop carry `room` and `tick` fields — assert against a
  captured `tracing` subscriber.
