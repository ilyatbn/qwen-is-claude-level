Delivery scope per event — **this is the part that matters**:

| Scope | Events |
|---|---|
| Everyone | `carve`, `explosion`, `projectile_spawn`, `projectile_despawn`, `hitscan`, `item_spawn`, `item_pickup`, `item_despawn`, `crate_spawn`, `death`, `respawn`, `score`, `effect_*`, `hazard_spawn`, `phase_change`, `round_state`, `round_end`, `player_join`, `player_leave`, `mask_checksum` |
| Owner only | `inventory` |
| Victim and attacker only | `damage` |

## Notes

**`inventory` must never reach anyone but its owner.** Other players' inventories
are deliberately private — what someone is holding is visible from their sprite,
which is intentionally imperfect information (`docs/30-items-inventory.md` §6).
Leaking it is a small but real competitive advantage, and it is the kind of thing
that is easy to get wrong when adding a broadcast helper later. Write the test.

**`carve` carries a per-round monotonic `seq`.** Every terrain change on the server
produces exactly one `carve` event, and clients apply them in `seq` order
(`docs/11-map-destruction.md` §6). Assign the sequence here, in emission order, and
never reorder or coalesce carves — coalescing two overlapping carves into one
changes the resulting mask and breaks the bit-identical guarantee.

Explosions emit **both** an `explosion` (cosmetic) and a `carve` (authoritative).
Keeping them separate means a client that drops the pretty flash still gets the
terrain right. Do not merge them.

Every event carries the `tick` it occurred on, so the client can order it against
snapshots.

All events are JSON. They are low-frequency relative to snapshots and being
human-readable in a log is worth far more than the bytes
(`docs/40-net-protocol.md` §Encoding). The one bursty case is a meteor shower, which
peaks around 6 KB/s — still fine.

Batch all of a tick's events into as few emissions as the socket.io API allows, but
do not invent a custom envelope format. Simplicity wins here.

## Tests

`crates/game-server/tests/events.rs`, with multiple real clients:

- A carve on the server produces exactly one `carve` event on every client.
- `carve` sequence numbers are monotonic with no gaps across a round.
- Two overlapping carves in one tick produce **two** events, not one.
- An explosion produces both `explosion` and `carve`.
- **`inventory` is delivered only to its owner** — connect three clients, change one
  player's inventory, and assert the other two received nothing.
- `damage` reaches only the victim and the attacker.
- `death` reaches everyone.
- Every event includes a `tick` field.
- Events from one tick arrive before events from the next.
- A client that connects mid-round does not receive replays of past events.
- A meteor shower's event burst is delivered without dropping any (count
  `hazard_spawn` events against the server's spawn count).
- `player_leave` is emitted when a socket disconnects abruptly, not only on a clean
  close.
