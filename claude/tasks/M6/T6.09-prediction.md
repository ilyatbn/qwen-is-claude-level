## Deliverable

```ts
export class Predictor {
  constructor(core: Core, localId: number);

  /** Called every frame: sample, buffer, send, and apply locally at once. */
  pushInput(input: Input, dt: number): void;

  /** Called on each snapshot: drop acknowledged inputs, correct, replay. */
  reconcile(snapshot: Snapshot): void;

  /** Simulation position (authoritative-ish). */
  readonly state: PlayerState;
  /** Rendered position — smoothed toward `state` after a correction. */
  readonly renderPos: { x: number; y: number };

  updateRender(dt: number): void;

  readonly stats: {
    pending: number; corrections: number;
    lastCorrectionPx: number; maxCorrectionPx: number;
  };
}
```

Reconciliation, exactly as the doc's §2:
```
drop pending inputs with seq <= snapshot.lastInputSeq
error = distance(state.pos, snapshot.myPos)
if error > RECONCILE_EPSILON_PX:
    state = snapshot.myState
    for each remaining pending input: core.applyInput(...)
```

## Notes

The reason this works at all is that `core.applyInput` is the **same compiled Rust
code** the server runs (`docs/01-architecture.md`). Replaying `n` pending inputs
from a corrected state lands exactly where the server will land. There is no
approximation to tune.

**Snap the simulation, smooth the render.** On a correction, `state` jumps to the
server's value immediately — the simulation must never lag the truth, or every
subsequent prediction compounds the error. But `renderPos` eases toward `state` over
~100 ms so the player sees no teleport. Above 64 px (a big knockback, a respawn),
snap the render too: smoothing a teleport looks worse than the teleport.

**Predict only what your own input fully determines.** Not damage, not death, not
knockback, not pickups, not weather — the doc's §3 table. Each of those waits for
the server. It is tempting to predict pickups because they feel laggy; do not.
A pickup you predicted and lost is worse than one that arrived 60 ms late.

Do not predict firing either (`docs/42-netcode-prediction.md` §5): play the muzzle
flash and recoil immediately, but the projectile appears when `projectile_spawn`
arrives. Un-spawning a rejected projectile looks worse than a four-frame delay.

**Track the correction rate.** If corrections above the epsilon happen constantly,
something is genuinely wrong, and the number is the only way to know. T8.03 displays
it.

The pending buffer is bounded (say 240 inputs = 4 s). If it overflows, the
connection is in trouble — clear it and resync rather than growing without bound.

## Tests

`client/src/net/prediction.test.ts`, with a real `Core`:

- `pushInput` moves the local player immediately, in the same frame.
- Pending inputs accumulate and are sent.
- **The reconciliation identity**: a snapshot acknowledging seq N drops exactly the
  inputs up to N; replaying the rest from the snapshot state matches simulating them
  from the pre-snapshot state. This is the core property — if it fails, nothing else
  in this file works.
- An error under `RECONCILE_EPSILON_PX` produces **no** correction (assert `state` is
  unchanged bit for bit).
- An error over the epsilon snaps `state` and increments `corrections`.
- After a correction, `renderPos` moves smoothly toward `state` over ~100 ms rather
  than jumping.
- A correction over 64 px snaps `renderPos` too.
- With zero packet loss and matching physics, `corrections` stays 0 over 600 frames.
- With a deliberately perturbed server state, corrections occur and converge —
  `state` matches the server within one snapshot.
- The pending buffer never exceeds its cap; overflow clears and flags a resync.
- `stats.maxCorrectionPx` tracks the largest correction seen.
