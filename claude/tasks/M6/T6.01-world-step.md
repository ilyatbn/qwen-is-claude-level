## Deliverable

The single object that owns everything and advances it one tick.

```rust
pub struct World {
    pub map: Map,
    pub players: Vec<PlayerState>,        // kept sorted by id
    pub items: WorldItems,
    pub projectiles: Projectiles,
    pub spawn_schedule: SpawnSchedule,
    pub effects: EffectScheduler,
    pub buried_items: Vec<ItemId>,
    pub round_time: f32,
    pub tick: u32,
    pub phase: RoundPhase,
    pub wind: f32,
    events: Vec<GameEvent>,
    rng: ChaCha8Rng,
}

pub enum GameEvent { /* one variant per row of docs/40-net-protocol.md §3 */ }

impl World {
    pub fn new(seed: u64, scale: MapScale) -> Self;
    pub fn add_player(&mut self, id: PlayerId, skin_id: u16, name: String);
    pub fn remove_player(&mut self, id: PlayerId);
    pub fn queue_input(&mut self, id: PlayerId, input: Input);

    /// Advance one tick. THE ordering contract.
    pub fn step(&mut self, dt: f32);

    pub fn drain_events(&mut self) -> Vec<GameEvent>;
    pub fn state_hash(&self) -> [u8; 32];   // for replay verification
}
```

## Notes

**The order in `step` is a contract, not an implementation detail.** Implement it
exactly as `docs/41-server-loop-rooms.md` §2 lists it:

1. advance round time and the day/night cycle;
2. apply player inputs — **in ascending `PlayerId`, always**;
3. integrate players;
4. integrate projectiles, resolve collisions and explosions;
5. tick the weather scheduler and all active hazards;
6. integrate world items and crates;
7. resolve pickups — again in ascending `PlayerId`;
8. damage-over-time, overheal decay, shield expiry;
9. deaths and respawns;
10. despawn expired items and projectiles.

**Keep `players` sorted by id and iterate it directly.** Never a `HashMap`. Two
players reaching one item on the same tick must resolve identically in a live round
and in a replay; hash iteration order makes that a coin flip that only misbehaves
under load, which is the worst kind of bug.

Phase gating: no damage, no weather and no item spawns during `Warmup`
(`docs/41-server-loop-rooms.md` §3). Gate at the top of the relevant steps, not
inside each subsystem.

Events accumulate into `self.events` during the step and are drained by the caller
afterwards. `game-core` never emits them itself — it has no idea a network exists.

`state_hash` covers the mask, every player's position/velocity/health/score, item
positions and projectile positions. It is the footer of a replay file (T8.01) and
the fastest possible way to locate a determinism regression.

No `tokio`, no `std::time`, no logging. `dt` is passed in; `round_time` is
accumulated. This is what lets the replay binary run the identical simulation at
full speed with no clock at all.

## Tests

`crates/game-core/tests/world_step.rs`:

- A fresh world has a valid map, no players, and `tick == 0`.
- `step` advances `tick` by 1 and `round_time` by `dt`.
- **Determinism**: two worlds from the same seed, given the same input sequence for
  1000 ticks, have identical `state_hash`.
- **Player order independence**: adding players in id order 1,2,3 versus 3,2,1
  produces the same `state_hash` after 100 ticks.
- **Pickup tie**: two players contacting one item on the same tick — the lower id
  always wins, across 100 runs.
- No damage is applied during `Warmup` — fire a rocket into a player and assert
  health is unchanged.
- No weather effect starts during `Warmup`.
- No item spawns during `Warmup`.
- A player firing a bazooka produces `projectile_spawn`, then later `explosion` and
  `carve` events.
- A player dying produces a `death` event and `item_spawn` events for the drop.
- `drain_events` empties the queue; a second call returns nothing.
- Events carry the tick they occurred on.
- 6 players + 20 projectiles: one `step` completes in under 2 ms in release.
- 3600 ticks with no input leaves every player's position bit-identical.
